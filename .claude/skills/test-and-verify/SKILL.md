# test-and-verify

**PR作成の前提条件**です。ここを通っていないPRは作りません（[[commit-and-pr]]）。

## コマンドの決め方

順に探し、**最初に見つかったものを使います**。勝手に別のコマンドを発明しないでください。

1. `aidev.yaml` の `quality_gates:`（`format` / `lint` / `typecheck` / `test`）— **最優先**
2. CI定義（`azure-pipelines*.yml` 等）が実際に流しているコマンド
3. マニフェストのスクリプト（`package.json` の `scripts`、`Makefile` のターゲット等）

`quality_gates` に定義があるのに別コマンドを使うと、PostToolUse hook の
`aidev hook quality-gate` と結果が食い違います。合わせてください。

## 実行順（早く落ちるものから）

```text
format → lint → typecheck → build → test
```

この順にする理由は**フィードバックが速い順**だからです。型エラーがあるのに
テストを先に流すと、無関係な失敗の山を読む時間が無駄になります。

**作業ディレクトリに注意**してください。PKGのコマンドは `src/` の中で実行します。
ラッパー側のルートで `npm test` を叩いても、それはPKGのテストではありません。

## 落ちたときの手順

1. **出力を最後まで読む**。最初のエラーだけ直して再実行しない
2. **自分の変更が原因か切り分ける**。変更前から落ちていたなら、それは
   別の問題です。勝手に直さず、事実として報告します
3. 直す → **同じゲートを最初から流し直す**（差分実行で済ませない）
4. 3回直して通らない、または原因が範囲外 → 停止して報告（[[failure-triage]]）

## 報告のしかた（最重要）

> **実行していないものを「通った」と書かない。**

| 状況 | 書き方 |
| --- | --- |
| 実行して通った | `lint: pass (npm run lint)` |
| 実行して落ちた | `test: FAIL — 3 failing。出力は以下` + **実際の出力を貼る** |
| コマンドが無い | `typecheck: 未定義（aidev.yaml にも CI にも無い）` |
| 実行しなかった | `test: 未実行（理由: ...）` |
| 変更前から落ちている | `test: FAIL（変更前から既存。自分の変更とは無関係）` |

落ちたものを省いた要約は、デバッグを妨げます。**落ちた事実がいちばん重要な情報**です。
「おそらく通るはずです」は報告ではありません。流していないなら「未実行」です。

## テストを足すべき場合

- バグ修正 → **その不具合を再現するテスト**を先に書く（修正前に落ちることを確認する）
- 新機能 → 正常系に加えて、境界値・空入力・エラー経路
- 既存テストが無いモジュール → 最低限、変更箇所を通るテストを1本

テストが無いことを理由にテストを省かないでください。

## やってはいけないこと

- 落ちているテストを `skip` / `it.only` / コメントアウトで黙らせる
- アサーションを実装に合わせて緩める（実装が正しいと確認できた場合を除く）
- タイムアウトを延ばして誤魔化す
- `--force` / `--no-verify` でゲートを迂回する
- 秘密情報を含むログをそのまま貼る（[[secure-coding]]）

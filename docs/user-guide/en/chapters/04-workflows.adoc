[[workflows]]
== Delegating work to the AI (workflows)

Workflows are the only entry point for handing development work to the AI. You decide up front what the AI should do and how far it may rewrite, review that, and run only what was approved.

Here is who does what.

[cols="1,3,2",options="header"]
|===
|Role |Task |Reference

|Engineering Manager
|Defines the workflow, tries it locally, then sends it for review
|xref:workflows-define[Defining a workflow], xref:workflows-trial[Trying it before approval], xref:workflows-submit[Submit]

|Reviewer
|Reviews the definition and puts it on `main`. **Taking it in is the approval.**
|xref:review-workflow-def[Workflow definition pull requests]

|Developer
|Runs an approved workflow and sends the result for review
|xref:workflows-run[Running a workflow]
|===

**The Developer who runs it is not responsible for the result.** Responsibility lies with the person who reviewed the definition and the person who reviews the result PR.

The machinery of a run (loops, retries, running commands, committing, opening the PR) belongs to the ADK and cannot be written in the definition. What the definition cannot express is a request to the ADK.

[[workflows-define]]
=== Defining a workflow (Engineering Manager)

There are two ways to create a template. Each only writes `.aidev/workflows/<name>/workflow.yaml`; nothing runs.

[source,bash]
----
aidev create workflow write-tests                          # empty template
aidev create workflow write-tests --describe "Write tests for a given target in the existing style, make them pass, then open a PR"
----

`--describe` starts the workflow-creator agent and has it write the YAML. If agents or skills are missing, workflow-creator starts agents-creator as a subagent and has it write them in `.aidev/agents/` and `.aidev/skills/`. When an external system (Work Items, tickets, a database) is needed, it puts a proposed MCP server definition for the PKG's `.mcp.json` in its report (a person adds it). Afterwards the CLI validates it and shows the result and the next steps.

You can also start from a **standard workflow** the ADK bundles. `aidev create workflow e2e-tests --from playwright-tests` copies the workflow that writes Playwright tests from a test specification, and its agents and skills, into this PKG (xref:workflows-standard[Starting from a standard workflow]).

The definition lives in two places.

[cols="1,3,3",options="header"]
|===
|Where |What it decides |Example

|`workflow.yaml` (**constraints**)
|The order of the steps, the agent of each step, where that step may write, when it is done, the limits
|The survey step writes nothing. The implementation step writes only `tests/**`

|The agent's frontmatter (**capabilities**)
|The skills, tools, MCP servers and subagents that agent can use
|test-writer has the test-and-verify instructions and uses only Read, Edit and Write
|===

When you want the same agent to have different permissions for different jobs, split it into separate agents (a read-only `ticket-reader` and a `ticket-updater` that updates, for instance). To add capabilities in one workflow only, write them in that workflow.yaml's `agents:` (`skills`, `mcp` and `subagents` are added; `tools` replaces; xref:workflows-agents-skills[Agents and skills]).

Edit the template to fit the PKG. Most of the time you change each step's `writable` (where that step may write) and `until.command` (this PKG's test command).

[source,yaml]
----
name: write-tests                  # matches the directory name; lowercase, digits, hyphens
description: Write tests for the given target in the existing style, make them pass, then open a PR

objective: |                       # the objective handed to every agent step (required)
  Add tests for the target named in --task. Follow the way existing tests are
  written and run. Do not change the code under test.

# tool: claude                     # optional; one of tools.default in aidev.yaml. Default is tools.agent
# model: sonnet                    # optional; "" leaves it to the tool's default

steps:                             # run top to bottom
  - id: survey
    description: Survey how tests are written and find the missing ones   # optional; for the reviewer
    agent: test-investigator       # .aidev/agents/<name>.md (this PKG's agent) first, then the kit's bundled ones
    writable: []                   # required; this step writes nothing
    prompt: Find out how tests are written and run, and list the behaviours not yet covered in your final report.
  - id: write
    description: Write the tests found and fix them until they pass
    agent: test-writer
    writable: [tests/**]           # this step may write only inside tests/
    prompt: Write the tests the previous step listed, in the existing style, and run them.
    until:                         # when the step is done; the agent is repeated until it is
      command: npm test            # this exits 0 (no shell)
      max_retries: 4               # how often the agent is started again when the check fails (default 3, ceiling 10)
  - id: pr
    pull_request:                  # commit the changes in each step's writable → push → PR
      title: "test: add the missing tests"   # optional

limits:                            # what stops the run
  max_usd: 8                       # required. Once the reported cost reaches this, no further agent is started
  max_minutes: 45                  # optional. A time limit for the whole run; without it, time does not stop the run
----

[%autowidth.stretch,options="header"]
|===
|Key |Meaning

|`objective`
|The objective placed at the top of every agent step's instructions. Required.

|`tool` / `model`
|If omitted, `tools.agent` / `tools.agent_model` of `aidev.yaml` apply (or the per-agent `tools.agents.<name>` if present). `tool` must be one of `tools.default`.

|`steps`
|Run from top to bottom. Each step is exactly one of an agent step, a command step, a pull-request step or a parallel group, decided by which key it has: `agent`, `command`, `pull_request` or `parallel`. Every kind may have a `description` (optional) for the reviewer.

|`agents`
|Optional. What this workflow adds to its agents (`skills`, `mcp` and `subagents` are added; `tools` replaces) (xref:workflows-agents-skills[Agents and skills], xref:workflow-reference-agents[agents]).

|`inputs`
|Optional. Declares the values taken per run with `--input <name>=<value>`. They go where the definition writes `{inputs.<name>}` (xref:workflows-inputs[Taking values that change per run]).

|`env_required`
|Optional. Declares the environment variables (passwords, tokens) the person running it must set in their shell. Without them, nothing starts. The values only reach the environment of the agents and commands and are recorded nowhere (xref:workflows-env-required[Taking credentials from environment variables]).

|`provide`
|Optional. Files git ignores that are copied from your checkout into the run's worktree (globs) (xref:workflows-provide[Providing files the worktree lacks]).

|`never_commit`
|Optional. Paths a run never commits, on top of the ADK's own list (globs) (xref:workflows-never-commit[What is never committed]).

|agent step
|`agent`, `writable` and `prompt` are required. With `until`, the agent is repeated until `until` is met (started again at most `until.max_retries` times). `timeout_minutes` (the time allowed for one start of the agent) is optional.

|`until`
|When the step is done. Write `command` (it exits 0), `agent` + `prompt` (that agent passes the work), or both. With both, the agent checks only after the command passes. A list under `command` runs from top to bottom. `cwd`, `env` and `timeout_minutes` say how the commands run (xref:workflows-commands[Writing commands]). `max_retries` is how often the agent is started again when the check fails (default 3, at most 10; 0 means no retry). A step without `until` is not retried. For the agent check, see xref:workflows-until-agent[Letting an agent's review decide when a step is done].

|`writable`
|Paths (globs) the agent of that step may write. **The only place the AI can write PKG source is this range of the step now running in an approved workflow.** `protected` (`.claude/**`, `.aidev/policy.yaml` and so on) and `secrets_paths` cannot be written. `[]` means nothing can be written (a research-only step).

|`unchanged`
|Optional. Paths (globs) the step must not change. They cannot be written even inside `writable`, and the step fails if their contents differ after it (xref:workflows-unchanged[Naming what must not change]).

|`for_each`
|Optional. Repeats the step, starting the agent anew, for each target in a list (`from`). `max_items` is required (xref:workflows-for-each[Repeating a step per target]). `parallel` sets how many targets run at once (xref:workflows-parallel[Running agents in parallel]).

|parallel group
|The agent steps listed under `parallel:` start together; the run goes on when all have ended. Steps whose `writable` may overlap are refused (xref:workflows-parallel[Running agents in parallel]).

|command step
|`command` is split on whitespace and run without a shell. Any exit other than 0 fails the workflow. `cwd`, `env` and `timeout_minutes` are optional. To include files the command makes in the PR, list where they are in `writable` (the ADK runs the command itself, so the write guard does not apply).

|`pull_request`
|Pushes the steps' changes (each step's checkpoint commit, plus what is left inside the steps' `writable`) and opens a PR. `title` is optional; without it, write `pull_request: {}`. At most one.

|`limits.max_usd`
|Required. When the total cost reported by the tool (Claude Code only) reaches this, no further agent is started and the workflow stops.

|`limits.max_minutes`
|Optional. A time limit for the whole workflow, in minutes. Without it, time does not stop the run (the cost limit and the retry limits do). AI tools other than Claude Code report no cost, so with them it is required.
|===

Any key not in the table above is refused by validation. The type, default and allowed values of every field are in the xref:workflow-reference[Workflow definition reference].

What stops a run is the following. The cost limit cannot be omitted, and the retry and target ceilings cannot be raised.

* The cost limit (`limits.max_usd`, required)
* The retries per step (`until.max_retries`, at most 10) and detection of the same failure (stop when the result of `until` is identical twice in a row)
* The targets of a `for_each` (`max_items`, at most 10000)
* The time for one start of an agent and for one command (`timeout_minutes`, at most 240; 30 by default for an agent), which ends an agent or a command that hangs
* The time for the whole run (`limits.max_minutes`), optional

How to write a large job to run unattended is in xref:workflows-unattended[Running a large job without anyone stepping in].

[[workflows-standard]]
==== Starting from a standard workflow (`--from`)

The ADK bundles workflows for common jobs as **standard workflows**. `aidev list workflows` lists them at the end.

[cols="1,3",options="header"]
|===
|Standard workflow |What it does

|`playwright-tests`
|Writes a Playwright test for each case of a test specification (CSV, Markdown or text; one line or one section per case), runs it against the target environment and fixes it until it passes, has an agent review the whole against the specification once every case passes, and opens a PR. The cases are split into batches handled at the same time
|===

A standard workflow does not run inside the ADK. Copy it into the PKG with `--from` and use it there. `templates/workflows/<standard>/README.md` in the ADK checkout is a guide to that workflow: its flow, what it assumes, and the steps from the copy to a run (`aidev create workflow --from` prints where it is).

[source,bash]
----
aidev create workflow e2e-tests --from playwright-tests
----

[source,text]
----
aidev create workflow e2e-tests
✓ wrote .aidev/workflows/e2e-tests/workflow.yaml
✓ wrote .aidev/agents/playwright-test-planner.md
✓ wrote .aidev/agents/playwright-test-reviewer.md
✓ wrote .aidev/agents/playwright-test-writer.md
✓ wrote .aidev/skills/playwright-testing/SKILL.md
    from the kit's standard workflow playwright-tests: テスト仕様書（CSV など）の 1 ケースごとに Playwright のテストを書き、通るまで直し、全件通ったら agent がレビューして PR にする
    the files are this PKG's now: edit what differs here (the paths the steps write, the commands they run), then submit them for review
    how to use it: /home/me/ai-dev-kit/templates/workflows/playwright-tests/README.md
    inputs: spec (a file, --input only), base_url (required), test_user (required), batch_size (default 10)
    set this PKG's values once in aidev.yaml (--input overrides them per run):
      workflows:
        e2e-tests:
          inputs:
            base_url: <テスト対象環境の URL（ルート。例 https://staging.example.com）>
            test_user: <テストユーザーのログイン ID（ユーザー名かメールアドレス）>
            batch_size: 10
    before a run, export in the shell: E2E_PASSWORD (テストユーザーのパスワード（実行する人が export する。ファイルには書かない）)

ℹ Next:
    1. review:  git diff -- .aidev/workflows/e2e-tests/ .aidev/agents/ .aidev/skills/
    2. try:     aidev run workflow e2e-tests --trial   ← runs it as it is here; pushes nothing
    3. submit:  aidev submit workflow e2e-tests        ← branch + pull request for the reviewer
    4. run:     aidev run workflow e2e-tests           ← once merged (anyone on the team)
----

* What is copied is `workflow.yaml` (its `name:` is rewritten to the name you gave) and the agents (`.aidev/agents/`) and skills (`.aidev/skills/`) it uses. Once copied, they are **this PKG's files**. Like any other workflow, try it with `--trial`, open a PR with `aidev submit workflow`, and approve it by merging. A run never refers to the ADK's files.
* When the same agent or skill is already there with the same contents, it is kept (`kept`); when it differs, the copy stops without `--force`. Copying it once more under another name (`e2e-staging` and `e2e-prod`) shares the agents. To take in a newer version of a standard workflow after updating the ADK, run `aidev create workflow <name> --from <standard> --update`. The agents and skills become the ADK's current version (review them with `git diff`), and the `workflow.yaml` you changed for this PKG is left alone. When the definition differs from the ADK's, a command to compare them is shown, and you take over the changes you want. `--from … --force` puts the definition back to the ADK's version as well.
* What differs per PKG comes in two kinds. **What differs in the definition** (the directory the tests go in, the command that installs dependencies, how many batches run at once, the cost ceiling) is changed in the copied `workflow.yaml`. **What differs in value** (the target environment's URL, the test user) leaves the definition alone: write it in `workflows.<name>.inputs` of `aidev.yaml`, or pass it with `--input` at run time (xref:workflows-inputs[Taking values that change per run]). **Credentials** (the test user's password) are declared by name in the definition's `env_required:` and handed over by the person running it as an environment variable of their shell. They are never written to a file (xref:workflows-env-required[Taking credentials from environment variables]).

How `playwright-tests` goes, and what it assumes.

. `deps` (command step): `npm ci` installs the dependencies into the run's worktree. For a pnpm / yarn PKG, or one whose tests are in another directory, change this command and `cwd`
. `playwright` (command step): `node node_modules/@playwright/test/cli.js --version`. Without `@playwright/test` among this PKG's dependencies, it stops here (`playwright.config.*` is not what this check looks at)
. `browsers` (command step): `npx playwright install chromium`. Installs the browser on the machine running it when it is missing, and does nothing when it is there
. `plan` (agent step, writes nothing): reads the specification, splits the cases by screen or feature into batches of at most `batch_size`, and puts them in the run's notes
. `scaffold` (agent step): writes the shared helpers (reading the environment variables, logging in) in `tests/e2e/support/` and a smoke test in `tests/e2e/smoke/`, and makes it pass against the target environment. When the URL, the user, the password or the login screen is wrong, this is where it shows
. `generate` (agent step, `for_each`, 4 batches at a time by default): writes `tests/e2e/cases/<batch>/<case id>.spec.ts` for each batch and fixes them until that batch's tests pass (up to 3 times). A batch that does not pass is undone and the next one starts (`on_failure: continue`)
. `review` (agent step): runs the whole suite and fixes what does not pass and the duplicated helpers. The checking agent `playwright-test-reviewer` compares, for each case of the specification, the spec file and what it verifies, and sends the work back with its remarks when something is missing (up to 2 times)
. `pr`: opens the PR. The cases of the batches that failed and were left behind appear under "Targets left out" in the PR body

* It assumes Playwright is in the PKG and that `testDir` of `playwright.config.*` covers `tests/e2e/` (to put the tests elsewhere, change the paths in the copied YAML). In a PKG that does not have it yet, the run stops at the first step (`npm ci` in `deps`, or `playwright`) and shows the command's output and the step's description on screen. The workflow adds no dependency itself: follow "Playwright がまだ無い PKG に入れる" in the copied README (`aidev create workflow --from` prints where it is) to add `@playwright/test` and `playwright.config.*`, commit them, then run (a PKG that is not a Node.js project works too, with a `package.json` at its root that exists only for Playwright). A `webServer` setting that starts a local server is either taken out for this workflow, which runs against the target environment (`base_url`), or `for_each.parallel` is set to 1 (servers started at the same time collide on the port).
* The tests read `E2E_BASE_URL`, `E2E_USER` and `E2E_PASSWORD` from `process.env` (each agent step's `env` passes `base_url` and `test_user` to the agent and to the `until` commands; `E2E_PASSWORD` comes from the shell). The password is written neither in the tests nor in the logs.
* Evidence: the tests leave a screen capture per step (the fixture in `tests/e2e/support/evidence.ts`: `evidence.capture` at the end of each step, `final` at the end of the test). They are at `test-results/evidence/<case id>/<NN>-<label>.png` under the directory Playwright runs in; the final full run of the `review` step completes the set, and it stays in the run's worktree (`never_commit`, so not in the PR; the README of the standard workflow says how to put it there).
* Raise the cost ceiling (`limits.max_usd: 50`) to fit the number of cases. When it is reached, the run stops, and `--resume` continues it.

[source,bash]
----
export E2E_PASSWORD='…'                                                          # only in the shell of the person running it
aidev run workflow e2e-tests --trial --input spec=~/specs/login.csv --max-usd 5     # try it with a few cases first
aidev run workflow e2e-tests --input spec=~/specs/all-cases.csv
----

[[workflows-commands]]
==== Writing commands

`until.command` and `command` do not go through a shell. Quotes, pipes, redirects and variables cannot be written. Use these keys instead.

[source,yaml]
----
  - id: write
    agent: e2e-writer
    writable: [e2e/tests/**]
    prompt: Write the IT tests for the screens the previous step listed.
    until:
      command:                     # a list runs from top to bottom and stops at the first failure
        - npm ci
        - npx playwright test
      cwd: e2e                     # the directory to run in (inside the PKG). Default: the PKG root
      env:                         # environment variables for the commands (fixed values)
        CI: 1
        BASE_URL: http://localhost:3000
      timeout_minutes: 15          # time limit for one command (minutes; at most 240)
----

[%autowidth.stretch,options="header"]
|===
|Key |Meaning

|a list under `command`
|Only in `until`. It replaces `&&`. To run commands in order as command steps, write one command step after another.

|`cwd`
|The directory the command runs in. It cannot be outside the PKG (`..` or an absolute path).

|`env`
|Environment variables for the command. The values are fixed text in the definition and are reviewed in the PR. **Do not write secrets** (a password is declared by name under `env_required` and taken from the shell: xref:workflows-env-required[Taking credentials from environment variables]). A name starting with `AIDEV_` or `GIT_CONFIG` is refused. An agent step may carry `env` too: its values go into both the agent's environment and the `until` commands, so the tests the agent runs itself and the ADK's check run with the same settings (`until.env` is layered on top).

|`timeout_minutes`
|Time limit for one command, in minutes. If omitted, the command may use the time the workflow has left (or, with no workflow time limit, run until it ends).
|===

The whole output of every command is kept under `logs/` in the run record. When an `until` command fails, the agent gets the end of the output and the location of that file.

[[workflows-handoff]]
==== Passing results between steps

Each agent step starts as a new process. The conversation of an earlier step is gone. There are two ways to pass results on.

* **The final report** — the ADK puts the final report of each earlier agent step into the instructions of the later agent steps (the last 6000 characters of a long report). In a survey step, ask in the `prompt` for the results the next step needs to be written in the final report.
* **The notes directory** — have a long or exact result, such as a plan or a list of target files, written to a file. The place is `.aidev/workflows/<name>/runs/<id>/notes/` in the run's worktree, one per run; the ADK puts it into the instructions of every agent step. A step with `writable: []` can write there too. A checking agent only reads it. Nothing in it is committed.

[source,yaml]
----
  - id: plan
    agent: upgrade-planner
    writable: []
    prompt: Find what has to change and write the list of targets to targets.md in the notes directory.
  - id: migrate
    agent: upgrader
    writable: [src/**, package.json, package-lock.json]
    prompt: Read targets.md in the notes directory and migrate the targets from the top.
----

[[workflows-for-each]]
==== Repeating a step per target

Split a job with many targets, such as writing tests screen by screen or migrating module by module, into one target at a time. When one start handles them all, the later targets get worse work, and one failure redoes the whole step.

[source,yaml]
----
  - id: plan
    agent: e2e-planner
    writable: []
    prompt: Find the screens that need IT tests and write them to targets.txt in the notes directory, one per line.
  - id: write
    agent: e2e-writer
    writable: [e2e/tests/**]
    for_each:
      from: targets.txt            # a file in the notes directory; an earlier step writes it
      max_items: 20                # required. How many targets one run may take on (at most 10000)
    prompt: Write the IT test for the screen {item} in e2e/tests/{item}.spec.ts.
    until:
      command: npx playwright test tests/{item}.spec.ts   # checks this target only
      cwd: e2e
      max_retries: 3
----

* The ADK reads the list. One line is one target; blank lines and lines starting with `#` are skipped. A line that appears twice is one target.
* `{item}` can be written in `prompt`, `writable`, `until.command` and `until.prompt`. It is required in `prompt`, and cannot be written in `unchanged`. In `writable`, the target's agent can write only that target's paths (xref:workflows-parallel[Running agents in parallel]).
* The agent is started anew for each target. `until` and its retries apply per target. The time and cost limits count for the whole run.
* When one target fails, the run stops there. The targets that passed stay as they are, and `--resume` continues from the target that stopped (xref:workflows-resume[Continuing a stopped run]).
* With `on_failure: continue` under `for_each`, the changes of a target that fails are undone and the next target starts. What is undone is the files inside the step's `writable` that changed during that target. The failed targets and why are listed in `run.json`, in the report to the later steps and in the PR body. When every target fails, the run stops. Reaching the cost or time limit stops the run even with `continue`.
* The later steps get one report that sums up the result of each target.

A target is one word made of letters, digits and `. _ / @ -` (up to 200 characters). If a line contains a space, starts with `-` or contains `..`, the ADK stops before it starts an agent. A target becomes an argument of a command, so text that could be an option or point somewhere else is refused. Write this format in the `prompt` of the step that writes the list.

[[workflows-parallel]]
==== Running agents in parallel

There are two ways to run agents at the same time. Both run in the same working tree, so the ADK checks, at validation and in the hook, that **agents running at once cannot write the same file**.

**Run the targets of a repeated step in parallel** (`for_each.parallel`). Write every `writable` path with `{item}` in it. Each target's agent can write only its own target's paths, and `on_failure: continue` puts back only that target's paths.

[source,yaml]
----
  - id: write
    agent: e2e-writer
    writable: [e2e/tests/{item}.spec.ts]   # a path per target; required with parallel
    for_each:
      from: targets.txt
      max_items: 200
      parallel: 4                          # up to 4 targets at once (at most 16; default 1)
      on_failure: continue
    prompt: Write the e2e test for screen {item} in e2e/tests/{item}.spec.ts.
    until:
      command: npx playwright test tests/{item}.spec.ts
      cwd: e2e
----

**Run different steps at the same time** (a `parallel:` group). The agent steps listed in the group start together, and the run goes on to the next step when all of them have ended.

[source,yaml]
----
  - id: build
    description: Build the API and the screens at the same time
    parallel:
      - id: api
        agent: api-writer
        writable: [api/**]
        prompt: Implement the API as planned.
      - id: web
        agent: web-writer
        writable: [web/**]
        prompt: Implement the screens as planned.
  - id: integrate
    agent: integrator
    writable: [api/**, web/**]
    prompt: Connect the two.
----

* A group holds agent steps only (2 to 16). Each of them may have `for_each` and `until`.
* Validation refuses a group whose steps' `writable` may overlap, or where one step's `writable` may overlap another's `unchanged`. Overlap is judged from the fixed part (before `*` or `{item}`): `src/**` and `src/a.ts` overlap, `src/a.ts` and `src/b.ts` do not.
* The steps of a group cannot read each other's reports. The steps after the group get all of them.
* When one fails, the others keep running until they end (starting no new target). Then the run stops. `--resume` runs again only the steps that did not finish.
* `until.command` runs at the same time too. Tests that use the same port or files get in each other's way when run at once.
* The cost limit can be passed by as many starts as run at once (the agents already running when the limit is reached are not stopped).

[[workflows-unchanged]]
==== Naming what must not change

`until` only sees whether a command succeeds. An agent can pass `until` by weakening the check instead of fixing the code: deleting a failing test, rewriting an expectation, loosening the test runner's configuration. List the paths that must not be weakened in `unchanged`.

[source,yaml]
----
  - id: migrate
    agent: upgrader
    writable: [src/**, tests/**, package.json, package-lock.json]
    unchanged: [tests/**]          # the existing tests must stay as they are
    prompt: Read targets.md in the notes directory and migrate the targets from the top.
    until:
      command: npx vitest run      # call the test runner itself, not a script in package.json
----

* The agent cannot write a path in `unchanged`, even inside `writable` (the hook refuses it).
* The ADK remembers the state when the step started and compares after every attempt. If something changed, the attempt fails; with `until`, the agent is started again with the changed paths (at most `until.max_retries` times). A step without `until` fails there (with `for_each`, that target fails). Changes made by a command or through `Bash` are detected too.
* If the same paths are changed twice in a row, the run stops. Put them back, then `--resume`.
* What an earlier step changed is part of the state "when the step started". An implementation step with `unchanged: [tests/**]` can follow a step that writes the tests.
* Gitignored files are not compared.

Detection is per file. A change inside a file that stays in `writable` (a `test.skip` in a newly written test, a rewritten `scripts` entry in `package.json`) is not detected. Two things cover that.

* Have `until.command` call the test runner itself, not `npm test` (when `package.json` is in `writable`, `scripts.test` can be rewritten).
* Add a checking agent to `until` and write "no skipped or empty tests" in `until.prompt` (xref:workflows-until-agent[Letting an agent's review decide when a step is done]).

[[workflows-inputs]]
==== Taking values that change per run (`inputs` and `--input`)

When a value that changes from run to run — the path of a test specification, the screen to cover, the browser to use — is rewritten in a `prompt`, the definition changes with every run and has to be approved again. `--task` is free text handed to the agents as data; it never reaches a command. A value that goes into a fixed place in the definition is declared under `inputs:`, and the person running the workflow passes it with `--input <name>=<value>`.

[source,yaml]
----
inputs:
  spec:
    description: the test specification to work from   # shown to the person running it, by --dry-run and in the PR body
    file: true          # a file anywhere on this machine; the run gets a copy
  screen:
    description: the screen to cover
    pattern: '[a-z0-9-]+'   # quote it (a bare [ starts a YAML list)
  browser:
    default: chromium
    pattern: '[a-z]+'

objective: |
  Write the IT tests the specification {inputs.spec} describes for the screen {inputs.screen}.

steps:
  - id: write
    agent: e2e-writer
    writable: [e2e/tests/**]
    prompt: Read {inputs.spec} and write the tests for {inputs.screen}.
    until:
      command: npx playwright test tests/{inputs.screen}.spec.ts --project {inputs.browser}
      cwd: e2e
----

* A declaration can hold `description`, `default`, `pattern`, `path` and `file`. An input without `default` is required (there is no `required` key). `path` and `file` cannot be written together, and a `file` input cannot have a `default`. A name starts with a lowercase letter and is made of lowercase letters, digits, `_` and `-`, up to 32 characters.
* `{inputs.<name>}` can be written in `objective`, an agent step's `prompt`, `until.prompt`, `until.command`, a command step's `command` and the values of `env` (of a step and of `until`). Anywhere else (`description`, a step's `description`, `pull_request.title`, `writable`, `unchanged`, `cwd`, `for_each.from`) validation refuses it. It cannot be the executable of a command (the first word). A name that is not declared is refused by validation.
* The values are written into the definition before the run; `{item}` is replaced per target afterwards. A value is not a template, so it cannot contain `{` or `}`.
* A value is one line, up to 1000 characters, with no control characters, and with `pattern` the whole value must match it (the ADK wraps it as `^(?:…)$`). A `default` is checked by the same rules at validation.
* **An input that reaches a command** (one written in `until.command`, a command step's `command` or an `env` value) must have `pattern`, `path: true` or `file: true`. Its value must also be one word within the fixed rule `^[A-Za-z0-9._@][A-Za-z0-9._/@:=+-]{0,999}$` (with no `..` segment). A value with whitespace or a leading `-` could be an option or point somewhere else — the same idea as a `for_each` target. A `pattern` can narrow this, never widen it.
* `path: true` is a path relative to the PKG (not starting with `/` or a drive letter, no `..`). It must be text (`.xlsx`, `.docx`, `.pdf`, images and so on are refused with `the AI tools read text; export … to Markdown, CSV or text first and pass that file`). The path must reach the run's worktree: either it is committed at HEAD, or git ignores it and a `provide` glob matches it. `--dry-run` and the run decide this before anything starts and stop with `is not committed; a run starts from HEAD (commit it, or declare the input with file: true and pass the file)` or `is ignored by git and no provide: entry copies it into the run (add one, or pass it as a file input)`. After `provide` has copied, the run also checks that the path exists in the worktree.
* `file: true` is the path of a file anywhere on this machine (absolute, or relative to the shell's current directory). It must exist and be text (the same extension rule as `path`). The ADK copies it to `.aidev/workflows/<name>/runs/<id>/inputs/<name><extension>` in the run's worktree, and `{inputs.<name>}` becomes that path relative to the PKG (it is under `runs/`, so it is gitignored: the agents can read it, and it is never committed). `run.json` keeps that path, and the log says `input <name>: copied <from> to <to>`. `--resume` uses that copy as it is. Use `file` for a file one person has (a specification exported from Excel, say) and `provide` for data the whole team keeps at a fixed gitignored path (xref:workflows-provide[Providing files the worktree lacks]).

A value that differs per PKG but not per run (the target environment's URL, the test user name) can be written in `workflows.<name>.inputs` of `aidev.yaml`. The definition (`workflow.yaml`) then stays the same from one PKG to another; only `aidev.yaml` differs.

[source,yaml]
----
workflows:
  e2e-tests:
    inputs:
      base_url: https://staging.example.com
      test_user: qa-user@example.com
----

* The precedence is `--input` > `aidev.yaml` > the declaration's `default`. A value from `aidev.yaml` is checked by the same rules as `--input`, and the `inputs` row of `--dry-run` shows `(from aidev.yaml)`. A name the workflow does not declare stops with `aidev.yaml: workflows.<name>.inputs: the workflow declares no input "<name>"`.
* A `file: true` input cannot be written there (the file is on the machine of the person running it, so it is passed with `--input`).
* `aidev.yaml` is committed, so credentials cannot be written there. An input whose name looks like `password`, `secret`, `token`, `pat` or `api_key` is a configuration error. A password is taken through `env_required` (xref:workflows-env-required[Taking credentials from environment variables]).

When you run it, pass `--input` once per input (`--input=<name>=<value>` works too).

[source,bash]
----
aidev run workflow e2e-tests --input spec=../specs/login.txt --input screen=login --input browser=firefox
aidev estimate workflow e2e-tests --input screen=login     # an estimate does not need the required inputs
----

* Without a required input, nothing starts: it stops with `the workflow needs --input for: spec (the test specification to work from)` and exit code 1 (`--dry-run` too). A name that is not declared gives `the workflow declares no input "nope" (its inputs: spec, screen, browser)`; the same name twice gives `input <name> is given twice`.
* `--input` cannot be passed with `--resume` (`--resume continues the run with the inputs it was started with; do not pass --input`). A continued run uses the recorded values and checks them again by the same rules as when they were passed (the record is a file an agent could rewrite).
* The values go where `{inputs.<name>}` is written and, as data, into the instructions of every agent (the checking agents included) under a `## Inputs for this run` section. They also appear on the `inputs` row of `--dry-run` (a `file` input with `(copied from <path>)`), in the `## Inputs (--input name=value)` section of `--dry-run` and of the submit PR body (name, description, required or default, `pattern`, `a path in the repository`, `reaches a command`), in the `## Inputs` section of the run's PR body, on the `inputs:` lines of the last commit's message, in `inputs` in `run.json`, in the head and the summary of `--log`, and in the record `aidev modify --from-run` hands to the agent.

[[workflows-env-required]]
==== Taking credentials from environment variables (`env_required`)

A test user's password or an API token is written neither in the definition, nor in `aidev.yaml`, nor in a prompt. Declare the names of the environment variables (with a description for the person running it) under `env_required:`, and the person running it sets them in their shell.

[source,yaml]
----
env_required:
  E2E_PASSWORD: the test user's password
  E2E_API_TOKEN:                 # a description is optional; a list of names works too: env_required: [E2E_PASSWORD]
----

* `aidev run workflow` (`--dry-run` too) checks **by name only** that the declared variables are set, and when one is not, nothing starts: it stops with `the environment variable E2E_PASSWORD (…) is not set; the workflow needs it (env_required)`. The `env` row of `--dry-run` shows `set` / `NOT SET`. The values are not shown.
* The values reach the environment of the agents and commands (the child processes inherit the shell environment of the person running it, the same way as before). The instructions get **the names and descriptions only**, under `## Environment variables of this run`, and the agents are told to write the values nowhere. `run.json`, the logs, the PR body and the commits do not carry the values either.
* The tests and commands read them at run time, as in `process.env.E2E_PASSWORD`. The same name cannot be written in the `env` of a command step, of an agent step or of `until` (validation refuses it).
* A name follows the rules of environment variables (a letter or `_` first, then letters, digits and `_`); `AIDEV_*` and `GIT_CONFIG*` cannot be written.
* The declaration appears under `## Environment variables the run needs` in the submit PR body. The reviewer checks that the variables listed there really are credentials (a setting goes in `inputs` or `env`).

[[workflows-provide]]
==== Providing files the worktree lacks (`provide` and `file` inputs)

A run works in a worktree of its own made from HEAD, so files git ignores are not there: a specification brought from another repository and put in `.gitignore`, test fixtures, and the like. There are two ways to provide them. Data the whole team keeps at a fixed gitignored path is copied from your checkout with `provide:`; a file one person has is passed as a `file: true` input (xref:workflows-inputs[Taking values that change per run]). Dependencies (`node_modules`) are not for `provide`: a command step such as `command: npm ci` installs them. `provide` is for data a command cannot make.

[source,yaml]
----
provide: [docs/spec/**, e2e/fixtures/**]
----

* Before the first step (every time it starts, `--resume` included), the files git ignores in your checkout that match a glob are copied, file by file, to the same path in the worktree (overwriting). Only ignored files are copied: a tracked file is already in the worktree as it is at HEAD, and a file that is neither tracked nor ignored is the state of your work in progress, which never reaches a run. A glob names files, not directories (`docs/spec/**` is every ignored file under docs/spec).
* Never copied: anything matching `secrets_paths` (the log says `not copied (a secret path …)`), anything under `.aidev/` or `.git/`, and symbolic links. Validation refuses a glob that does not start with a fixed directory (`**/*.txt`), one that names `.aidev`, `.git` or a protected path, and one whose last name looks like a credential file (`.env`, `.env.*`, `.npmrc`, `.netrc`, `.pypirc`, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `*.jks`, `*.keystore`).
* A glob that matches no ignored file in your checkout stops `--dry-run` and the run before anything starts: `provide: <glob> matches no file that git ignores in <checkout> (a run copies only ignored files from the checkout; put the file there, or take the entry out)`.
* A copied file must be ignored in the worktree too (the rule that ignores it must be in a committed `.gitignore`). Otherwise it stops with `provide: <file> is ignored in <checkout> by a rule the repository does not carry; commit the .gitignore that ignores it, so every run (and every teammate's) treats it alike`.
* The log says `provide: N path(s) copied from the checkout: …` and one line per path not copied. `--dry-run` has a `provide` row. The submit PR body has a `## Provided from the checkout` section.

[[workflows-never-commit]]
==== What is never committed (`never_commit` and the ADK's own list)

A command step that runs `npm ci` leaves `node_modules` in the worktree. Unless the PKG's `.gitignore` ignores it, a checkpoint or the pull-request step would commit it as long as it is inside `writable`. The ADK never commits what a toolchain leaves behind: the untracked files matching the following globs.

[source,text]
----
**/node_modules/**  **/bower_components/**  **/.pnpm-store/**  **/.yarn/cache/**
**/.venv/**  **/venv/**  **/__pycache__/**  **/*.pyc  **/.pytest_cache/**  **/.mypy_cache/**  **/.ruff_cache/**
**/.tox/**  **/.nox/**  **/.gradle/**  **/.DS_Store  **/Thumbs.db  **/*.orig  **/*.rej
----

A workflow adds its own with `never_commit:`. Nothing can be taken off the ADK's list. Build output (`dist/`, `build/`, `target/`) is not on it, because it can be a deliverable; a workflow that does not want it adds it.

[source,yaml]
----
never_commit: [e2e/test-results/**, e2e/playwright-report/**]
----

* Only untracked files are concerned. A change to a file git tracks is the run's work wherever it is (when a step changes a file inside a committed, vendored `node_modules`, it is committed like any other).
* Where it applies: the checkpoints of steps and targets, the last commit of the pull-request step, the `unchanged` comparison, the undoing of a failed target (`on_failure: continue`), the diff shown to the checking agent, and the check for "uncommitted changes" before a new run (residue left in the worktree does not stop the next run).
* Validation refuses a `never_commit` of the form `<dir>/**` that covers an entry of a step's `writable` or of `provide` (nothing that step did would ever be committed).
* What is left out is said. The pull-request step's log has one line per glob, `N file(s) left out as never committed (<glob>; e.g. <path>)`; that step in `run.json` has `leftOut: { "<glob>": count }`; the `--json` output has `leftOut`; the end of the run shows `left out, never committed: N file(s) matching <glob> (e.g. <path>)`; the PR body has a `## Left out` section. `--dry-run` has a `never commit` row, and the submit PR body a `## Never committed` section.

[[workflows-unattended]]
==== Running a large job without anyone stepping in

How to write a large job — writing hundreds or thousands of e2e tests, upgrading a framework — so that once it starts you only wait for it to finish.

[source,yaml]
----
steps:
  - id: plan
    agent: e2e-planner
    writable: []
    prompt: Survey the screens that need tests and write them to targets.txt in the notes directory, one per line.
  - id: write
    agent: e2e-writer
    writable: [e2e/tests/**]
    unchanged: [e2e/playwright.config.ts]
    for_each:
      from: targets.txt
      max_items: 1500              # more than there are targets
      on_failure: continue         # undo a target that does not pass and go on
    prompt: Write the IT test for the screen {item} in e2e/tests/{item}.spec.ts.
    until:
      command: npx playwright test tests/{item}.spec.ts
      cwd: e2e
      timeout_minutes: 15
      max_retries: 3
  - id: pr
    pull_request: {}

limits:
  max_usd: 400                     # the only stop; no max_minutes
----

* **Leave out the time limit.** Without `limits.max_minutes`, the run stops only on the cost limit, the retries and the target ceiling. `timeout_minutes` ends an agent or a command that hangs.
* **Split the work per target.** Do not give one agent start the whole job: use `for_each` for one target at a time. A failure stays with its target, and `--resume` continues per target.
* **Do not stop on a failed target.** With `on_failure: continue`, a target that does not pass is undone and the run goes on. The ones left are listed under "Targets left out" in the PR body, for another run (with a list of just those) or for a person.
* **Look at the cost first.** Decide `limits.max_usd` from the optimistic and pessimistic figures of `aidev estimate workflow <name> --ai --task "…"` (xref:cli-estimate[aidev estimate]).
* **Keep the record in one file.** `aidev run workflow <name> --log <file>` writes the whole run (each agent's tool calls, final reports, command output) and a summary to one file.

These still need a person:

* When the machine running it stops (sleep, restart, network loss), the run stops. `aidev run workflow <name> --resume last` continues and skips the targets already handled.
* A passing failure of the AI tool (overload, rate limit) counts as that target failing (with `on_failure: continue`, it is undone and the run goes on).
* By default, targets are handled one at a time. `for_each.parallel` runs several at once (xref:workflows-parallel[Running agents in parallel]).
* The changes become one PR. When thousands of changes are too many to review in one PR, split the list and run it several times.

[[workflows-until-agent]]
==== Letting an agent's review decide when a step is done

"All tests pass" can be judged by a command; "the tests are sound" cannot. For a condition like that, name a checking agent in `until`.

[source,yaml]
----
  - id: write
    description: Write the tests, make them pass, then get them passed by review
    agent: test-writer
    writable: [tests/**]
    prompt: Write the tests the previous step listed, in the existing style, and run them.
    until:
      command: npm test            # first, this exits 0
      agent: test-reviewer         # then this agent passes the work
      prompt: |                    # what test-reviewer checks
        Every behaviour the previous step listed is tested.
        The tests check behaviour seen from outside, not the implementation's internals.
      max_retries: 4
----

One attempt goes in this order:

. `test-writer` writes the tests
. `npm test` runs. If it fails, `test-writer` is started again with its output (`test-reviewer` is not started)
. `test-reviewer` starts, with `test-writer`'s report, the list of files changed inside `writable`, the location of a file with the diff, and `until.prompt`
. If `test-reviewer` ends its final message with the line `VERDICT: PASS`, the step is done. `VERDICT: FAIL`, or no such line, fails the check, and `test-writer` is started again with `test-reviewer`'s report

About the checking agent:

* **It writes nothing.** The step's `writable` does not apply to it. What it can use (skills, tools, MCP servers) is its own frontmatter plus what the workflow's `agents:` gives it; give it read-only tools such as `tools: Read, Grep, Glob`.
* The ADK puts the pass/fail format (the `VERDICT:` line) into its instructions. You do not need to write it in the agent's body or in `until.prompt`.
* Write in `until.prompt` exactly what to check. A vague check makes the same remark repeat and stop the run, or uses up `until.max_retries`.
* Its starts count toward the retries (`until.max_retries`), the cost limit and the time limit. An attempt starts two agents, so allow for that in `limits.max_usd`.
* When it passes the work, its report also goes into the instructions of the later agent steps.
* The checking agent is reviewed in the pull request together with the workflow, and the workflow runs only while it matches `origin/main`.

[[workflows-trial]]
=== Trying it before approval (`--trial`)

A workflow rarely works the first time it is written. That the `until` command does not pass in this PKG, that `writable` is too narrow, what a command step leaves behind, a file the worktree lacks: you find these out by running it. Going through submit → approve → run → fail → fix again and again piles trial-and-error commits on `main`. `--trial` runs the definition as it is in your checkout, before approval, so you can check it.

[source,bash]
----
aidev run workflow write-tests --trial --task "src/services/order.ts"      # fix → try → fix → try
aidev run workflow write-tests --trial --dry-run                           # only see what would be tried
aidev submit workflow write-tests                                          # submit once the result is right
----

The next steps shown after `aidev create workflow` follow the same order: 1. review, 2. try (`--trial`), 3. submit, 4. run (after `aidev modify workflow`: 1. review, 2. try, 3. estimate, 4. submit).

A trial run works like this.

* **It runs the definition as it is in your checkout.** Whether it is approved does not matter, and uncommitted edits are included. The definition must validate and pass the pre-launch checks (xref:workflows-run[Running a workflow]). `--dry-run --trial` shows `not required: --trial runs the definition as it is in this checkout (…)` on the `approved` row, a `trial` row and the branch `aidev/<name>.trial`, and when nothing is wrong ends with `dry run: the definition validates and would run as a trial (nothing pushed).` and exit code 0. The message of an unapproved workflow run without `--trial` now adds `To try it as it is first: aidev run workflow <name> --trial` (`(try it as it is with --trial)` in `--dry-run`).
* **It works on a branch and worktree of its own.** The branch is `aidev/<name>.trial` (`aidev/<name>.trial-<yyyymmddHHMM>` with `--dated`); the worktree is `aidev-<name>.trial` in the same place as an ordinary run's. A workflow name cannot contain `.`, so it never collides with another workflow's branch.
* **Every trial starts clean.** Each new trial (one that is not a `--resume`) does `reset --hard` of the trial branch to the commit checked out now and removes what the last trial left uncommitted. What git ignores and the never-committed residue stay, so the `node_modules` a command step installed is there for the next trial. The `runs/` records of earlier trials stay too (`--from-run` reads them).
* **Only the definition's files are brought in.** The reviewed files (`workflow.yaml` and the PKG agents and skills it references) are copied from your checkout into the worktree and committed on the trial branch as `aidev(<name>): trial definition`. No other uncommitted change reaches the worktree (the run starts from HEAD). When the checkout has uncommitted changes, the trial and its `--dry-run` warn: `the checkout has N uncommitted change(s) a run does not see (it starts from HEAD): …; commit them first if the steps need them`.
* **The write guard holds the agents to the trial's definition.** Instead of an approval, the ADK keeps a trial record in the worktree's git directory (outside the working tree) and hands `AIDEV_WORKFLOW_TRIAL` to the agents only. On every write and tool call, the hook checks that the hash of the definition files in the worktree is the one the trial started with, and allows the step's `writable` only while it is (the reason given is `a trial run of the definition sha256:…`; it never calls this approval). Rewriting the definition, an agent or a skill during the run is refused from then on, exactly as editing an approved workflow is. The record is removed when the run ends (on Ctrl-C too).
* **Nothing is pushed, and no PR is opened.** The pull-request step goes as far as the commit (the last commit's message carries `approved: none (a trial run of the definition sha256:…)` and `trial run: not pushed`) and skips the push and the PR. The agents and command steps are given, through environment variables, a git configuration that refuses to push (an ADK `pre-push` hook, and push URLs pointed at an invalid scheme). A step's `env` cannot override it (names starting with `GIT_CONFIG` cannot be written there). A command step or `until.command` of the form `git … push` is refused before the run starts with `pushes; a trial run pushes nothing`. `git push`, `gh pr create`, `az repos pr create` and `glab mr create` from an agent's `Bash` are denied by the hook.
* **Records and the estimate.** `run.json` has `trial: true`, `trialHash` and `approvedRef: null`. The estimate record has `trial: true` too, and `aidev estimate` learns nothing from trial runs. The estimate-reviewer does not start by itself after a trial either. The `--log` summary says `(a trial run: nothing pushed)`.
* **Continuing and fixing.** `--resume last` picks the last run of the same kind (with `--trial`, the last trial; without it, the last run that was not a trial). Continuing a trial needs `--trial`, and a run that was not a trial cannot take it. A continued trial must still have the definition it started with; when it changed, the message says `start a new trial`. A continued run (trial or not) is refused when the checkpoints of its finished steps are no longer on the branch (a later trial reset it, or the branch was moved after a merge). `aidev modify workflow <name> --from-run last` accepts a trial's record too (its head says `(a trial run)`, and it hands over the inputs and the tool calls the agent was refused).
* **Keeping the cost down.** `--max-usd <n>` lowers the cost ceiling below `limits.max_usd` for this run only (it only lowers it; the `limits` row reads like `$0.5 (limits.max_usd is $1)`). It works for any run, not just trials.

When a trial ends, it shows this.

[source,text]
----
✓ workflow finished: 3 step(s)
    agent runs: 3, reported cost $2.0333
ℹ trial run: nothing pushed; the result is on aidev/write-tests.trial in ~/.local/share/ai-dev-kit/worktrees/my-pkg-1a2b3c4d/aidev-write-tests.trial (the pull request text it would carry: .aidev/workflows/write-tests/runs/2026-10-14T01-12-03-114Z/pull-request.md)
    branch aidev/write-tests.trial (1 checkpoint commit(s) in this start); worktree ~/.local/share/ai-dev-kit/worktrees/my-pkg-1a2b3c4d/aidev-write-tests.trial
    left out, never committed: 312 file(s) matching **/node_modules/** (e.g. node_modules/.package-lock.json)
⚠ 1 file(s) changed outside what the steps may write, by a command step or past the guard; not committed: coverage/lcov.info
⚠ step write: the tool was refused 2 call(s): Write src/services/order.ts; Edit package.json (a path outside writable? see run.json "denied")
ℹ trial run: nothing was pushed. aidev/write-tests.trial holds 3 commit(s) since 9f8e7d6a1b2c
    inspect: git -C "<worktree>" log --oneline 9f8e7d6a1b2c..HEAD   /   git -C "<worktree>" diff --stat 9f8e7d6a1b2c
    when the result is right: aidev submit workflow write-tests   (the reviewed definition then runs with "aidev run workflow write-tests")
    record: <worktree>/.aidev/workflows/write-tests/runs/2026-10-14T01-12-03-114Z
----

* `left out, never committed: …` counts what was kept out of the commits: a toolchain's residue and the `never_commit` paths (xref:workflows-never-commit[What is never committed]).
* `… changed outside what the steps may write …` are files a command step wrote outside `writable`, or an agent wrote past the guard. They are not committed. If they are needed, widen that step's `writable`.
* `the tool was refused N call(s): …` is how often the agent was refused for calling outside `writable` or for a tool it was not given (the list is in `denied` of that step in `run.json`). It is a clue whether `writable` is too narrow or the `prompt` needs fixing.
* The two git commands after `inspect:` show the trial branch's commits and diff. The text that would have become the PR body is in `pull-request.md` in the run record.
* When the result is right, submit with `aidev submit workflow <name>`. When it stopped, continue with `--resume <run id> --trial`, or have it fixed with `aidev modify workflow <name> --from-run <run id>`.

There are things a trial does not guarantee.

* A trial bounds the ADK's runner and git. What an agent can do through other tools or MCP servers is decided by the PKG's policy allow rules, as in an approved run. It does not stop every side effect of an unreviewed definition, and it does not strip the hosting PAT (an MCP server may need it). A workflow with an agent that updates an external system updates it in a trial too.
* A trial that passes is not an approval. Only a definition that was submitted, reviewed and merged to `main` runs (with a push and a PR) with `aidev run workflow <name>`.

=== Submitting a workflow (Engineering Manager)

Once you have reviewed the definition with `git diff`, submit it.

[source,bash]
----
git diff -- .aidev/workflows/write-tests/ .aidev/agents/ .aidev/skills/
aidev submit workflow write-tests
----

[source,text]
----
aidev submit workflow write-tests

✓ committed 3f2a9c1b7d0e (1 file(s))

* It validates the definition, commits `workflow.yaml` and the agents and skills in the PKG it references on the branch `aidev/workflow-<name>` as `aidev: workflow <name>`, pushes and opens a PR (Azure DevOps). With `generic` hosting it pushes, and you open the PR by hand. With `--no-push` it does not push either.
* The PR body gives the objective, what each step does (order, agent, where it may write, that agent's skills, tools and MCP servers, the subagents it may start, `until`, parallel groups), the files involved (new or changed) and the limits, and says that merging approves this workflow. [[workflows-approval]]
=== Definition of approval

"Approved" means that the contents of `workflow.yaml`, and of the agents and skills in the PKG it references, are **byte for byte identical to what is on `origin/<tracking branch>`** (usually `origin/main`). There is no command or file that records approval.

* The check uses the last fetched `origin/main`. After a merge, run `git fetch origin` before running the workflow. The check also works offline.
* Editing locally after approval makes the workflow unapproved at once. If a running agent rewrites `workflow.yaml` or its own definition to widen the range, it is refused, because the check runs on every write.
* See the state with `aidev list workflows`.

[source,text]
----
aidev list workflows
  write-tests           approved                          指定した対象のテストを既存の書き方で書き、通してから PR を作る
  e2e-tests             not on origin/main                主要画面の IT テストを Playwright で書く
  write-conventions     changed since origin/main         Wiki と根拠ソースから開発規約を書き、PR を作る

----

[cols="1,2,4",options="header"]
|===
|State |Meaning |Action

|`approved`
|Same as `origin/main`
|You can run it.

|`not on origin/main`
|Not on `main` yet (not submitted, or the PR is not merged)
|Submit it. If it is merged, `git fetch origin`.

|`changed since origin/main`
|Differs from what is on `main`
|Review the diff and submit again, or revert with `git checkout origin/main -- .aidev/workflows/<name>/`.

|`invalid: …`
|The YAML fails validation
|Fix the key that is shown.
|===

[[workflows-run]]
=== Running a workflow (Developer)

[source,bash]
----
git fetch origin
aidev run workflow write-tests --dry-run --task "src/services/order.ts"
aidev run workflow write-tests --task "src/services/order.ts"
aidev run workflow e2e-tests --input spec=../specs/login.txt --input screen=login   # a workflow that declares inputs:
----

`--dry-run` shows the approval state, the agents and AI tools used, the limits, a cost estimate (optimistic to pessimistic), this run's task and inputs, and what each step does (where it may write; skills, tools and MCP servers), and starts nothing. Problems that stop a run before it starts (a command's executable not on PATH, no file matching a `provide` glob, a `path: true` input that does not reach the worktree) show up here too. Check with this first.

For the cost breakdown, use `aidev estimate workflow <name>`. With `--ai`, an agent reads this run's `--task` and the code, estimates the retries and the `for_each` targets, and narrows the range (xref:cli-estimate[aidev estimate]).

[source,bash]
----
aidev estimate workflow write-tests --ai --task "src/services/order.ts"
----

`--task` is the instruction for this run (a Work Item number, a target path, and so on). It is handed to every agent step as data and cannot change the `objective` or any step's `writable`. Pass a long instruction with `--task-file <path>`.

When the workflow declares `inputs:`, pass `--input <name>=<value>` once per input. Without a required input, nothing starts: it stops with `the workflow needs --input for: …` (xref:workflows-inputs[Taking values that change per run]). A value written in `workflows.<name>.inputs` of `aidev.yaml` is used when `--input` is left out. When the workflow declares `env_required:`, set those environment variables (a password and the like) in your shell before running it; without them, nothing starts (xref:workflows-env-required[Taking credentials from environment variables]). `--max-usd <n>` lowers the cost ceiling below `limits.max_usd` for this run only (like `--max-minutes`, it only lowers it).

This is what happens during a run.

* A run works in **a git worktree of its own**. It never touches your working tree, so it runs even with uncommitted changes there, and you can keep working while it runs (xref:workflows-worktree[The run's worktree and branch]).
* There is one branch per workflow (`aidev/<name>`); every run uses the same branch and worktree. Only when you want a dated branch of its own (`aidev/<name>-<yyyymmddHHMM>`), pass `--dated`.
* The agents run under the same configuration files, hooks and policy as an interactive session. They can write only inside the `writable` of the step now running; the hook refuses writes anywhere else. The agents themselves never commit or push.
* Before the first step, the gitignored files matching the globs of `provide:` are copied from your checkout into the worktree, and a copy of each `file: true` input is put under `inputs/` in the run record (xref:workflows-provide[Providing files the worktree lacks]).
* Each time a step (one target, for `for_each`) passes, the changes inside its `writable` are **committed as a checkpoint** (`aidev(<name>): <step>`). A stopped run continues from the last checkpoint. Untracked files matching the ADK's own list (`node_modules`, `__pycache__` and so on) or `never_commit:` are not committed (xref:workflows-never-commit[What is never committed]).
* Claude Code is started with only the `tools` and `mcp` given by the agent's frontmatter and the workflow's `agents:` (named `subagents` are handed over with `--agents`). Other tools do not exist for it, and the hook refuses them if called. An agent without `mcp` gets no MCP servers. `Bash`, `WebFetch` and `WebSearch`, when given, count as approved for the run (nobody is there to approve a call, and an agent has to be able to run the tests itself). The `deny` / `ask` rules of the PKG's `.claude/settings.json` (`git push`, for instance) and the hook (writing outside `writable`, pushing from a trial) still apply.
* The final report of each earlier agent step goes into the instructions of the later agent steps. The files in the notes directory can be read too (xref:workflows-handoff[Passing results between steps]).
* If `until` is not met, the same agent is started again with the result attached (the command's output, or the checking agent's report). If the same result appears twice in a row, the run stops.
* When a command takes longer than 15 seconds, one line with the elapsed time is shown every 15 seconds.
* The `pull_request` step makes a last commit of what is left inside the steps' `writable` and the run record, pushes the branch and opens a PR. A PR already open for the branch has its description updated instead. The PR body gives the workflow name, the run id, the starting commit, the approval reference, the number of agent starts, the cost, and the final report of each agent step (shortened to fit the 4000 characters Azure DevOps accepts; if it still does not fit, it is cut at a line break with a note pointing to `pull-request.md`, keeping the last line, and the run log says it was shortened). The full text is in `pull-request.md` in the run record. If the branch has no change since the base, neither a commit nor a PR is created.
* The record is written to `.aidev/workflows/<name>/runs/<id>/` in the worktree as the run goes. It is gitignored and never committed. `--resume`, `aidev estimate` and `aidev modify --from-run` look for records in the checkout and the worktrees together.
* At the end of the run, it shows the files that changed outside the steps' `writable` (`N file(s) changed outside what the steps may write, by a command step or past the guard; not committed: …`) and the tool calls the agents were refused (`step <id>: the tool was refused N call(s): Write src/x.ts …`; they are also in `denied` of that step in `run.json`). Neither is committed. They are a clue whether `writable` is too narrow or the step needs fixing.

[[workflows-worktree]]
==== The run's worktree and branch

[%autowidth.stretch,options="header"]
|===
|Item |What it is

|Where the worktree is
|`<AIDEV_HOME>/worktrees/<PKG name>-<hash>/<branch name with / as ->` (`~/.local/share/ai-dev-kit/…` on Linux, `%LOCALAPPDATA%\ai-dev-kit\…` on Windows). The hash is made from **where the PKG clone is (its absolute path)**, only so that two clones of one PKG on a machine do not share a directory. It has nothing to do with the workflow's content and does not change when the workflow is fixed. Later runs find the worktree by its branch name (`git worktree list`), not by the path. It is outside the PKG, so tests and linters run in the PKG do not pick up a second copy of the sources.

|Branch
|`aidev/<name>`. The first time, it starts at the commit checked out now. With `--dated`, each run gets a new `aidev/<name>-<yyyymmddHHMM>` and a worktree of its own. With `--trial`, it works on `aidev/<name>.trial` and its worktree (`aidev-<name>.trial`), which is reset to the commit checked out now at every trial (xref:workflows-trial[Trying it before approval]).

|Later runs
|Use the same branch and worktree. When the branch's changes are already in the base (the commit checked out now), the branch is moved to the base first. When it has changes the base does not, the base is merged into it, and the run builds on the earlier runs' work. A merge conflict stops the run (resolve it in the worktree, or use `--dated`).

|Uncommitted changes
|A new run does not start while the worktree has uncommitted changes inside the workflow's `writable` (a stopped run's partial work). Continue with `--resume last`, or throw them away with the commands shown.

|One at a time
|Only one run works in a worktree at a time; the next one stops while another is going.

|What is not in it
|What git ignores (`node_modules`, `.env`, build output) is not in a new worktree. A workflow that needs dependencies starts with a step such as `command: npm ci` (what it installs is never committed; xref:workflows-never-commit[What is never committed]). Gitignored data (specifications, fixtures) is copied from your checkout with `provide:` or passed as a `file: true` input (xref:workflows-provide[Providing files the worktree lacks]).

|Cleaning up
|The worktree stays after the run (for `--resume` and the records). Remove it with `git worktree remove <path>` and the branch with `git branch -D aidev/<name>` when no longer needed; the next run makes them again.
|===

[%autowidth.stretch,options="header"]
|===
|File |Contents

|`run.json`
|The result of each step, why the run stopped, the cost, and the cost of each agent start (`calls`, which xref:cli-estimate[the estimate] reads). Updated each time a step ends.

|`log.txt`
|The progress lines shown on screen

|`reports/<step>.md`
|The whole final report of each finished agent step (the checking agent's is `<step>.until.md`). For a `for_each` step it is the summary per target; each target's whole report is `<step>.t<target number>.md`

|`logs/<step>.<attempt>.<number>.log`
|The whole output of a command (for a `for_each` target, `<step>.t<target number>.<attempt>.<number>.log`)

|`diffs/<step>.<attempt>.diff`
|The diff shown to the checking agent

|`unchanged/<step>.json`
|The state of the `unchanged` paths when the step started

|`notes/`
|Files the steps wrote for the steps after them

|`inputs/<name><extension>`
|The copy of a `file: true` input. `{inputs.<name>}` is this path (xref:workflows-inputs[Taking values that change per run])

|`pull-request.md`
|The full PR text. Use it when you open the PR by hand with `generic` hosting. In a `--trial` run, it is the text that would have become the PR.
|===

[[workflows-resume]]
==== Continuing a stopped run

A stopped run can continue from the step it stopped at. Finished steps are not run again.

[source,bash]
----
aidev run workflow write-tests --resume last          # continue the last run
aidev run workflow write-tests --resume 2026-09-23T01-12-03-114Z
----

* It continues in the run's worktree and branch, with the same `--task` and notes, whatever branch you are on. `--task` and `--dated` cannot be passed.
* The step that stopped starts over **from the last checkpoint**: what it left uncommitted inside `writable` is put back. The finished steps and targets are in the checkpoints, so their work stays.
* The final reports of the finished steps are read from the record and put into the instructions of the later steps.
* A `for_each` step skips the targets that finished and continues from the one that stopped. The list is read again, so when a target cannot be made to pass, you can delete its line from the list file (in the worktree's notes directory) and continue.
* The agent is told why the run stopped.
* The time and cost limits are counted anew for the continued run. The cost and the agent starts in `run.json` are totals.
* If the definition (`workflow.yaml`) changed after the run started, the run cannot continue. Start a new run.
* When the worktree was removed but the branch is still there, the worktree is made again (the records were in the worktree, so after removing it, start a new run).

When the cause is in the definition (the `until` command does not pass in this PKG, `writable` is too narrow, and so on), the run stops at the same place again. A workflow mostly fails because an agent meets the same error again and again; have the definition fixed from the run's record (xref:workflows-fix-from-run[Fixing a workflow from a stopped run]).

Messages when it stops, and what to do. The exit code is 1.

[%autowidth.stretch,options="header"]
|===
|Message |Action

|`workflow <name> is not approved: … is not on origin/main yet`
|The PR is not merged. If it is, `git fetch origin`. To try the definition as it is, use the `aidev run workflow <name> --trial` shown (xref:workflows-trial[Trying it before approval]).

|`workflow <name> is not approved: … differs from origin/main`
|The definition was changed locally. Revert it, or ask the Engineering Manager to submit again. To try the changed definition, use `--trial`.

|`the worktree of aidev/<name> (…) has uncommitted changes, left by a run that stopped in the middle of a step`
|An earlier run stopped part way. Continue it with `--resume last`, or throw the changes away with the `git -C … reset --hard` and `clean -fd` shown, then run.

|`another run (…, process N) is working in …`
|A run of the same workflow is going. Wait for it to end.

|`aidev/<name> has work that conflicts with …`
|The branch's earlier work conflicts with the base now. Resolve it with `git merge` in the worktree, or use `--dated` for a branch of its own.

|`workflow stopped — step <id>: the until check still fails after N retries (…)` +
`… the same failure repeated`
|The agent could not meet `until` (the parentheses give the last result: `npm test exited 1`, `test-reviewer answered FAIL` and so on). The finished steps are in the checkpoints on the branch `aidev/<name>`. Look at them, and at the command's output (the file `log` in `run.json` points to) or `review` in `run.json` (the checking agent's last report). If you can fix the cause by hand, fix it and continue with `--resume last`. Otherwise make `--task` more specific or ask the Engineering Manager to revisit `until.max_retries`, the `prompt` or `until.prompt`.

|`workflow stopped — step <id>: cost limit of $N reached` +
`… time limit of N minutes exceeded`
|A limit was reached. Continue with `--resume last` (the limits are counted anew). If it keeps happening, make `--task` smaller, or ask the Engineering Manager to revisit the limits (the limits are part of the definition, so changing them is a PR).

|`workflow stopped — step <id>: <command> exited N`
|A `command` step failed. Read the output (the file `log` in `run.json` points to), fix the cause and continue with `--resume last`.

|`workflow stopped — step <id>: … N path(s) that must stay unchanged were changed`
|The step changed a path in `unchanged`. The changed paths are in `log.txt`. Put them back (`git checkout -- <path>` and so on), then continue with `--resume last`. If the job cannot be done without changing them, ask the Engineering Manager to revisit the definition.

|`workflow stopped — step <id>: target <target>: …`
|A `for_each` step stopped at that target. The rest of the reason reads like the rows above. Fix the cause and continue from that target with `--resume last`.

|`workflow stopped — step <id>: <file> line N: "…" is not a target` +
`… lists N targets, above for_each.max_items`
|The list is not written in the expected format, or it has more targets than the limit. Fix the list file (`notes/` in the run record) and continue with `--resume last`. If it keeps happening, ask the Engineering Manager to fix the `prompt` of the step that writes the list.

|`workflow <name> has changed since run <id> started`
|The definition changed after the run started. Start a new run without `--resume`.

|`run <id> was not made on a branch of its own (it predates worktree runs)`
|A run started by a version from before worktree runs cannot continue. Start a new run.

|`the checkpoints of run <id> are no longer on aidev/<name> (… is not in its history; a later run moved the branch); start a new run`
|The checkpoints of the finished steps are no longer on the branch (a later `--trial` reset it, or the branch was moved after a merge). Start a new run without `--resume`.

|`run <id> was a trial run; resume it with --trial` +
`run <id> was not a trial run; resume it without --trial` +
`workflow <name> has no recorded run that was not a trial (pass --trial to continue the last trial)` +
`workflow <name> has no recorded trial run (its runs were started without --trial)`
|`--resume` continues only a run of the same kind. Add `--trial` to continue a trial, and leave it out for an ordinary run (xref:workflows-trial[Trying it before approval]).

|`the definition of <name> (or an agent or skill it uses) changed since trial run <id> started; start a new trial`
|The definition (or an agent or skill) changed after the trial started. Run it again with `--trial`, without `--resume`.

|`--resume continues the run with the inputs it was started with; do not pass --input`
|A continued run uses its first inputs. Leave `--input` out.

|`the workflow needs --input for: <name> (<description>)` +
`the workflow declares no input "<name>" (its inputs: …)` +
`input <name>: "<value>" does not match its pattern (<pattern>)` +
`input <name> reaches a command, so its value must be one plain token (…)` +
`input <name> is given twice`
|An `--input` is missing, its name is not declared, or its value breaks the rules. The declarations are listed under `## Inputs (--input name=value)` in `--dry-run` (xref:workflows-inputs[Taking values that change per run]). Nothing has started.

|`input <name>: <path> is not committed; a run starts from HEAD (commit it, or declare the input with file: true and pass the file)` +
`input <name>: <path> is ignored by git and no provide: entry copies it into the run (add one, or pass it as a file input)` +
`input <name>: <path> does not exist in <checkout>` +
`input <name>: <path> does not exist in the run's worktree (…); a file git ignores reaches it only through provide:`
|A `path: true` input does not reach the run's worktree. Commit it, add it to `provide:`, or pass it as a `file: true` input (xref:workflows-provide[Providing files the worktree lacks]). Nothing has started.

|`input <name>: <file> is not a file on this machine` +
`input <name>: the AI tools read text; export <file> to Markdown, CSV or text first and pass that file`
|The file of a `file: true` input is missing or is not text (Excel, Word, PDF and images cannot be read). Export it to text and pass that path.

|`provide: <glob> matches no file that git ignores in <checkout> (a run copies only ignored files from the checkout; put the file there, or take the entry out)`
|Your checkout has no gitignored file matching that glob. Put the file there, or ask the Engineering Manager to take the `provide` entry out. Nothing has started.

|`provide: <file> is ignored in <checkout> by a rule the repository does not carry; commit the .gitignore that ignores it, so every run (and every teammate's) treats it alike`
|The rule that ignores that file is not committed (`.git/info/exclude`, or a `.gitignore` not committed yet). Write it in `.gitignore` and commit.

|`step <id>: <command> was not found on PATH, so "…" could not run`
|The command's executable is not on PATH. Install it or put it on PATH. Nothing has started (a relative path such as `./run.sh` or `node_modules/.bin/x` is not checked, because an earlier step may make it).

|`step <id>: "git … push" pushes; a trial run pushes nothing`
|With `--trial`, a command step or `until.command` that pushes cannot run. Take it out for the trial, or check another way.

|`agent <name> uses the MCP server <server>, which .mcp.json does not register`
|A server in the agent's `mcp` is not in the PKG's `.mcp.json`. Register the server in `.mcp.json` (a person does this). Nothing has started.

|`agent <name> is given tools (in its frontmatter or the workflow's agents:), and <tool> cannot be limited to them; run it with claude`
|An agent with `tools` or `mcp` does not start on an AI tool that cannot be limited (Copilot CLI and so on). Set `tools.agent` in `aidev.yaml` (or the workflow's `tool`) to `claude`.

|`branch aidev/<name> is ready; hosting.type is generic; open the pull request by hand`
|Normal. Open the PR by hand from the pushed branch.

|`N file(s) changed outside what the steps may write, by a command step or past the guard; not committed: …`
|The run has not stopped (the exit code follows the result). A command step wrote outside `writable`, or an agent wrote past the guard. It is not committed; if it is needed, the Engineering Manager widens that step's `writable`.

|`step <id>: the tool was refused N call(s): Write src/x.ts … (a path outside writable? see run.json "denied")`
|The run has not stopped. The agent was refused for calling outside `writable` or for a tool it was not given. The list is in `denied` of that step in `run.json`. If the work needs it, the Engineering Manager fixes `writable` or the agent's `tools`.

|`left out, never committed: N file(s) matching <glob> (e.g. <path>)`
|Normal. A toolchain's residue (`node_modules` and so on) and the `never_commit` paths were kept out of the commits (xref:workflows-never-commit[What is never committed]).
|===

[[workflows-fix]]
=== Fixing a workflow (Engineering Manager)

There are two reasons to fix a workflow: the reviewer of the definition pull request asks for changes, or a run's result (the result pull request) is not what you expected. In both cases you fix **the definition (`workflow.yaml` and the agents and skills)**. Fixing only the result pull request by hand does not help: the next run gives the same result.

==== Where to fix

Start from the problem you see.

[cols="2,1,3",options="header"]
|===
|Problem |Where to fix |How

|The survey step's findings are not used by the next step
|The survey step's `prompt`
|Write "list the results in your final report". For a long list or a plan, write "write it to a file in the notes directory", and write "read that file" in the next step's `prompt` (xref:workflows-handoff[Passing results between steps]).

|A write is denied and the run stops (`is read-only`)
|That step's `writable`
|Add the path it needs. Add only places that step really needs.

|It changes files you did not ask for
|That step's `writable` and `prompt`
|Narrow `writable`, and write "do not change …" in the `prompt`.

|It passes `until` by weakening tests or settings
|That step's `unchanged`, `until`
|List the paths that must not be weakened in `unchanged`. Have `until.command` call the test runner itself (xref:workflows-unchanged[Naming what must not change]).

|Many targets: the later ones get worse work, and one failure redoes everything
|How the steps are split
|Split it into a step that writes the list and a step that handles one target at a time with `for_each` (xref:workflows-for-each[Repeating a step per target]).

|It does not know the procedure, so the way of working varies
|The agent's `skills`
|Write the procedure as a skill and add it to the agent's `skills`.

|It cannot see an external system (tickets and so on)
|The agent's `mcp` and the PKG's `.mcp.json`
|Register the server in `.mcp.json` (a person does this) and add its name to the agent's `mcp`.

|It says a tool it needs is missing
|The agent's `tools`
|Add that tool. Do not add `Bash` to an agent that touches external systems; split it into another agent instead.

|`until` keeps failing and the run stops
|`until` (with its `max_retries`), how the steps are split
|Check by hand that the `until` command really passes in this PKG (`cwd` is the directory it runs in, `env` its environment variables). If the job is too big, split the step.

|The checking agent keeps failing the work
|`until.prompt`, the step's `prompt`
|Read its remarks in `review` in `run.json`. Make the check specific, and write the same points in the step's `prompt` so the working agent knows them from the start.

|It stops at the cost or time limit
|`limits.max_usd`, `limits.max_minutes`
|Decide from the cost and time in the run record (`.aidev/workflows/<name>/runs/<id>/run.json` in the run's worktree) and the estimate of `aidev estimate workflow <name>`.

|A value that differs per run (the specification's path, the screen) is rewritten in the `prompt`
|`inputs`
|Declare it under `inputs:` and write `{inputs.<name>}` in the `prompt` or `until.command`. The person running it passes it with `--input` (xref:workflows-inputs[Taking values that change per run]).

|It stops on a file the worktree lacks (a gitignored specification or fixtures)
|`provide`, a `file: true` input
|For data kept at a path the team agreed on, write a glob in `provide:`. For a file one person has, use a `file: true` input (xref:workflows-provide[Providing files the worktree lacks]). `node_modules` is installed by a `command: npm ci` step.

|What a command step or the tests left behind (result reports, caches) gets committed
|`never_commit`
|Write those paths in `never_commit:`. `node_modules`, `__pycache__` and the like are not committed even without it (xref:workflows-never-commit[What is never committed]).
|===

Agents and skills are shared by every workflow that uses them. **Changing an agent's .md also changes how the other workflows that use that agent behave.** To change only one workflow, make a separate agent (`aidev create agent <new-name>`).

[[workflows-fix-from-run]]
==== Fixing a workflow from a stopped run

A workflow mostly fails because an agent meets the same error again and again (`the same failure repeated`). With `--from-run`, the workflow-creator gets that run's record and is asked to change the definition so the cause goes away.

[source,bash]
----
aidev modify workflow write-tests --from-run last
aidev modify workflow write-tests --from-run 2026-09-23T01-12-03-114Z --describe "make the test data from fixtures"
----

* What the agent gets: why the run stopped, each step's result and agent starts, the last check of each step that did not pass (the log of the `until` command, the checking agent's findings, the failed targets), and the end of the run log.
* The agent states the cause in one line (`CAUSE:`) before listing its changes. It is told to raise retries or limits only when the record shows that is the cause.
* `--describe` may be left out (the request is then "fix what made this run fail"); when given, it goes to the agent too.
* What changed and why is kept in `.aidev/cache/modify/<name>.json` and goes into the PR description of the next `aidev submit workflow` (xref:review-workflow-def[Workflow definition pull requests]).

==== Fix and submit again

. If the definition pull request is not merged yet, make sure you are on its branch (`aidev/workflow-<name>`). After `aidev submit workflow` you are on that branch.
+
[source,bash]
----
git checkout aidev/workflow-write-tests    # only if you moved to another branch
----
+
To fix a workflow that is already merged, start from the latest `main` (`git checkout main`, `git pull`).
. Edit `workflow.yaml`, the agents and the skills, by hand or by telling workflow-creator what to change in plain language (xref:cli-modify[aidev modify]).
+
[source,bash]
----
aidev modify workflow write-tests --describe "Add a reviewer to the write step's until that checks what the tests verify"
----
+
`modify` gives the agent the current definition and has it leave what the request does not touch. An agent other workflows also use is not edited; a new agent is written instead. The files as they were are kept in `.aidev/cache/modify/`.
+
To change it while looking at the flow of its steps, use the editor in the browser (xref:cli-edit[aidev edit]). Every change is checked as a run would check it, and the page shows the difference from the approved copy and the estimated cost. It saves `workflow.yaml` only.
+
[source,bash]
----
aidev edit workflow write-tests
----
. Check for mistakes in how it is written. If it shows `invalid:`, fix the item it names.
+
[source,bash]
----
aidev list workflows
----
. Show each step's details and check they are what you meant. It is not approved, so the last line says `would be refused (try it as it is with --trial)`, but you can still use it to check the content.
+
[source,bash]
----
aidev run workflow write-tests --dry-run
----
. Check that the cost ceiling (`limits.max_usd`) still fits the changed definition.
+
[source,bash]
----
aidev estimate workflow write-tests
----
. Try the definition as it is. It runs before approval and pushes nothing. Fix and try again until the result is what you expect (xref:workflows-trial[Trying it before approval]).
+
[source,bash]
----
aidev run workflow write-tests --trial --task "src/services/order.ts"
----
. Submit again. The fix is added as a commit on the same branch, and if a pull request exists, its body is updated to the new content.
+
[source,bash]
----
aidev submit workflow write-tests
----

Once merged, the new definition is approved. Until then your local change exists only in your clone; others can keep running the previous definition that is on `main`.

[[workflows-agents-skills]]
=== Agents and skills

An agent is a role definition handed to the AI tool (Markdown); a skill is a set of instructions. A workflow's steps reference agents by name, and an agent references the skills it uses by name.

The ADK ships **machinery** only: the workflow runner and its validation, the approval check, the write limits, and four agents — workflow-creator (writes workflows), agents-creator (writes agents), knowledge-builder (writes the Wiki) and permission-setting (drafts the policy candidate). The CLI also has agents for estimates (cost-estimator, estimate-reviewer); they are not placed in the PKG, and the CLI starts them for `aidev estimate` and at the end of a run (xref:cli-estimate[aidev estimate]).

The development work itself — workflows that implement, write tests or write out conventions, and their agents — belongs to the **package**. The only thing the ADK bundles is the standard workflow templates (`playwright-tests`; xref:workflows-standard[Starting from a standard workflow]), and even those become the package's files once copied with `--from`. The Engineering Manager creates them with `aidev create workflow <name> --describe "<what you want>"` or copies a standard workflow. MCP servers (reading Azure DevOps Work Items, for instance) are also the package's own, in its `.mcp.json`; the ADK neither ships nor starts them.

PKG-specific agents and skills go in `.aidev/agents/<name>.md` and `.aidev/skills/<name>/SKILL.md`. They take precedence over a bundled one of the same name. There are three ways to make them.

* Write a template with `aidev create agent <name>` / `aidev create skill <name>` and edit it. For an `agent`, `--describe "<text>"` can have agents-creator write it
* `aidev create workflow --describe`, where workflow-creator has agents-creator write the agents and skills the workflow needs
* Have the AI write them in an interactive session (`.aidev/agents/**` and `.aidev/skills/**` are writable under the default policy)

An agent's frontmatter says what that agent can use (its capabilities).

[source,markdown]
----
---
name: test-writer
description: Writes tests in the existing style. Started by the write-tests workflow
skills: [test-and-verify]            # skills whose text goes into its instructions; [] when none
tools: Read, Grep, Glob, Edit, Write # the built-in tools it can use; omitted = the tool's default (all)
mcp: []                              # MCP servers it can use (keys of the PKG's .mcp.json); omitted = none
subagents: []                        # subagents it may start; omitted = whatever the AI tool offers
model: inherit
---
----

[%autowidth.stretch,options="header"]
|===
|Key |Meaning

|`skills`
|Skills whose text goes into that agent's instructions. The PKG's `.aidev/skills/<name>/SKILL.md` is looked up first; if absent, the ADK's bundled one is used.

|`tools`
|The built-in tools it can use in Claude Code (`Read`, `Edit`, `Bash` and so on). Tools not listed are not given. If omitted, it gets all of the tool's defaults.

|`mcp`
|The MCP servers it can use. Write names registered in the PKG's `.mcp.json`. Servers not listed are not given. A name not in `.mcp.json` stops the workflow before it starts.

|`subagents`
|The subagents it may start with the `Agent` tool (names of `.aidev/agents/<name>.md`). When written, no other can be started (xref:workflows-subagents[Naming the subagents an agent may start]).
|===

* An agent with `tools` or `mcp` runs only on Claude Code, because Copilot CLI and the others cannot limit the tools they are given.
* Do not give `Bash` to an agent that touches an external system. With `Bash` it can reach outside without going through MCP, and limiting `mcp` means nothing. Tests are run by the ADK through `until`, not by the agent.
* Give work with different permissions to different agents (a read-only `ticket-reader` and a `ticket-updater` that updates, for instance).

To add a skill or an MCP server in one workflow only, write it in that workflow.yaml's `agents:` rather than the agent's frontmatter. `skills`, `mcp` and `subagents` are added to the frontmatter's; `tools` is used instead of the frontmatter's (xref:workflow-reference-agents[agents]).

[source,yaml]
----
agents:
  ticket-reader:
    skills: [ticket-format]
    mcp: [azure-devops]
----

[[workflows-subagents]]
==== Naming the subagents an agent may start

An agent with the `Agent` tool can hand part of its work to subagents (several at once if it likes). `subagents` **names the subagents** that agent may start. Write it in the agent's frontmatter or in workflow.yaml's `agents:`.

[source,yaml]
----
agents:
  lead:
    subagents: [scout, reviewer]     # .aidev/agents/scout.md, reviewer.md
----

* A subagent is defined in an ordinary agent file (`.aidev/agents/<name>.md`). The ADK hands its body and skills to Claude Code as a subagent for that run (`--agents`).
* An agent with `subagents` can start only those (the hook refuses the others, Claude Code's built-in general-purpose included). Without it, the agent can use whatever Claude Code offers, as before.
* A subagent can use only its own `tools` and `mcp`, and cannot have a tool or MCP server its parent agent lacks (validation refuses it). It writes where the parent's step may write (`writable`).
* An agent with `subagents` runs only on Claude Code. If the PKG's `.claude/settings.json` is older (its hook does not see `Agent`), the run stops before it starts; update it with `aidev sync tools` and commit.
* A subagent's file is approved like the others: `aidev submit workflow` puts it in the PR.

List them with `aidev list agents` / `aidev list skills`, and remove them with `aidev remove agent|skill <name>` (one referenced by a workflow is refused). All of them go into the PR together with the workflow through `aidev submit workflow`, are reviewed there, and only what is on `main` is used by a workflow.

[[workflow-reference]]
== Workflow definition reference

This chapter describes every field of a workflow and of the agents and skills it uses. The ideas and how to use them are in xref:workflows[Delegating work to the AI (workflows)]; this chapter is for looking things up while you write.

[[workflow-reference-files]]
=== Files and how they relate

[cols="2,3,3",options="header"]
|===
|File |What it holds |Who refers to it

|`.aidev/workflows/<name>/workflow.yaml`
|The order of the steps and each step's limits (where it may write, when it is done, ceilings). What this workflow adds to its agents (`agents:`)
|`aidev run workflow <name>`

|`.aidev/agents/<name>.md`
|An agent's role (the body) and what it can use (`skills`, `tools`, `mcp`, `subagents` in its frontmatter)
|A step's `agent:` and `until.agent:`

|`.aidev/skills/<name>/SKILL.md`
|A procedure
|An agent's frontmatter `skills:`, a workflow's `agents.<agent>.skills`
|===

.A workflow names agents in its steps; an agent names skills
[mermaid]
----
flowchart LR
  W["workflow.yaml"] -- "steps[].agent" --> A["agents/#60;name#62;.md"]
  W -- "steps[].until.agent" --> R["agents/#60;checker#62;.md"]
  A -- "frontmatter skills" --> S["skills/#60;name#62;/SKILL.md"]
  A -- "frontmatter mcp" --> M["server in .mcp.json"]
  W -- "agents.#60;name#62;.skills" --> S
  W -- "agents.#60;name#62;.mcp" --> M
  A -- "frontmatter subagents" --> SA["agents/#60;subagent#62;.md"]
  W -- "agents.#60;name#62;.subagents" --> SA
----

Agents and skills are looked up in the PKG's `.aidev/` first, then among those bundled with ADK. With the same name, the PKG's wins.

[[workflow-reference-skeleton]]
=== workflow.yaml as a whole

An example with every field. Text after `#` explains it.

[source,yaml]
----
name: e2e-tests                    # required
description: Write e2e tests for the main screens and open a PR
objective: |                       # required
  Add Playwright tests for the screens named in the task, from {inputs.spec}.
tool: claude                       # optional
model: sonnet                      # optional
agents:                            # optional. What this workflow adds to an agent
  e2e-writer:
    skills: [test-and-verify]      # added to the frontmatter's skills
    mcp: [playwright]              # added to the frontmatter's mcp
    tools: [Read, Grep, Edit]      # used instead of the frontmatter's tools
inputs:                            # optional. Values taken per run with --input <name>=<value>
  spec:
    description: the test specification to work from
    file: true                     # a file on this machine; the run gets a copy
  browser:
    default: chromium
    pattern: '[a-z]+'              # an input that reaches a command needs a pattern
env_required:                      # optional. Environment variables (credentials) the shell of whoever runs it must have. A list of names only works too
  E2E_PASSWORD: the password of the test user
provide: [e2e/fixtures/**]         # optional. Gitignored files copied from your checkout
never_commit: [e2e/test-results/**]   # optional. Never committed, on top of the ADK's own list

steps:                             # required; run top to bottom
  - id: plan                       # an agent step
    description: Find the screens that need tests
    agent: e2e-planner
    writable: []
    prompt: Survey the screens and write them to targets.txt in the notes directory, one per line.
  - id: write                      # an agent step with for_each, until and unchanged
    agent: e2e-writer
    writable: [e2e/tests/**]
    unchanged: [e2e/playwright.config.ts]
    for_each:
      from: targets.txt
      max_items: 20
      on_failure: continue
    prompt: Write the e2e test for screen {item} in e2e/tests/{item}.spec.ts.
    until:
      command: [npm ci, npx playwright test tests/{item}.spec.ts --project {inputs.browser}]
      cwd: e2e
      env: { CI: 1 }
      timeout_minutes: 15
      agent: e2e-reviewer
      prompt: Does the test cover every main action of screen {item}?
      max_retries: 3
    timeout_minutes: 30
  - id: lint                       # a command step
    command: npm run lint
  - id: pr                         # a pull-request step
    pull_request:
      title: "test: add e2e tests"

limits:
  max_usd: 10                      # required
  max_minutes: 45                  # optional
----

A field that is not in the tables below is refused by validation (`unknown key …`). `aidev list workflows` (shown as `invalid:`), `aidev run workflow <name> --dry-run` and `aidev submit workflow` validate.

[[workflow-reference-top]]
=== Top level

[cols="1,1,1,4",options="header"]
|===
|Field |Type |Required |Description

|`name`
|string
|required
|The workflow's name, the same as its directory. Lowercase letters, digits and dashes, up to 64 characters, starting with a letter or digit (`^[a-z0-9][a-z0-9-]{0,63}$`).

|`description`
|string
|optional
|One line. Shown by `aidev list workflows` and in the PR title and body.

|`objective`
|string
|required
|What the workflow is for. It heads the instructions of every agent step.

|`tool`
|string
|optional
|The AI tool that runs the agents (`claude`, `copilot`, `codex`, `kiro`). Only one listed in `tools.default` in `aidev.yaml`. When omitted: `tools.agents.<agent>.tool`, then `tools.agent` in `aidev.yaml`.

|`model`
|string
|optional
|The model name (`sonnet` and so on). `""` passes no model and leaves it to the AI tool. When omitted: `tools.agents.<agent>.model`, then `tools.agent_model` in `aidev.yaml`. Letters, digits and `. _ - : / @ [ ]`, up to 200 characters.

|`agents`
|mapping
|optional
|What this workflow adds to its agents. The keys are names of agents the steps use (`agent:` or `until.agent:`) (xref:workflow-reference-agents[agents]).

|`inputs`
|mapping
|optional
|Declares the values taken per run with `--input <name>=<value>`. The keys are the inputs' names; each goes where the definition writes `{inputs.<name>}` (xref:workflow-reference-inputs[inputs]).

|`env_required`
|list or mapping
|optional
|Environment variables (credentials) that must be set in the shell of the person running it. A list of names, or a mapping from name to description. Without them, nothing starts (xref:workflow-reference-env-required[env_required]).

|`provide`
|list of globs
|optional
|Files git ignores in your checkout, copied into the run's worktree before the first step (xref:workflow-reference-provide[provide]).

|`never_commit`
|list of globs
|optional
|Paths a run never commits, on top of the ADK's own list (xref:workflow-reference-never-commit[never_commit]).

|`steps`
|list
|required
|The steps, at least one, run top to bottom. Each step is exactly one of an agent step, a command step, a pull-request step or a parallel group, decided by which key it has: `agent`, `command`, `pull_request` or `parallel` (the sections below). A step with two of them is refused.

|`limits`
|mapping
|required
|What stops the run. Holds `max_usd` (required) and `max_minutes` (optional) only (xref:workflow-reference-limits[limits]).
|===

[[workflow-reference-agents]]
=== agents

The skills, MCP servers and built-in tools an agent can use are normally written in its frontmatter (xref:workflow-reference-agent[Agent definition]). `agents:` is where workflow.yaml adds what an agent should have **only in this workflow**. The same agent can run with different capabilities in another workflow.

[source,yaml]
----
agents:
  ticket-reader:
    skills: [ticket-format]        # added to the frontmatter's skills
    mcp: [azure-devops]            # added to the frontmatter's mcp
  test-writer:
    tools: [Read, Grep, Glob, Edit, Write]   # used instead of the frontmatter's tools
----

[cols="1,1,1,4",options="header"]
|===
|Field |Type |Required |Description

|`agents.<agent>`
|mapping
|optional
|`<agent>` is the name of an agent a step's `agent:` or `until.agent:` uses, or of a subagent in its `subagents`. Any other name is refused (`no step names agent …`). Holds `skills`, `mcp`, `tools` and `subagents` only.

|`agents.<agent>.skills`
|list
|optional
|Skills **added** to the frontmatter's `skills`. Looked up in the PKG, then among those bundled with ADK; one found in neither stops validation (`<workflow.yaml>: agents.<agent>: skill … is neither in …`).

|`agents.<agent>.mcp`
|list
|optional
|MCP servers (keys of the PKG's `.mcp.json`) **added** to the frontmatter's `mcp`. A name not in `.mcp.json` stops the workflow before it starts.

|`agents.<agent>.tools`
|list
|optional
|The built-in tools the agent can use in this workflow. When written, it is used **instead of** the frontmatter's `tools` (not added to it). When omitted, the frontmatter's `tools` apply. An empty list is refused.

|`agents.<agent>.subagents`
|list
|optional
|Subagents the agent may start, **added** to the frontmatter's `subagents` (xref:workflows-subagents[Naming the subagents an agent may start]). The subagents named here may be keys of `agents:` too.
|===

* What is added is treated like the frontmatter's capabilities: Claude Code is started with only those, and the hook refuses any other tool. An agent with `tools` or `mcp` runs only on Claude Code.
* workflow.yaml is what gets approved, so changing `agents:` makes the workflow unapproved again. Put it in a PR with `aidev submit workflow` and have it reviewed.
* A step cannot carry `skills`, `mcp`, `tools` or `subagents` (`a step does not carry …`). For different capabilities per step, use a different agent.

[[workflow-reference-inputs]]
=== inputs

How a value that changes per run goes into a fixed place in the definition (xref:workflows-inputs[Taking values that change per run]). A name declared under `inputs:` is written as `{inputs.<name>}`, and the person running the workflow passes it with `aidev run workflow <name> --input <name>=<value>`.

[source,yaml]
----
inputs:
  spec:
    description: the test specification to work from
    file: true
  screen:
    description: the screen to cover
    pattern: '[a-z0-9-]+'
  browser:
    default: chromium
    pattern: '[a-z]+'
----

[cols="1,1,1,4",options="header"]
|===
|Field |Type |Required |Description

|`inputs.<name>`
|mapping
|optional
|`<name>` starts with a lowercase letter and is made of lowercase letters, digits, `_` and `-`, up to 32 characters (`^[a-z][a-z0-9_-]{0,31}$`). It holds only the five fields below (there is no `required` field: an input without `default` is required). An empty mapping (`notes: {}`) is a required input with no rule.

|`description`
|string
|optional
|For the person running it. Shown when an `--input` is missing, and under `## Inputs (--input name=value)` in `--dry-run` and in the submit PR body.

|`default`
|string
|optional
|The value when `--input` is not given. Without it, the input is required. Checked at validation by the same rules as a value. Cannot be written for a `file: true` input.

|`pattern`
|string
|required for an input that reaches a command (without `path` or `file`)
|A regular expression the whole value must match (up to 200 characters; the ADK wraps it as `^(?:…)$`). A value starting with `[` is a YAML list, so quote it (`'[a-z]+'`).

|`path`
|`true` / `false`
|optional
|With `true`, the value is a path relative to the PKG. One starting with `/` or a drive letter, one containing `..`, and one with a non-text extension (`.xlsx`, `.docx`, `.pdf`, images, archives) are refused. Before the run starts, it is checked to be committed at HEAD, or ignored by git and matched by a `provide` glob; after `provide` has copied, it is checked to exist in the worktree. Cannot be written with `file`.

|`file`
|`true` / `false`
|optional
|With `true`, the value is the path of a file anywhere on this machine (absolute, or relative to the shell's current directory). It must be an existing text file (the same extension rule as `path`). The ADK copies it to `.aidev/workflows/<name>/runs/<id>/inputs/<name><extension>` in the run's worktree, and `{inputs.<name>}` becomes that path relative to the PKG (gitignored; never committed). `--resume` uses that copy. No `default`, and cannot be written with `path`.
|===

Rules for `{inputs.<name>}`:

* It can be written in `objective`, an agent step's `prompt`, `until.prompt`, `until.command`, a command step's `command` and the values of `env` (of a step and of `until`). In `description`, a step's `description`, `pull_request.title`, `writable`, `unchanged`, `cwd`, `until.cwd` or `for_each.from`, validation refuses it (`… cannot name an input ({inputs.…})`). It cannot be the executable of a command (the first word) (`the executable of a command (…) is fixed; an input can be an argument, not the command`). A name that is not declared gives `… names {inputs.<name>}, which inputs: does not declare`.
* The values are written into the definition before the run (as one argument in a command). `{item}` is replaced per target afterwards. A value cannot contain `{` or `}`.
* A value is one line, up to 1000 characters, with no control characters. With `pattern`, the whole value must match it.
* **An input that reaches a command** (one written in `until.command`, a command step's `command` or an `env` value) must have `pattern`, `path: true` or `file: true` (`inputs.<name> reaches a command (…), so it needs a pattern that bounds its value (or path: true / file: true)`). Its value must also be one word within the fixed rule `^[A-Za-z0-9._@][A-Za-z0-9._/@:=+-]{0,999}$` with no `..` segment (no whitespace, no leading `-`: the same idea as a `for_each` target). A `pattern` can narrow this, never widen it.

Rules for `--input` (`aidev run workflow`, `aidev estimate workflow`):

* `--input <name>=<value>` once per input (`--input=<name>=<value>` works too).
* A required input missing: `the workflow needs --input for: <name> (<description>)` (the run exits 1 before anything starts; `--dry-run` too. `aidev estimate` estimates without it). A name not declared: `the workflow declares no input "<name>" (its inputs: …)`. The same name twice: `input <name> is given twice`.
* It cannot be passed with `--resume`. A continued run uses the values recorded in `run.json`, checked again by the same rules as when they were passed.
* A value written in `aidev.yaml` as `workflows.<name>.inputs.<input>: <value>` is used when `--input` is not given (`--input` > `aidev.yaml` > `default`). It is checked by the same rules; a name not declared stops with `aidev.yaml: workflows.<name>.inputs: the workflow declares no input "<name>"`, and a `file: true` input with `… is a file on the machine of whoever runs the workflow`. An input with a credential-like name is refused when `aidev.yaml` is read (xref:configuration[aidev.yaml reference]). The `inputs` row of `--dry-run` carries `(from aidev.yaml)`.
* Besides where `{inputs.<name>}` is written, the values go, as data, into a `## Inputs for this run` section of the instructions of every agent (the checking agents included), onto the `inputs` row of `--dry-run`, into `## Inputs` of the run's PR body, into the last commit's message, into `inputs` in `run.json`, into the head and the summary of `--log`, and into the record of `aidev modify --from-run`.

[[workflow-reference-env-required]]
=== env_required

Environment variables that must be set in the shell of the person running the workflow (xref:workflows-env-required[Taking credentials from environment variables]). They are for credentials (passwords, tokens); a setting goes in `inputs` or `env`.

[source,yaml]
----
env_required:
  E2E_PASSWORD: the password of the test user   # name: description
  API_TOKEN:                                    # the description can be left out
# A list of names only can be written too
# env_required: [E2E_PASSWORD, API_TOKEN]
----

[cols="1,1,1,4",options="header"]
|===
|Field |Type |Required |Description

|`env_required`
|list of names, or mapping name → description
|optional
|A name follows the rule for environment variables (`^[A-Za-z_][A-Za-z0-9_]{0,63}$`). `AIDEV_*` and `GIT_CONFIG*` cannot be written. Up to 32. The description is one line, and is shown in the error for the person running it, on the `env` row of `--dry-run`, under `## Environment variables the run needs` in the submit PR body, and under `## Environment variables of this run` in the agents' instructions. The same name written in the `env` of a command step, of an agent step or of `until` is refused by validation (`env sets <NAME>, which env_required says the shell provides`).
|===

* `aidev run workflow` and `--dry-run` check, before anything starts, that each variable is set (and not empty). When one is not, they print `the environment variable <NAME> (<description>) is not set; the workflow needs it (env_required). Export it in the shell that runs aidev; …` and exit 1. The same with `--resume`. The `env` row of `--dry-run` reads `<NAME>: set` or `<NAME>: NOT SET`.
* The values are never read. The agents and commands inherit the environment of the shell of the person running it, and that is how the values reach them. No value goes into `run.json`, `log.txt`, `--log`, the PR body, a commit message or an agent's instructions.

[[workflow-reference-provide]]
=== provide

Files git ignores in your checkout that are copied into the run's worktree (xref:workflows-provide[Providing files the worktree lacks]).

[source,yaml]
----
provide: [docs/spec/**, e2e/fixtures/**]
----

[cols="1,1,1,4",options="header"]
|===
|Field |Type |Required |Description

|`provide`
|list of globs
|optional (default `[]`)
|Globs starting with a fixed directory or file name (`**/*.txt` is refused: `must start with a fixed directory or file name`). Validation refuses a path under `.aidev`, `.git` or `protected` (`never copied into a run`), and one whose last name looks like a credential file (`.env`, `.env.*`, `.npmrc`, `.netrc`, `.pypirc`, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `*.jks`, `*.keystore`; `credentials never go into a run`).
|===

* Before the first step (every time it starts, `--resume` included), the **ignored files** matching a glob are copied, file by file, to the same path in the worktree (overwriting). A tracked file is in the worktree as it is at HEAD; a file that is neither tracked nor ignored is not copied. `docs/spec/**` is every ignored file under docs/spec.
* Anything matching `secrets_paths`, anything under `.aidev/` or `.git/`, and symbolic links are not copied (the log says `provide: <path> not copied (<reason>)`).
* A glob that matches no ignored file stops `--dry-run` and the run before anything starts (`provide: <glob> matches no file that git ignores in <checkout> (…)`).
* When the rule that ignores a copied file is not in a committed `.gitignore`, the run stops (`provide: <file> is ignored in <checkout> by a rule the repository does not carry; commit the .gitignore that ignores it, …`).
* The log says `provide: N path(s) copied from the checkout: …`. `--dry-run` has a `provide` row, and the submit PR body a `## Provided from the checkout` section.

[[workflow-reference-never-commit]]
=== never_commit

Paths a run never commits, on top of the ADK's own list (xref:workflows-never-commit[What is never committed]).

[source,yaml]
----
never_commit: [e2e/test-results/**, e2e/playwright-report/**]
----

[cols="1,1,1,4",options="header"]
|===
|Field |Type |Required |Description

|`never_commit`
|list of globs
|optional (default `[]`)
|Untracked files that are not committed even inside a step's `writable`. One of the form `<dir>/**` that covers an entry of a step's `writable` or of `provide` is refused by validation (`never_commit <glob> covers what step <id> may write (…)`, `never_commit <glob> covers provide <glob>`).
|===

The ADK's own list. An untracked file matching it is not committed even without `never_commit`. Nothing can be taken off it.

[source,text]
----
**/node_modules/**
**/bower_components/**
**/.pnpm-store/**
**/.yarn/cache/**
**/.venv/**
**/venv/**
**/__pycache__/**
**/*.pyc
**/.pytest_cache/**
**/.mypy_cache/**
**/.ruff_cache/**
**/.tox/**
**/.nox/**
**/.gradle/**
**/.DS_Store
**/Thumbs.db
**/*.orig
**/*.rej
----

* Only untracked files are concerned. A change to a file git tracks is committed wherever it is.
* It applies to the checkpoints, the last commit of the pull-request step, the `unchanged` comparison, the undoing of a failed target, the diff shown to the checking agent, and the check for uncommitted changes before a new run.
* What is left out appears in the pull-request step's log (`N file(s) left out as never committed (<glob>; e.g. <path>)`), in `leftOut` of that step in `run.json`, at the end of the run (`left out, never committed: …`) and in the `## Left out` section of the PR body. `--dry-run` has a `never commit` row, and the submit PR body a `## Never committed` section.

[[workflow-reference-agent-step]]
=== Agent step

A step that starts an agent to do the work. A step with `agent` is an agent step.

[cols="1,1,1,1,4",options="header"]
|===
|Field |Type |Required |Default |Description

|`id`
|string
|optional
|`step-<number>`
|The step's name, unique in the workflow. Lowercase letters, digits and dashes, up to 32 characters. Used in the run record's file names and in what `--resume` shows.

|`description`
|string
|optional
|none
|For the reviewer. Shown by `--dry-run` and in the submit PR body. Not given to the agent.

|`agent`
|string
|required
|
|The agent to start (letters, digits and `. _ -`). `.aidev/agents/<name>.md`, else the one bundled with ADK.

|`prompt`
|string
|required
|
|What this step asks for. With `for_each`, it must contain `{item}`. `{inputs.<name>}` can be written too (xref:workflow-reference-inputs[inputs]).

|`writable`
|list of globs
|required
|
|Where this step's agent may write. `[]` writes nothing. Relative to the PKG root; an entry that starts with `/`, contains `..` or is a protected path (`.claude/**`, `.aidev/policy.yaml` and so on; xref:permissions[Permissions and safety]) is refused.

|`unchanged`
|list of globs
|optional
|`[]`
|Paths this step must leave as they are. They cannot be written even inside `writable`, and after every attempt they are compared with how they were when the step started (xref:workflows-unchanged[Naming what must not change]).

|`env`
|mapping
|optional
|`{}`
|Fixed environment variables (`NAME: value`) added to the environment of this step's agent and of its `until` commands. Use it for settings a test or a tool reads (the URL of the environment under test, say). The same rules as a command step's `env`; writing `{inputs.<name>}` makes that input one that "reaches a command", and in a `for_each` step `{item}` can be written too. `until.env` is layered on top. The agent's instructions carry the names and values as `Your environment also has these set for this step`. **Never a secret** (declare the environment variable's name under `env_required`; the same name here is refused by validation). Names that change what the agent's tool runs or where it talks (`PATH`, `PATHEXT`, `COMSPEC`, `SHELL`, `HOME`, `USERPROFILE`, `NODE_OPTIONS`, `NODE_PATH`, `NODE_EXTRA_CA_CERTS`, `SSL_CERT_*`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `DYLD_*`, `CLAUDE_*`, `ANTHROPIC_*`, `GIT_*`, `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` / `NO_PROXY`) cannot be set on an agent step (the hooks must keep running; a command step's `env` may still set them).

|`for_each`
|mapping
|optional
|none
|Start the agent afresh once per target (xref:workflow-reference-for-each[for_each]).

|`until`
|mapping
|optional
|none
|When the step is done. The agent is started again until it is met (xref:workflow-reference-until[until]).

|`timeout_minutes`
|number
|optional
|30
|The time allowed for one start of the agent, in minutes. Above 0 and at most 240 (`0.5` is fine). When less time is left in the workflow, that is used instead.
|===

[[workflow-reference-until]]
==== until

Write `command`, `agent`, or both. With both, the agent checks only after every command has passed.

[cols="1,1,1,4",options="header"]
|===
|Field |Type |Required |Description

|`command`
|string, or a list of strings
|required without `agent`
|Passes when it exits 0. A list runs top to bottom and fails at the first command that fails. No shell: quotes, pipes, redirections and variables (`\|&;<>$"'`, backquote, `\`) cannot be written. `{inputs.<name>}` can be written as an argument (not as the executable; that input needs `pattern`, `path` or `file`).

|`cwd`
|string
|optional
|The directory to run the commands in (inside the PKG). The PKG root when omitted. No absolute path, no `..`. Only with `command`.

|`env`
|mapping
|optional
|Environment variables for the commands (`NAME: value`). Each value is one fixed line. Names starting with `AIDEV_` or `GIT_CONFIG` are refused. The values are reviewed in the PR, so never put secrets here. Only with `command`. A value can hold `{inputs.<name>}` (the same rules as an input that reaches a command).

|`timeout_minutes`
|number
|optional
|The time allowed for one command, in minutes. Above 0 and at most 240. Only with `command`.

|`agent`
|string
|required without `command`
|The checking agent. It writes nothing. It passes the work when its final message ends with a `VERDICT: PASS` line (xref:workflows-until-agent[Letting an agent's review decide when a step is done]).

|`prompt`
|string
|required with `agent`
|What the checking agent checks. `{inputs.<name>}` can be written too.

|`max_retries`
|integer
|optional (default 3)
|How many times the agent is started again after the first attempt when the check fails. 0 to 10; 0 means no retry. A failed `unchanged` check is retried the same way. A step without `until` is not retried.
|===

[[workflow-reference-for-each]]
==== for_each

[cols="1,1,1,4",options="header"]
|===
|Field |Type |Required |Description

|`from`
|string
|required
|The name of the list file. It is in the run's notes directory (`.aidev/workflows/<name>/runs/<id>/notes/` in the run's worktree), written by an earlier step. Letters, digits and `. _ -`, up to 100 characters.

|`max_items`
|integer
|required
|The most targets one run takes on. 1 to 10000. A longer list stops the run before any agent starts.

|`on_failure`
|`stop` or `continue`
|optional
|What happens when a target fails. `stop` (the default) stops there. `continue` puts back the files inside `writable` that changed during that target and starts the next one. The run still stops when every target fails or a cost or time limit is reached (xref:workflows-unattended[Running a large job without anyone stepping in]).

|`parallel`
|integer
|optional (default 1)
|How many targets run at once. 1 to 16. From 2 up, every `writable` path of the step must contain `{item}` (`e2e/tests/{item}.spec.ts` and so on) (xref:workflows-parallel[Running agents in parallel]).
|===

The list has one target per line. Blank lines and lines starting with `#` are skipped, a leading `- ` or `* ` is removed, and a repeated line counts once. A target is one word of letters, digits and `. _ / @ -` (up to 200 characters, not starting with `-`, no `..`).

`{item}` can be written only in the `prompt` (where it is required), `writable`, `until.command` and `until.prompt` of a step with `for_each`. Anywhere else, validation refuses it. In `writable`, `{item}` becomes the target's name, and that target's agent may write only there. A path with `{item}` starts with a fixed directory (`{item}/x.ts` is refused). The pull-request step commits the whole directory before `{item}` (`e2e/tests/**` for `e2e/tests/{item}.spec.ts`).

[[workflow-reference-parallel]]
=== Parallel group

A step that runs agent steps at the same time (xref:workflows-parallel[Running agents in parallel]).

[cols="1,1,1,4",options="header"]
|===
|Field |Type |Required |Description

|`id`
|string
|optional
|The group's name. The same rules as a step id, and it may not repeat one.

|`description`
|string
|optional
|For the reviewer.

|`parallel`
|list
|required
|The agent steps that run at once (2 to 16). Each has the fields of an agent step; one without `id` is named `<group id>-1` and so on. Command steps, pull-request steps and groups cannot be listed.
|===

* In `run.json`, `--resume` and the estimate, the steps of a group are steps of their own.
* Validation refuses steps whose `writable` may overlap, or a `writable` that may overlap another step's `unchanged`.

[[workflow-reference-command-step]]
=== Command step

A step where ADK runs a command once. Anything but exit 0 stops the workflow there. No agent is started.

[cols="1,1,1,4",options="header"]
|===
|Field |Type |Required |Description

|`id`, `description`
|string
|optional
|As in an agent step.

|`command`
|string
|required
|The command to run (one line). No shell, as with `until.command`. `{item}` cannot be written. `{inputs.<name>}` can be written as an argument (not as the executable).

|`cwd`, `env`, `timeout_minutes`
|
|optional
|As the fields of the same name in `until`. Without `timeout_minutes`, the command may use the rest of the workflow's time (or run until it ends when there is no time limit).

|`writable`
|list of globs
|optional
|Which of the command's output files the pull-request step commits. ADK runs the command itself, so no write guard applies.
|===

[[workflow-reference-pr-step]]
=== Pull-request step

[cols="1,1,1,4",options="header"]
|===
|Field |Type |Required |Description

|`id`, `description`
|string
|optional
|As in an agent step.

|`pull_request`
|mapping
|required
|A step with this key is a pull-request step. At most one per workflow. It holds only `title`; without a title, write `pull_request: {}`.

|`pull_request.title`
|string
|optional
|The title of the PR and the commit. When omitted: `aidev: <description, or name>`.
|===

Each step's changes are already committed as a checkpoint when the step passes. This step makes a last commit of what is left inside the steps' `writable` and the run record, pushes the branch (`aidev/<name>`, or `aidev/<name>-<yyyymmddHHMM>` with `--dated`) and opens a PR (Azure DevOps; a PR already open for the branch has its description updated). When the branch has no change since the base, it does nothing. Untracked files matching the ADK's own list or `never_commit` are not committed, and the number left out goes into the log and the PR body (`## Left out`) (xref:workflow-reference-never-commit[never_commit]). A `--trial` run goes as far as the last commit and does neither the push nor the PR (xref:workflows-trial[Trying it before approval]).

[[workflow-reference-limits]]
=== limits

[cols="1,1,1,1,4",options="header"]
|===
|Field |Type |Required |Default |Description

|`limits.max_usd`
|number
|required
|
|The cost ceiling in USD. Once the cost the AI tool reported adds up to it, no further agent starts. An agent already running is not stopped, so a run can go past it by its last start. Only Claude Code reports cost. xref:cli-estimate[aidev estimate] gives an estimate. `aidev run workflow --max-usd` lowers it for one run (it cannot raise it).

|`limits.max_minutes`
|integer
|optional
|none
|A time limit for the whole workflow, in minutes, with no ceiling. Without it, time does not stop the run. Required when an agent runs on an AI tool other than Claude Code (no cost is reported, so `max_usd` cannot stop it). `aidev run workflow --max-minutes` lowers it for one run (or sets one for that run when the workflow has none).
|===

[[workflow-reference-agent]]
=== Agent definition (`.aidev/agents/<name>.md`)

A frontmatter and a Markdown body. `aidev create agent <name>` writes a template.

[source,markdown]
----
---
name: e2e-writer
description: Writes a Playwright test per screen. Started by the e2e-tests workflow
skills: [test-and-verify]
tools: Read, Grep, Glob, Edit, Write
mcp: []
model: inherit
---

# e2e-writer

(role, inputs and outputs, procedure, when to stop)
----

[cols="1,1,1,4",options="header"]
|===
|Field |Type |Required |Description

|`name`
|string
|recommended
|The same as the file name (letters, digits and `. _ -`). ADK looks agents up by file name.

|`description`
|string
|recommended
|When it is started and what it does. Shown by `aidev list agents` and read by workflow-creator when it picks agents.

|`skills`
|list (`[a, b]` or `a, b`)
|optional
|Skills whose body goes into its instructions. Looked up in the PKG, then in ADK; a skill found in neither stops the workflow at validation. A workflow's `agents:` can add more for that workflow only (xref:workflow-reference-agents[agents]).

|`tools`
|list
|optional
|The built-in tools it may use (`Read`, `Edit`, `Bash` and so on). When omitted, the tool's default set. Claude Code is started with these only, and the hook refuses any other.

|`mcp`
|list
|optional
|The MCP servers it may use (keys of the PKG's `.mcp.json`). When omitted, no MCP server is given. A name missing from `.mcp.json` stops the workflow before it starts.

|`subagents`
|list
|optional
|The subagents this agent may start with the `Agent` tool (names of `.aidev/agents/<name>.md`). When written, no other can be started; when omitted, whatever the AI tool offers can. With `tools`, include `Agent`. A subagent's `tools` and `mcp` must be within this agent's, and a subagent cannot have `subagents` of its own (xref:workflows-subagents[Naming the subagents an agent may start]).

|`model`
|string
|optional
|Write `inherit`. It is not used when a workflow starts the agent; the workflow's `model` and `aidev.yaml` decide. A subagent runs on its parent agent's model.
|===

* An agent with `tools` or `mcp` runs only with Claude Code (other AI tools cannot be limited to them, so the run stops before it starts).
* Do not give `Bash` to an agent that touches an external system. With `Bash` it can go out without MCP, however `mcp` is limited.
* Capabilities can be added per workflow with `agents:`, but no field changes them per step. Work in one workflow that needs different permissions gets a separate agent.
* Changing an agent changes every workflow that uses it.

ADK puts the body at the head of an agent step's instructions and adds the following after it. The body does not need to repeat them.

[cols="1,3",options="header"]
|===
|What ADK adds |Contents

|Workflow and Objective
|The workflow's name, `description` and `objective`

|Task for this run
|What `--task` says (as data)

|Inputs for this run
|The `--input` values (as data; they are already in place where `{inputs.<name>}` was written)

|Reports from the earlier steps
|The final reports of the earlier agent steps (the last 6000 characters of each)

|Notes of this run
|Where the notes directory is and which files it holds

|Step
|The step's `prompt`; with `for_each`, this target; on a retry, what failed last time

|Rules
|Where it may write (`writable`), what must not change (`unchanged`), not to commit, what to put in the final report

|Reference documents
|The paths listed in `references` in `aidev.yaml` (xref:configuration[aidev.yaml reference])
|===

The checking agent (`until.agent`) receives the step's `prompt`, the report of the step's agent, the list of changed files, where the diff file is, `until.prompt`, and the rule to end on a `VERDICT:` line.

[[workflow-reference-records]]
=== Run record (`runs/<id>/run.json`)

`aidev run workflow` writes it to `.aidev/workflows/<name>/runs/<id>/` in the run's worktree as the run goes (gitignored). The estimate (xref:cli-estimate[aidev estimate]), `--resume` and `aidev modify --from-run` read the `run.json` files of the checkout and of every run worktree together.

[cols="1,4",options="header"]
|===
|Field |Contents

|`runId`, `name`, `hash`
|The run's id (its start time), the workflow's name, the hash of `workflow.yaml` at the start

|`approvedRef`, `approvedSha`
|The ref approval was checked against (`origin/main` and so on) and its commit. Both `null` in a `--trial` run

|`trial`, `trialHash`
|`true` in a `--trial` run, with the hash (`sha256:…`) of the reviewed files (`workflow.yaml` and the agents and skills) when it started; a continued trial must still match it. `false` (no `trialHash`) in a run that is not a trial

|`startedAt`, `finishedAt`, `startedBy`
|When it started and finished, and the user name that ran it (for the record)

|`branch`, `worktree`, `baseSha`, `task`, `inputs`
|The branch it ran on (`aidev/<name>`, dated with `--dated`, `aidev/<name>.trial` with `--trial`), the path of the run's worktree, the commit it started from, what `--task` said, the `--input` values (`default` included; a `file: true` input is the path of the copy under `inputs/` in the run record)

|`steps`
|Per step: `id`, `kind`, `ok`, `attempts`, and the checkpoint commit made when it passed (`checkpoint`). An agent step also has a summary of its last result (`result`), the checking agent's report (`review`), the command output file (`log`) and the tool calls the agent was refused (`denied`: lines such as `Write src/x.ts`, up to 20); a `for_each` step has `items` per target (each with its own `checkpoint`; a target that failed under `on_failure: continue` has `failed: true` and `reason`) and the number that failed (`failed`). The pull-request step has the number left out as never committed (`leftOut`, per glob) and whether it pushed (`pushed`; `false` in a `--trial`)

|`calls`
|One entry per agent start: `step`, `role` (`agent`, or `until` for the checking agent), `agent`, `item` (the `for_each` target), `attempt`, `tool`, `model`, `ok`, `costUsd`, `durationMs`, and the number of refused tool calls (`denials`, only when there were any)

|`done`, `stopReason`
|Whether it finished, and why it stopped

|`agentRuns`, `costUsd`
|The number of agent starts and the total reported cost (including any `--resume`)

|`pr`, `resumes`
|The PR it opened (in a `--trial`, `{ ok: false, trial: true, reason, branch, description }`); when it was resumed and at which step
|===

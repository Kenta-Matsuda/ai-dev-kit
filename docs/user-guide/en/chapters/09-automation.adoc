[[automation]]
== Automation

There are three kinds of automation. In all of them, a human merges the pull request.

[[automation-ci]]
=== CI

Copy the Azure Pipelines examples from the kit's `pipelines/` into the PKG and change `AIDEV_KIT_URL` to the URL of your central kit. CI clones the kit and runs `node cli/bin/aidev.js` directly, so `aidev` does not need to be installed.

[%autowidth.stretch,options="header"]
|===
|File |Purpose

|`pipelines/azure-pipelines-check.yml`
|Runs `aidev check` on every PR. Make it a **required build validation** in the branch policy of `main`. Without it, an edit that removes the hooks could be merged.

|`pipelines/azure-pipelines-wiki.yml`
|Runs `aidev knowledge update --branch` on `main` daily at 18:00 UTC. It picks up what was merged without a Wiki, commits on the branch `aidev/wiki-<sha12>` and opens a PR. It publishes only when the prose is complete, so the pipeline needs the agent tool (`tools.agent`, Claude Code by default) and its credentials. Set the variables `AZURE_DEVOPS_PAT`, `ANTHROPIC_API_KEY`, `AIDEV_BOT_NAME` and `AIDEV_BOT_EMAIL`. It does nothing when the Wiki already describes the HEAD of `main`.
|===

When developers bring the Wiki to HEAD with every commit, this pipeline is a safety net.

The exit code of `aidev check` is the contract with CI.

[%autowidth.stretch,options="header"]
|===
|Exit code |Meaning

|0
|Consistent. Warnings (Wiki behind HEAD, prose pending, `main` moved ahead) still return 0; `--strict` turns them into 2.

|2
|The tool configuration record (`.aidev/materialized.json`) is missing, `aidev apply` conflict markers remain, or the kit's hooks are gone from `.claude/settings.json`. Files the team merely edited still return 0.

|3
|`.aidev/policy.yaml` is missing or broken.

|4
|The Wiki is missing or broken, or the lease of a publish to the tracking branch expired and was left behind.
|===

[[automation-workflow]]
=== aidev workflow — running approved scripts

Runs JavaScript written by the team, exactly as a human approved it, with limits on iterations, time and commands.

. Create the scaffold.
+
[source,bash]
----
aidev workflow new nightly-tests
----
+
This creates `workflow.yaml` (limits, budget, allowed commands) and `steps.js` (the logic) in `.aidev/workflows/nightly-tests/`.

. Edit both files and review them with `git diff`.

. Approve. The approval is recorded as a hash of the two files and becomes invalid if either one is edited.
+
[source,bash]
----
aidev workflow approve nightly-tests
----

. Run.
+
[source,bash]
----
aidev workflow run nightly-tests
----
+
If it stops at a limit, continue with `--resume`.

How to write `steps.js` is explained in the scaffold's comments. The limits are 10 iterations, 60 minutes and 3 identical failures; they cannot be raised.

`steps.js` can start a bundled agent with `ctx.agent(prompt)`. Which agent, tool and model it uses is set in the `agent:` block of `workflow.yaml` (`name` / `tool` / `model` / `timeout_ms`); anything left out follows `tools.agents.<name>` and `tools.agent` in `aidev.yaml`. Each run is cut off at the workflow's remaining time, and once the reported cost reaches `cost.max_usd` no further agent starts (only Claude Code reports cost).

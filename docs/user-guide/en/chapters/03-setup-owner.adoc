[[setup-owner]]
== Adopting aidev in a package

Adopt {project-name} in a PKG for the first time, and prepare the shared setup, the AI's write permissions and the description of the code for the AI, then hand them to the team. One person does this once per PKG. **This person decides what the AI is allowed to do and what it is asked to do in this PKG.** Developers do not decide.

This chapter is the one-time adoption. What you keep doing afterwards is in xref:maintain[Maintenance].

=== Prerequisites

* xref:install[Installing aidev] is done, and `aidev doctor` shows `✓` for `claude`
* A clone of the PKG with at least one commit and `origin` set
* For Azure DevOps, `AZURE_DEVOPS_PAT` is set
* Generating the Wiki takes time. Expect a few minutes to fifteen minutes per 20 generation targets

=== Procedure

. Create a working branch at the PKG root.
+
[source,bash]
----
cd <pkg>
git switch -c feature/ai-dev-kit
----

. Run `aidev init` and answer four questions. Enter accepts the default shown in `[ ]`.
+
[source,bash]
----
aidev init
----
+
[%autowidth.stretch,options="header"]
|===
|Question |How to answer

|1/4 tools
|Press Enter for `claude`. For several tools, write them comma-separated, such as `claude, copilot` (`claude`, `copilot`, `codex`, `kiro`). The team decides who uses which tool; the answer is kept in `aidev.yaml`.

|2/4 Wiki generation targets
|The paths you want explanation pages for (globs, comma-separated). `src/**`, `docs/**` and similar are suggested. The Wiki's research covers the whole PKG anyway, so list only the places you want pages for.

|3/4 secret paths
|Paths the AI must never read. Add the places where certificates or configuration live to the five defaults.

|4/4 hosting
|Inferred from the `origin` URL. For Azure DevOps, confirm organization / project / repository, then answer the branch the Wiki should follow (default `main`). This branch is also the reference for workflow approval.
|===
+
After the questions, the configuration files are written and a summary of the policy is shown with `Place this policy now? (y/N)`. `y` places the policy. `N` writes a candidate file that you approve in the next step. At the end, `next steps` lists the remaining steps (approving the policy, building the Wiki, committing, the PR). `aidev init` does not build the Wiki.
+
* `✗ N file(s) already exist here and differ from the kit templates` → `.claude/` or similar already contains files that differ from the kit templates. Save their contents somewhere, then run `aidev init --force`.
* `run "aidev init" at the repository root` → move to the root and run it there.

. Approve the policy (only if you answered `N` in step 2). Read the candidate and place it once you agree with it.
+
[source,bash]
----
cat .aidev/policy.candidate.yaml
aidev create policy --approve
----
+
See xref:permissions[Permissions and safety] for what the policy contains. The range of source the AI may write is not in the policy; it goes in the `writable` of each step of the workflows you create later.

. Build the Wiki. `--no-commit` leaves the result in the working tree so it is committed together with the setup in the next step. It takes time. If it stops part way, running the same command again resumes where it left off.
+
[source,bash]
----
aidev sync wiki --no-commit
----
+
[source,text]
----
ℹ running the knowledge-builder agent: 163 generation target(s) in 9 batch(es) of up to 20, after a survey run
✓ survey complete in 3m 12s ($0.4120)
ℹ batch 1/9: 20 target(s), src/api/auth.ts … src/api/users.ts
✓ batch 1/9 complete: 20/20 in 4m 2s ($0.5533)
...
✓ knowledge-builder completed 163/163 queued generation target(s) ($4.9012)
----
+
It is done when the last line is `✓ knowledge-builder completed N/N`. If it stops with anything else, check the following and run the same command again.
+
* `⚠ the knowledge-builder agent did not run` → Claude Code was not found. Fix the `claude` line of `aidev doctor`.
* `✗ … ran out of time` / `⚠ … partial Wiki progress` / Ctrl-C → the finished part is saved. Run it again.
+
The Wiki is complete when the second line of `aidev check` is `✅`.

. Commit and open a PR.
+
[source,bash]
----
aidev check
git add aidev.yaml .aidev .claude CLAUDE.md
git commit -m "chore: adopt ai-dev-kit"
git push -u origin feature/ai-dev-kit
----
+
Make sure `aidev check` says `✓ environment is consistent.` before you push. `.aidev/.gitignore` excludes the temporary files, so `git add .aidev` adds nothing you do not want. If you also chose `copilot` / `codex` / `kiro`, `git add` that tool's configuration files too (`.github/`, `AGENTS.md`, `.kiro/`; see xref:files-and-state[Files in the PKG]).

. Have the PR reviewed and merge it into `main`. The reviewer looks at the setup (`aidev.yaml`, the policy) and the contents of the Wiki. After the merge, Developers can join with xref:setup-member[Getting started].

[[setup-owner-guardrails]]
=== Required configuration

Both of the following are configured as part of adoption. Without them, a change that widens what the AI may write can land without review.

[[maintain-branch-policy]]
==== Branch policy configuration

A workflow is approved by being merged into `main`, so **the branch policy of `main` is what approval really is.** Set up the following.

* Make the `aidev check` pipeline a required build validation
* Add required reviewers for `.aidev/workflows/**`, `.aidev/agents/**`, `.aidev/skills/**`, `.aidev/policy.yaml` and `aidev.yaml`
* Forbid direct pushes to `main`

Without this, a change that widens what the AI may write, or one that removes the write limits, can land without review.

[[maintain-ci]]
==== CI configuration

CI does two things: it stops the merge of a PR with `aidev check`, and at night it brings the Wiki of `main` up to date. In both cases a human does the merging.

Copy the Azure Pipelines examples from the kit's `pipelines/` into the PKG and change `AIDEV_KIT_URL` to the URL of your central kit. CI clones the kit and runs `node cli/bin/aidev.js` directly, so `aidev` does not need to be installed.

[%autowidth.stretch,options="header"]
|===
|File |Purpose

|`pipelines/azure-pipelines-check.yml`
|Runs `aidev check` on every PR. Make it a **required build validation** in the branch policy of `main`. Without it, an edit that removes the write limits could be merged.

|`pipelines/azure-pipelines-wiki.yml`
|Runs `aidev sync wiki --branch` on `main` daily at 18:00 UTC. It picks up what was merged without a Wiki, commits on the branch `aidev/wiki-<sha12>` and opens a PR. It publishes only when the prose is complete, so the pipeline needs the agent tool (`tools.agent`, Claude Code by default) and its credentials. Set the variables `AZURE_DEVOPS_PAT`, `ANTHROPIC_API_KEY`, `AIDEV_BOT_NAME` and `AIDEV_BOT_EMAIL`. It does nothing when the Wiki already describes the HEAD of `main`.
|===

When Developers bring the Wiki to HEAD with every commit, the nightly pipeline is a safety net.

The exit code of `aidev check` is the contract with CI; see xref:cli-exit-codes[Command Reference: Exit codes] for what each code means.

[[setup-owner-after]]
=== Post-adoption tasks

With the above in place, work through these in order. The Engineering Manager does all of them and turns them into PRs.

[%autowidth.stretch,options="header"]
|===
|Task |Method

|Tell the Developers
|→ xref:setup-member[Getting started]

|Define the work handed to the AI
|Describe what you want, create the processing workflow, check for each step where it may write and which tools the agent can use, and submit it. Once merged, Developers can run it. → xref:workflows[Delegating work to the AI]

|Write out the development conventions of this PKG
|Create a processing workflow that writes this PKG's conventions, with evidence, from the Wiki and the source; submit it and run it after the merge. → xref:workflows-define[Defining a workflow]

|Run lint / test after the AI edits files
|Write them in `quality_gates` of `aidev.yaml`. → xref:configuration[aidev.yaml reference]
|===

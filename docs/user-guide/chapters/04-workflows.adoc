[[workflows]]
== AI への作業委譲（workflow）

AI に開発作業を任せる入口は workflow だけです。「何をさせるか」「どこまで書き換えてよいか」を事前に決めてレビューし、承認したものだけを実行します。

役割ごとの分担です。

[cols="1,3,2",options="header"]
|===
|役割 |作業 |参照先

|Engineering Manager
|workflow を定義し、手元で試してから、レビューへ提出する
|xref:workflows-define[workflow の定義]、xref:workflows-trial[承認の前に試す]、xref:workflows-submit[提出する]

|レビューする人
|定義をレビューして `main` に入れる。**取り込むことが承認です。**
|xref:review-workflow-def[workflow 定義の PR]

|Developer
|承認済みの workflow を実行し、成果物をレビューへ提出する
|xref:workflows-run[workflow の実行]
|===

**実行した Developer は成果物に責任を負いません。** 責任は、定義をレビューした人と、成果物の PR をレビューする人にあります。

ループ・再試行・コマンド実行・コミット・PR 作成といった実行の仕組みは ADK が持ち、定義には書けません。定義で表せないことは ADK への要望です。

[[workflows-flow]]
=== 全体フロー

.定義 → 試す → 承認 → 実行。push と PR を伴う実行ができるのは承認済みの定義だけ
[mermaid]
----
flowchart LR
  subgraph O["Engineering Manager"]
    direction TB
    n["workflow を作る"]
    d["内容を確認する"]
    t["--trial で試す"]
    s["レビューへ提出"]
    n --> d --> t --> s
  end
  subgraph R["レビューする人"]
    direction TB
    p1["定義を読む"]
    m1["取り込む = 承認"]
    p2["成果物を読む"]
    m2["取り込む"]
    p1 --> m1
    p2 --> m2
  end
  subgraph M["Developer"]
    direction TB
    f["最新の承認状態を取得"]
    r["workflow を実行"]
    pr["成果物の PR"]
    f --> r --> pr
  end
  s -- "PR" --> p1
  m1 -- "origin/main" --> f
  pr --> p2
----

[[workflows-define]]
=== workflow の定義（Engineering Manager）

雛形を作ります。どちらも `.aidev/workflows/<name>/workflow.yaml` を書くだけで、実行はしません。

[source,bash]
----
aidev create workflow write-tests                          # 空の雛形
aidev create workflow write-tests --describe "指定した対象のテストを既存の書き方で書き、通してから PR にする"
----

`--describe` は workflow-creator agent を起動して YAML を書かせます。足りない agent・skill があれば、workflow-creator が agents-creator をサブエージェントとして起動し、`.aidev/agents/`・`.aidev/skills/` に書かせます。外部システム（Work Item、チケット、DB）が要るときは、PKG の `.mcp.json` に足す MCP server の定義案を報告に書きます（追加は人が行います）。書いたあと CLI が検証し、結果と次の手順を表示します。

ADK が同梱する **標準 workflow** から始めることもできます。`aidev create workflow e2e-tests --from playwright-tests` は、テスト仕様書から Playwright のテストを書く workflow と、その agent・skill をこの PKG に複製します（xref:workflows-standard[標準 workflow から作る]）。

定義は 2 か所に分かれます。

[cols="1,3,3",options="header"]
|===
|書く場所 |決めること |例

|`workflow.yaml`（**制約**）
|ステップの順番、各ステップの agent、そのステップが書いてよい場所、終わりの判定、上限
|調査ステップは何も書けない。実装ステップは `tests/**` だけ書ける

|agent の frontmatter（**能力**）
|その agent が使える skill・ツール・MCP server・サブエージェント
|test-writer は test-and-verify の手順を持ち、Read・Edit・Write だけを使う
|===

同じ agent に仕事ごとに違う権限を持たせたいときは、agent を分けます（読むだけの `ticket-reader` と、更新する `ticket-updater` など）。ある workflow でだけ能力を足したいときは、workflow.yaml の `agents:` に書きます（`skills`・`mcp`・`subagents` は追加、`tools` は置き換え。xref:workflows-agents-skills[agent と skill]）。

雛形を PKG に合わせて編集します。多くの場合、変えるのは各ステップの `writable`（そのステップが書いてよい場所）と `until.command`（この PKG のテストコマンド）です。

[source,yaml]
----
name: write-tests                  # ディレクトリ名と一致。小文字・数字・ハイフン
description: 指定した対象のテストを既存の書き方で書き、通してから PR を作る

objective: |                       # すべての agent step に渡す目的（必須）
  Add tests for the target named in --task. Follow the way existing tests are
  written and run. Do not change the code under test.

# tool: claude                     # 任意。aidev.yaml の tools.default にあるもの。既定は tools.agent
# model: sonnet                    # 任意。"" でツールの既定に任せる

steps:                             # 上から順に実行する
  - id: survey
    description: 既存テストの書き方を調べ、足りないテストを洗い出す   # 任意。レビューする人向けの説明
    agent: test-investigator       # .aidev/agents/<name>.md（この PKG の agent）→ kit 同梱の順に探す
    writable: []                   # 必須。このステップは何も書けない
    prompt: テストの書き方と実行方法を調べ、未カバーの振る舞いを最終報告に列挙する。
  - id: write
    description: 洗い出したテストを書き、通るまで直す
    agent: test-writer
    writable: [tests/**]           # このステップが書けるのは tests/ の中だけ
    prompt: 前のステップが列挙したテストを既存の書き方で書き、実行する。
    until:                         # 終わりの判定。満たすまで agent を繰り返す
      command: npm test            # exit 0 になること（shell を通さない）
      max_retries: 4               # 不合格のとき agent をやり直す回数（既定 3、上限 10）
  - id: pr
    pull_request:                  # 各ステップの writable の変更を commit → push → PR
      title: "test: 足りないテストを追加"   # 任意

limits:                            # 実行を止める条件
  max_usd: 8                       # 必須。報告された費用がこれに達したら次の agent を起動しない
  max_minutes: 45                  # 任意。全体の時間の上限。書かなければ時間では止めない
----

[%autowidth.stretch,options="header"]
|===
|項目 |意味

|`objective`
|すべての agent step の指示の先頭に入る目的。必須です。

|`tool` / `model`
|省略すると `aidev.yaml` の `tools.agent` / `tools.agent_model`（agent ごとの `tools.agents.<name>` があればそれ）に従います。`tool` は `tools.default` にあるものだけです。

|`steps`
|上から順に実行します。1 つの step は agent step・command step・pull-request step・parallel グループのどれか 1 つで、種類は `agent`・`command`・`pull_request`・`parallel` のどのキーを持つかで決まります。どの種類にも、レビューする人向けの `description`（任意）を書けます。

|`agents`
|任意。この workflow でだけ agent に足す能力（`skills`・`mcp`・`subagents` は追加、`tools` は置き換え）（xref:workflows-agents-skills[agent と skill]、xref:workflow-reference-agents[agents]）。

|`inputs`
|任意。実行のたびに `--input <name>=<値>` で受け取る値の宣言。定義の `{inputs.<name>}` と書いた場所に入ります（xref:workflows-inputs[実行ごとに変わる値を受け取る]）。

|`env_required`
|任意。実行する人の shell に設定しておく環境変数（パスワード、トークン）の宣言。無ければ何も始めません。値は agent とコマンドの環境に届くだけで、どこにも記録されません（xref:workflows-env-required[認証情報は環境変数で受け取る]）。

|`provide`
|任意。git が無視するファイルのうち、手元のチェックアウトから実行の worktree にコピーするもの（glob）（xref:workflows-provide[worktree に無いファイルを用意する]）。

|`never_commit`
|任意。ADK の既定の一覧に加えて、実行が決してコミットしないパス（glob）（xref:workflows-never-commit[決してコミットしないもの]）。

|agent step
|`agent`・`writable`・`prompt` が必須です。`until` を書くと、それを満たすまで agent を繰り返します（やり直しは `until.max_retries` 回まで）。`timeout_minutes`（agent 1 回の時間の上限）は任意です。

|`until`
|そのステップの終わりの判定です。`command`（exit 0 になること）と `agent` + `prompt`（その agent が合格と判定すること）のどちらか、または両方を書きます。両方あるときはコマンドが通ってから agent が確認します。`command` は list にすると上から順に実行します。コマンドの実行の仕方は `cwd`・`env`・`timeout_minutes` で決めます（xref:workflows-commands[コマンドの書き方]）。`max_retries` は、不合格のとき agent をやり直す回数です（既定 3、上限 10。0 ならやり直しません）。`until` が無いステップはやり直しません。agent での判定は xref:workflows-until-agent[agent のレビューで終わりを判定する] を参照してください。

|`writable`
|そのステップの agent が書けるパス（glob）。**PKG のソースを AI が書けるのは、承認済み workflow の、いま動いているステップのこの範囲だけです。** `protected`（`.claude/**`、`.aidev/policy.yaml` など）と `secrets_paths` は書けません。`[]` なら何も書けません（調査だけのステップ）。

|`unchanged`
|任意。そのステップが変えてはいけないパス（glob）。`writable` の中にあっても書けず、ステップの前後で内容が変わっていれば不合格です（xref:workflows-unchanged[変えてはいけない場所を決める]）。

|`for_each`
|任意。対象の一覧（`from`）の 1 件ごとに、agent を新しく起動して繰り返します。`max_items` は必須です（xref:workflows-for-each[対象ごとに繰り返す]）。`parallel` で同時に動かす件数を決められます（xref:workflows-parallel[並列に動かす]）。

|parallel グループ
|`parallel:` に並べた agent step を同時に起動し、全部終わってから次へ進みます。`writable` どうしが重なり得ると拒否されます（xref:workflows-parallel[並列に動かす]）。

|command step
|`command` を空白で分割して shell 無しで実行します。exit 0 以外で workflow は失敗します。`cwd`・`env`・`timeout_minutes` は任意です。コマンドが作るファイルを PR に入れるときは、その場所を `writable` に書きます（ADK が実行するコマンドなので、書き込みの検問はかかりません）。

|`pull_request`
|各ステップの変更（ステップごとのチェックポイントのコミット）と、残った `writable` の範囲の変更をまとめて push し、PR を作ります。`title` は任意で、書かないときは `pull_request: {}` と書きます。1 つまでです。

|`limits.max_usd`
|必須。ツールが報告した費用（Claude Code のみ）の合計がこれに達すると、次の agent を起動せず止まります。

|`limits.max_minutes`
|任意。workflow 全体の時間の上限（分）。書かなければ、時間では止めません（費用の上限と再試行の上限で止まります）。Claude Code 以外の AI ツールは費用を報告しないので、その場合は必須です。
|===

上の表にない項目を書くと、検証で拒否されます。各項目の型・既定値・書ける値の一覧は xref:workflow-reference[workflow 定義リファレンス] にあります。

実行を止める仕組みは次のとおりです。費用の上限は省略できず、再試行回数と件数の上限は上げられません。

* 費用の上限（`limits.max_usd`、必須）
* step ごとのやり直しの回数（`until.max_retries`、10 回まで）と、同じ失敗の検知（`until` の結果が 2 回続けて同じなら停止）
* `for_each` の件数（`max_items`、10000 件まで）
* agent 1 回の起動とコマンド 1 つの時間（`timeout_minutes`、240 分まで。agent の既定は 30 分）。止まって動かない agent やコマンドを打ち切るためのものです
* 全体の時間（`limits.max_minutes`）。任意です

大きな仕事を無人で走らせる書き方は xref:workflows-unattended[人が介入せずに大きな仕事を走らせる] にあります。

[[workflows-standard]]
==== 標準 workflow から作る（`--from`）

ADK は、よくある仕事の workflow を **標準 workflow** として同梱しています。`aidev list workflows` の末尾に一覧が出ます。

[cols="1,3",options="header"]
|===
|標準 workflow |内容

|`playwright-tests`
|テスト仕様書（CSV・Markdown・テキスト。1 行か 1 節が 1 ケース）の 1 ケースごとに Playwright のテストを書き、対象環境に対して実行して通るまで直し、全件通ったら agent が仕様と突き合わせてレビューし、PR にする。ケースは batch に分けて同時に進める
|===

標準 workflow は ADK の中では動きません。`--from` で PKG に複製して使います。

[source,bash]
----
aidev create workflow e2e-tests --from playwright-tests
----

[source,text]
----
aidev create workflow e2e-tests
✓ wrote .aidev/workflows/e2e-tests/workflow.yaml
✓ wrote .aidev/agents/playwright-test-planner.md
✓ wrote .aidev/agents/playwright-test-reviewer.md
✓ wrote .aidev/agents/playwright-test-writer.md
✓ wrote .aidev/skills/playwright-testing/SKILL.md
    from the kit's standard workflow playwright-tests: テスト仕様書（CSV など）の 1 ケースごとに Playwright のテストを書き、…
    the files are this PKG's now: edit what differs here (the paths the steps write, the commands they run), then submit them for review
    inputs: spec (a file, --input only), base_url (required), test_user (required), batch_size (default 10)
    set this PKG's values once in aidev.yaml (--input overrides them per run):
      workflows:
        e2e-tests:
          inputs:
            base_url: <テスト対象環境の URL（ルート。例 https://staging.example.com）>
            test_user: <テストユーザーのログイン ID（ユーザー名かメールアドレス）>
            batch_size: 10
    before a run, export in the shell: E2E_PASSWORD (テストユーザーのパスワード（実行する人が export する。ファイルには書かない）)
----

* 複製されるのは `workflow.yaml`（`name:` は付けた名前に書き換わる）と、それが使う agent（`.aidev/agents/`）・skill（`.aidev/skills/`）です。複製した時点で **この PKG のファイル** になります。他の workflow と同じく `--trial` で試し、`aidev submit workflow` で PR にし、マージで承認します。実行時に ADK 側のファイルを参照することはありません。
* 同じ agent・skill が既にあって内容が同じなら残し（`kept`）、違えば `--force` が無いと止まります。別の名前でもう 1 つ複製する（`e2e-staging` と `e2e-prod`）ときは agent を共有します。ADK を更新して新しい版の標準 workflow を取り込むには、もう一度 `--from … --force` で複製し、差分をレビューします。
* PKG ごとに違うものは 2 種類に分かれます。**定義で違うもの**（テストを置くディレクトリ、依存を入れるコマンド、同時に進める batch の数、費用の上限）は複製した `workflow.yaml` を直します。**値で違うもの**（テスト対象環境の URL、テストユーザー）は定義を変えず、`aidev.yaml` の `workflows.<name>.inputs` に書くか、実行時に `--input` で渡します（xref:workflows-inputs[実行ごとに変わる値を受け取る]）。**認証情報**（テストユーザーのパスワード）は定義の `env_required:` が名前を宣言し、実行する人が shell の環境変数で渡します。ファイルには書きません（xref:workflows-env-required[認証情報は環境変数で受け取る]）。

`playwright-tests` の流れと前提です。

. `deps`（command step）: `npm ci` で依存を実行の worktree に入れる。pnpm / yarn の PKG、テストが別ディレクトリにある PKG は、この command と `cwd` を直す
. `playwright`（command step）: `npx playwright --version`。Playwright（`@playwright/test` と `playwright.config.*`）が PKG に無ければここで止まる
. `plan`（agent step、何も書かない）: 仕様書を読み、ケースを画面・機能ごとに `batch_size` 以下の batch に分けて、実行の notes に置く
. `scaffold`（agent step）: `tests/e2e/support/` に共通の helper（環境変数の読み取り、ログイン）、`tests/e2e/smoke/` に smoke test を書き、対象環境に対して通す。URL・ユーザー・パスワード・ログイン画面のどれかが違えばここで分かる
. `generate`（agent step、`for_each`、既定で 4 batch 同時）: batch ごとに `tests/e2e/cases/<batch>/<ケース ID>.spec.ts` を書き、その batch のテストが通るまで直す（3 回まで）。通らなかった batch は戻して次へ進む（`on_failure: continue`）
. `review`（agent step）: 全体を実行し、通らないものと重複した helper を直す。確認役の `playwright-test-reviewer` が仕様のケースごとに spec ファイルと検証の内容を突き合わせ、足りなければ指摘を添えて差し戻す（2 回まで）
. `pr`: PR を作る。失敗して残った batch のケースは PR 本文の「Targets left out」に出る

* 前提: Playwright が PKG に入っていて、`playwright.config.*` の `testDir` が `tests/e2e/` を含むこと（別の場所に置くなら、複製した YAML のパスを直す）。`webServer` でローカルのサーバを起動する設定は、対象環境（`base_url`）に対するこの workflow では外すか、`for_each.parallel` を 1 にする（同時に起動すると port がぶつかる）。
* テストは `E2E_BASE_URL`・`E2E_USER`・`E2E_PASSWORD` を `process.env` から読みます（各 agent step の `env` が `base_url`・`test_user` を agent と `until` のコマンドに渡し、`E2E_PASSWORD` は shell から届く）。パスワードはテストにもログにも書かれません。
* 費用の上限（`limits.max_usd: 50`）はケース数に合わせて上げます。達すると止まり、`--resume` で続けられます。

[source,bash]
----
export E2E_PASSWORD='…'                                                          # 実行する人の shell にだけ
aidev run workflow e2e-tests --trial --input spec=~/specs/login.csv --max-usd 5     # まず少ないケースで試す
aidev run workflow e2e-tests --input spec=~/specs/all-cases.csv
----

[[workflows-commands]]
==== コマンドの書き方

`until.command` と `command` は shell を通しません。引用符・パイプ・リダイレクト・変数は書けません。代わりに次の項目を使います。

[source,yaml]
----
  - id: write
    agent: e2e-writer
    writable: [e2e/tests/**]
    prompt: 前のステップが挙げた画面の IT テストを書く。
    until:
      command:                     # list は上から順に実行する。最初に失敗したところで止まる
        - npm ci
        - npx playwright test
      cwd: e2e                     # 実行するディレクトリ（PKG の中）。省略すると PKG のルート
      env:                         # コマンドに渡す環境変数（固定の値）
        CI: 1
        BASE_URL: http://localhost:3000
      timeout_minutes: 15          # コマンド 1 つの時間の上限（分。最大 240）
----

[%autowidth.stretch,options="header"]
|===
|項目 |意味

|`command` の list
|`until` だけで書けます。`&&` の代わりです。command step で順に実行したいときは、command step を並べます。

|`cwd`
|コマンドを実行するディレクトリです。PKG の外（`..` や絶対パス）は書けません。

|`env`
|コマンドに渡す環境変数です。値は定義に書いた固定の文字列で、PR でレビューされます。**秘密情報は書きません**（パスワードは `env_required` で名前を宣言し、shell から受け取ります。xref:workflows-env-required[認証情報は環境変数で受け取る]）。`AIDEV_` か `GIT_CONFIG` で始まる名前は書けません。agent step 自体にも `env` を書けます。その値は agent の環境と `until` のコマンドの両方に入るので、agent が自分で実行するテストと ADK の判定が同じ設定で動きます（`until.env` はその上に重なります）。

|`timeout_minutes`
|コマンド 1 つの時間の上限（分）です。省略すると、workflow の時間の上限まで（それも無ければ終わるまで）待ちます。
|===

コマンドの出力は全文を実行記録の `logs/` に残します。`until` のコマンドが失敗すると、出力の末尾と、その file の場所を agent に渡します。

[[workflows-handoff]]
==== ステップの間で結果を渡す

各 agent step は、新しいプロセスとして起動されます。前のステップの会話は残りません。結果を渡す方法は 2 つあります。

* **最終報告** — 前の agent step の最終報告を、ADK が後の agent step の指示に入れます（長い報告は末尾 6000 文字）。調査ステップでは、次のステップが使う結果を最終報告に書くよう `prompt` で頼みます。
* **notes ディレクトリ** — 計画や対象ファイルの一覧のように、長いものや正確に渡したいものは file に書かせます。場所は実行ごとの `.aidev/workflows/<name>/runs/<id>/notes/`（実行の worktree の中）で、ADK が各 agent step の指示に入れます。`writable: []` のステップも書けます。確認役の agent は読むだけです。コミットはされません。

[source,yaml]
----
  - id: plan
    agent: upgrade-planner
    writable: []
    prompt: 変更が要る箇所を調べ、対象の一覧を notes ディレクトリの targets.md に書く。
  - id: migrate
    agent: upgrader
    writable: [src/**, package.json, package-lock.json]
    prompt: notes ディレクトリの targets.md を読み、上から順に移行する。
----

[[workflows-for-each]]
==== 対象ごとに繰り返す

画面ごとにテストを書く、module ごとに移行する、のように対象が多い仕事は、1 件ずつに分けます。1 回の起動で全部をやらせると、後の対象ほど質が落ち、1 件の失敗でステップ全体をやり直すことになります。

[source,yaml]
----
  - id: plan
    agent: e2e-planner
    writable: []
    prompt: IT テストが要る画面を調べ、notes ディレクトリの targets.txt に 1 行 1 件で書く。
  - id: write
    agent: e2e-writer
    writable: [e2e/tests/**]
    for_each:
      from: targets.txt            # notes ディレクトリの file。前のステップが書く
      max_items: 20                # 必須。1 回の実行で扱う件数の上限（最大 10000）
    prompt: 画面 {item} の IT テストを e2e/tests/{item}.spec.ts に書く。
    until:
      command: npx playwright test tests/{item}.spec.ts   # この件だけを判定する
      cwd: e2e
      max_retries: 3
----

* 一覧は ADK が読みます。1 行が 1 件で、空行と `#` で始まる行は飛ばします。同じ行が 2 回あれば 1 件です。
* `{item}` は `prompt`、`writable`、`until.command`、`until.prompt` に書けます。`prompt` には必須です。`unchanged` には書けません。`writable` に書くと、その件の agent はその件のパスにだけ書けます（xref:workflows-parallel[並列に動かす]）。
* 1 件ごとに agent を新しく起動します。`until` とやり直しの回数も 1 件ごとです。時間と費用の上限は実行全体で数えます。
* 1 件が失敗すると、そこで止まります。通った件はそのまま残り、`--resume` は止まった件から続けます（xref:workflows-resume[止まった実行を続ける]）。
* `for_each` に `on_failure: continue` を書くと、失敗した件の変更を戻して次の件へ進みます。戻すのは、そのステップの `writable` の中で、その件の間に変わったファイルです。失敗した件と理由は `run.json`、後のステップへの報告、PR 本文に並びます。全件が失敗したときは止まります。費用と時間の上限に達したときは、`continue` でも止まります。
* 後のステップには、件ごとの結果をまとめた報告が 1 つ渡ります。

1 件に書けるのは、英数字と `. _ / @ -` だけの 1 語です（200 文字まで）。空白、先頭の `-`、`..` を含む行があると、ADK は agent を起動する前に止まります。件はコマンドの引数になるので、オプションや別の場所を指す文字列を受け付けないためです。一覧を書くステップの `prompt` に、この書き方を書いておきます。

[[workflows-parallel]]
==== 並列に動かす

agent を同時に動かす書き方は 2 つあります。どちらも同じ作業ツリーで動くので、**同時に動く agent が同じファイルを書けない** ことを、ADK が検証と hook で確かめます。

**対象ごとの繰り返しを並列にする**（`for_each.parallel`）。`writable` のパスをすべて `{item}` を含む形で書きます。各件の agent は自分の件のパスにしか書けず、`on_failure: continue` で戻すのもその件のパスだけです。

[source,yaml]
----
  - id: write
    agent: e2e-writer
    writable: [e2e/tests/{item}.spec.ts]   # 件ごとのパス。parallel には必須
    for_each:
      from: targets.txt
      max_items: 200
      parallel: 4                          # 同時に 4 件まで（最大 16。既定 1）
      on_failure: continue
    prompt: 画面 {item} の IT テストを e2e/tests/{item}.spec.ts に書く。
    until:
      command: npx playwright test tests/{item}.spec.ts
      cwd: e2e
----

**違うステップを同時に動かす**（`parallel:` グループ）。グループに並べた agent step が一緒に始まり、すべて終わってから次のステップへ進みます。

[source,yaml]
----
  - id: build
    description: API と画面を同時に作る
    parallel:
      - id: api
        agent: api-writer
        writable: [api/**]
        prompt: 計画どおりに API を実装する。
      - id: web
        agent: web-writer
        writable: [web/**]
        prompt: 計画どおりに画面を実装する。
  - id: integrate
    agent: integrator
    writable: [api/**, web/**]
    prompt: 2 つをつなぐ。
----

* グループに入れられるのは agent step だけです（2〜16 個）。各ステップは `for_each` や `until` を持てます。
* グループのステップどうしで、`writable` が重なり得るとき、また一方の `writable` が他方の `unchanged` と重なり得るときは、検証で拒否されます。重なりは固定部分（`*` や `{item}` より前）で判定するので、`src/**` と `src/a.ts` は重なり、`src/a.ts` と `src/b.ts` は重なりません。
* グループのステップは互いの報告を読めません。後のステップには全員の報告が渡ります。
* 1 つが失敗しても、動いている他のステップは終わるまで動きます（新しい件は始めません）。その後、実行は止まります。`--resume` は終わっていないステップだけをやり直します。
* `until.command` も同時に動きます。同じポートやファイルを使うテストは、同時に動かすと互いに邪魔をします。
* 費用の上限は、同時に動く agent の数だけ超えることがあります（上限に達した時点で動いている agent は止めないため）。

[[workflows-unchanged]]
==== 変えてはいけない場所を決める

`until` は「コマンドが成功すること」しか見ません。agent は、コードを直す代わりに判定のほうを弱めても、`until` を通せます。落ちるテストを消す、期待値を書き換える、test runner の設定を緩める、などです。弱められては困るパスを `unchanged` に書きます。

[source,yaml]
----
  - id: migrate
    agent: upgrader
    writable: [src/**, tests/**, package.json, package-lock.json]
    unchanged: [tests/**]          # 既存のテストは変えさせない
    prompt: notes ディレクトリの targets.md を読み、上から順に移行する。
    until:
      command: npx vitest run      # package.json の script ではなく、test runner を直接呼ぶ
----

* `unchanged` のパスは、`writable` の中にあっても agent は書けません（hook が拒否します）。
* ADK はステップを始めたときの状態を覚えておき、試行のたびに比べます。変わっていれば不合格で、`until` があれば、変わったパスを添えて agent をやり直させます（`until.max_retries` 回まで）。`until` が無いステップは、そこで不合格です（`for_each` ならその件が不合格）。コマンドや `Bash` が変えた場合も検出します。
* 同じパスが 2 回続けて変わっていれば止まります。元に戻してから `--resume` します。
* 前のステップが変えた内容は、そのステップの「始めたときの状態」に含まれます。テストを書くステップの後に、`unchanged: [tests/**]` の実装ステップを置けます。
* gitignore されたファイルは比べません。

検出できるのはファイル単位です。`writable` に残したファイルの中の変更（新しく書いたテストの `test.skip`、`package.json` の `scripts` の書き換え）は検出できません。次の 2 つで補います。

* `until.command` は `npm test` ではなく、test runner を直接呼びます（`package.json` が `writable` だと、`scripts.test` を書き換えられるためです）。
* `until` に確認役の agent を足し、`until.prompt` に「skip したテストや空のテストが無いこと」と書きます（xref:workflows-until-agent[agent のレビューで終わりを判定する]）。

[[workflows-inputs]]
==== 実行ごとに変わる値を受け取る（`inputs` と `--input`）

テスト仕様書のパス、対象の画面、使うブラウザのように、実行のたびに変わる値を `prompt` に書き換えていると、実行のたびに定義が変わり、承認をやり直すことになります。`--task` は agent に「データ」として渡す自由な文章で、コマンドには入りません。定義の決まった場所に入れる値は `inputs:` に宣言し、実行する人が `--input <name>=<値>` で渡します。

[source,yaml]
----
inputs:
  spec:
    description: the test specification to work from   # 実行する人、--dry-run、PR 本文に出る説明
    file: true          # この端末のどこかにあるファイル。実行はそのコピーを受け取る
  screen:
    description: the screen to cover
    pattern: '[a-z0-9-]+'   # 引用符で囲む（裸の [ は YAML の list になる）
  browser:
    default: chromium
    pattern: '[a-z]+'

objective: |
  Write the IT tests the specification {inputs.spec} describes for the screen {inputs.screen}.

steps:
  - id: write
    agent: e2e-writer
    writable: [e2e/tests/**]
    prompt: Read {inputs.spec} and write the tests for {inputs.screen}.
    until:
      command: npx playwright test tests/{inputs.screen}.spec.ts --project {inputs.browser}
      cwd: e2e
----

* 宣言に書けるのは `description`・`default`・`pattern`・`path`・`file` です。`default` の無い入力は必須です（`required` という項目はありません）。`path` と `file` は同時に書けず、`file` の入力に `default` は書けません。名前は英小文字で始まる英小文字・数字・`_`・`-`、32 文字までです。
* `{inputs.<name>}` を書けるのは、`objective`、agent step の `prompt`、`until.prompt`、`until.command`、command step の `command`、`env` の値（step と `until`）です。それ以外（`description`、step の `description`、`pull_request.title`、`writable`、`unchanged`、`cwd`、`for_each.from`）に書くと検証で拒否されます。コマンドの実行ファイル（先頭の語）にはできません。宣言していない名前を書くと検証で拒否されます。
* 値は実行の前に定義へ書き込まれ、`{item}` はその後で件ごとに置き換わります。値そのものはテンプレートではないので、`{` と `}` を含められません。
* 値は 1 行、1000 文字まで、制御文字なしで、`pattern` があれば値全体がそれに一致すること（ADK は `^(?:…)$` で囲みます）。`default` も検証のときに同じ規則で確かめます。
* **コマンドに届く入力**（`until.command`、command step の `command`、`env` の値に書いたもの）は、`pattern`、`path: true`、`file: true` のどれかが必須です。その値はさらに固定の規則 `^[A-Za-z0-9._@][A-Za-z0-9._/@:=+-]{0,999}$`（`..` のセグメントを含まない）に収まる 1 語でなければなりません。空白や先頭の `-` を含む値はオプションや別の場所を指せるため、`for_each` の件と同じ考え方です。`pattern` はこれを狭めることはできても、広げることはできません。
* `path: true` は PKG 内の相対パスです（`/` やドライブ文字で始まるもの、`..` を含むものは不可）。テキストでなければなりません（`.xlsx`・`.docx`・`.pdf`・画像などは `the AI tools read text; export … to Markdown, CSV or text first and pass that file` と拒否されます）。そのパスは実行の worktree に届くものでなければなりません。HEAD にコミット済みか、git が無視していて `provide` の glob に一致するかのどちらかです。`--dry-run` と実行は始める前にこれを判定し、`is not committed; a run starts from HEAD (commit it, or declare the input with file: true and pass the file)` または `is ignored by git and no provide: entry copies it into the run (add one, or pass it as a file input)` と表示して止まります。`provide` がコピーした後、そのパスが worktree にあることも確かめます。
* `file: true` はこの端末のどこかにあるファイルのパスです（絶対パスか、シェルのカレントディレクトリからの相対パス）。存在するファイルで、テキストであること（拡張子の規則は `path` と同じ）。ADK は実行の worktree の `.aidev/workflows/<name>/runs/<id>/inputs/<name><拡張子>` にコピーし、`{inputs.<name>}` はその PKG 内の相対パスになります（`runs/` の中なので gitignore 済み。agent は読めますが、コミットされません）。`run.json` にはそのパスが残り、ログに `input <name>: copied <元> to <先>` と書きます。`--resume` はそのコピーをそのまま使います。1 人が持っているファイル（Excel から書き出した仕様書など）には `file`、チーム全員が決まった gitignore 済みのパスに置くデータには `provide` を使います（xref:workflows-provide[worktree に無いファイルを用意する]）。

PKG ごとに違うが実行ごとには変わらない値（テスト対象環境の URL、テストユーザー名）は、`aidev.yaml` の `workflows.<name>.inputs` に書いておけます。定義（`workflow.yaml`）は PKG が違っても同じままで、違うのは `aidev.yaml` だけになります。

[source,yaml]
----
workflows:
  e2e-tests:
    inputs:
      base_url: https://staging.example.com
      test_user: qa-user@example.com
----

* 優先順位は `--input` > `aidev.yaml` > 宣言の `default` です。`aidev.yaml` の値は `--input` と同じ規則で確かめられ、`--dry-run` の `inputs` の行に `(from aidev.yaml)` と出ます。宣言に無い名前を書くと `aidev.yaml: workflows.<name>.inputs: the workflow declares no input "<name>"` で止まります。
* `file: true` の入力は書けません（実行する人の端末にあるファイルなので、`--input` で渡します）。
* `aidev.yaml` はコミットされるので、認証情報は書けません。`password`・`secret`・`token`・`pat`・`api_key` のような名前の入力は設定エラーになります。パスワードは `env_required`（xref:workflows-env-required[認証情報は環境変数で受け取る]）で受け取ります。

実行するときは、入力ごとに `--input` を付けます（`--input=<name>=<値>` とも書けます）。

[source,bash]
----
aidev run workflow e2e-tests --input spec=../specs/login.txt --input screen=login --input browser=firefox
aidev estimate workflow e2e-tests --input screen=login     # 見積もりでは、必須の入力が無くてもかまいません
----

* 必須の入力が無いと、何も始めずに `the workflow needs --input for: spec (the test specification to work from)` と表示して終了コード 1 で止まります（`--dry-run` でも同じです）。宣言に無い名前は `the workflow declares no input "nope" (its inputs: spec, screen, browser)`、同じ名前を 2 回渡すと `input <name> is given twice` です。
* `--resume` には `--input` を付けられません（`--resume continues the run with the inputs it was started with; do not pass --input`）。続きの実行は記録された値を使い、渡されたときと同じ規則でもう一度確かめます（記録は agent が書き換えられるファイルだからです）。
* 値は、`{inputs.<name>}` と書いた場所に入るほか、すべての agent（確認役も）の指示に `## Inputs for this run` の節として「データ」として入ります。`--dry-run` の `inputs` の行（`file` の入力は `(copied from <パス>)` 付き）、`--dry-run` と提出の PR 本文の `## Inputs (--input name=value)` の節（名前、説明、必須か既定値か、`pattern`、`a path in the repository`、`reaches a command`）、実行の PR 本文の `## Inputs`、最後のコミットの本文の `inputs:` の行、`run.json` の `inputs`、`--log` の先頭とサマリ、`aidev modify --from-run` が agent に渡す記録にも出ます。

[[workflows-env-required]]
==== 認証情報は環境変数で受け取る（`env_required`）

テストユーザーのパスワードや API のトークンは、定義にも `aidev.yaml` にも prompt にも書きません。`env_required:` に環境変数の名前（と、実行する人向けの説明）を宣言し、実行する人が shell で設定します。

[source,yaml]
----
env_required:
  E2E_PASSWORD: テストユーザーのパスワード
  E2E_API_TOKEN:                 # 説明なしでもよい。名前だけの list でも書ける: env_required: [E2E_PASSWORD]
----

* `aidev run workflow`（`--dry-run` も）は、宣言された変数が設定されているかを **名前だけ** で確かめ、無ければ何も始めずに `the environment variable E2E_PASSWORD (…) is not set; the workflow needs it (env_required)` と止まります。`--dry-run` の `env` の行には `set` / `NOT SET` が出ます。値は出ません。
* 値は agent とコマンドの環境に届きます（実行する人の shell の環境を子プロセスが引き継ぐ、今までどおりの経路です）。指示には `## Environment variables of this run` として **名前と説明だけ** が入り、agent には「値をどこにも書かない」と伝えます。`run.json`・ログ・PR 本文・コミットにも値は入りません。
* テストやコマンドは `process.env.E2E_PASSWORD` のように実行時に読みます。command step や `until` の `env` に同じ名前を書くことはできません（検証で拒否されます）。
* 名前は環境変数の規則（英字か `_` で始まる英数字と `_`）で、`AIDEV_*` と `GIT_CONFIG*` は書けません。
* 宣言は提出の PR 本文の `## Environment variables the run needs` に出ます。レビューする人は、そこに挙がる変数が本当に認証情報かを見ます（設定値なら `inputs` か `env` へ）。

[[workflows-provide]]
==== worktree に無いファイルを用意する（`provide` と `file` 入力）

実行は HEAD から作った専用の worktree で動くので、git が無視するファイルはそこにありません。別のリポジトリから持ってきて gitignore に入れてある仕様書や、テストのフィクスチャがこれにあたります。用意する方法は 2 つです。チームの全員が決まった gitignore 済みのパスに置くデータは `provide:` で手元のチェックアウトからコピーし、1 人が持っているファイルは `file: true` の入力で渡します（xref:workflows-inputs[実行ごとに変わる値を受け取る]）。依存パッケージ（`node_modules`）は `provide` ではなく、`command: npm ci` のような command step で入れます。`provide` はコマンドでは作れないデータのためのものです。

[source,yaml]
----
provide: [docs/spec/**, e2e/fixtures/**]
----

* 最初のステップの前に（`--resume` を含め、始めるたびに）、手元のチェックアウトで git が無視していて glob に一致するファイルを、1 ファイルずつ worktree の同じパスにコピーします（上書きします）。コピーするのは無視されているファイルだけです。追跡されているファイルは HEAD の内容が worktree にあり、追跡も無視もされていないファイルは手元の作業中の状態なので、実行には届きません。ディレクトリ単位ではなく、glob がファイルを名指しします（`docs/spec/**` は docs/spec の下の無視されているすべてのファイル）。
* コピーしないもの: `secrets_paths` に一致するもの（ログに `not copied (a secret path …)`）、`.aidev/` と `.git/` の下、シンボリックリンク。検証は、固定のディレクトリで始まらない glob（`**/*.txt`）、`.aidev`・`.git`・protected のパスを名指しする glob、最後の名前が認証情報のファイルに見える glob（`.env`、`.env.*`、`.npmrc`、`.netrc`、`.pypirc`、`*.pem`、`*.key`、`*.p12`、`*.pfx`、`*.jks`、`*.keystore`）を拒否します。
* 手元のチェックアウトで無視されているファイルに 1 つも一致しない glob があると、`--dry-run` と実行は何も始めずに止まります: `provide: <glob> matches no file that git ignores in <チェックアウト> (a run copies only ignored files from the checkout; put the file there, or take the entry out)`。
* コピーしたファイルは worktree でも無視されていなければなりません（無視する規則がコミット済みの `.gitignore` にあること）。そうでなければ `provide: <file> is ignored in <チェックアウト> by a rule the repository does not carry; commit the .gitignore that ignores it, so every run (and every teammate's) treats it alike` と表示して止まります。
* ログに `provide: N path(s) copied from the checkout: …` と、コピーしなかったパスを 1 行ずつ書きます。`--dry-run` には `provide` の行が出ます。提出の PR 本文には `## Provided from the checkout` の節が入ります。

[[workflows-never-commit]]
==== 決してコミットしないもの（`never_commit` と ADK の既定の一覧）

`npm ci` を実行する command step を置くと、`node_modules` が worktree にできます。PKG の `.gitignore` がそれを無視していなければ、`writable` の範囲の中にある限り、チェックポイントや pull-request step がコミットしてしまいます。ADK は、ツールが残す残骸を決してコミットしません。追跡されていないファイルのうち、次の glob に一致するものです。

[source,text]
----
**/node_modules/**  **/bower_components/**  **/.pnpm-store/**  **/.yarn/cache/**
**/.venv/**  **/venv/**  **/__pycache__/**  **/*.pyc  **/.pytest_cache/**  **/.mypy_cache/**  **/.ruff_cache/**
**/.tox/**  **/.nox/**  **/.gradle/**  **/.DS_Store  **/Thumbs.db  **/*.orig  **/*.rej
----

workflow は `never_commit:` で自分の分を足せます。ADK の一覧から外すことはできません。ビルド結果（`dist/`、`build/`、`target/`）は成果物になり得るので一覧にはありません。要らなければ workflow で足します。

[source,yaml]
----
never_commit: [e2e/test-results/**, e2e/playwright-report/**]
----

* 対象は追跡されていないファイルだけです。git が追跡しているファイルへの変更は、どこにあっても実行の仕事です（コミット済みの vendored な `node_modules` の中のファイルをステップが変えれば、他と同じようにコミットされます）。
* 効くところ: ステップと件のチェックポイント、pull-request step の最後のコミット、`unchanged` の比較、失敗した件の戻し（`on_failure: continue`）、確認役の agent に見せる差分、新しい実行の前の「未コミットの変更」の検査（worktree に残った残骸は次の実行を止めません）。
* 検証は、`<dir>/**` の形の `never_commit` が、どれかのステップの `writable` や `provide` の項目を覆うときに拒否します（そのステップの仕事が何もコミットされなくなるためです）。
* 外したものは表示します。pull-request step のログに glob ごとに `N file(s) left out as never committed (<glob>; e.g. <path>)`、`run.json` のそのステップに `leftOut: { "<glob>": 件数 }`、`--json` の出力に `leftOut`、実行の終わりに `left out, never committed: N file(s) matching <glob> (e.g. <path>)`、PR 本文に `## Left out` の節。`--dry-run` には `never commit` の行、提出の PR 本文には `## Never committed` の節が出ます。

[[workflows-unattended]]
==== 人が介入せずに大きな仕事を走らせる

E2E テストを数百〜数千件書く、フレームワークを上げる、といった大きな仕事を、実行したら終わるまで待つだけにする書き方です。

[source,yaml]
----
steps:
  - id: plan
    agent: e2e-planner
    writable: []
    prompt: テストが要る画面を調べ、notes ディレクトリの targets.txt に 1 行 1 件で書く。
  - id: write
    agent: e2e-writer
    writable: [e2e/tests/**]
    unchanged: [e2e/playwright.config.ts]
    for_each:
      from: targets.txt
      max_items: 1500              # 対象の数より大きくする
      on_failure: continue         # 通らない件は戻して先へ進む
    prompt: 画面 {item} の IT テストを e2e/tests/{item}.spec.ts に書く。
    until:
      command: npx playwright test tests/{item}.spec.ts
      cwd: e2e
      timeout_minutes: 15
      max_retries: 3
  - id: pr
    pull_request: {}

limits:
  max_usd: 400                     # これだけで止める。max_minutes は書かない
----

* **時間の上限を書かない。** `limits.max_minutes` を書かなければ、費用の上限・再試行回数・件数の上限でだけ止まります。止まって動かない agent やコマンドは `timeout_minutes` が打ち切ります。
* **対象ごとに分ける。** 1 回の agent の起動に全部をやらせず、`for_each` で 1 件ずつにします。1 件の失敗が全体に響かず、`--resume` も件の単位で続きます。
* **失敗した件で止めない。** `on_failure: continue` で、通らない件は戻して先へ進みます。残った件は PR 本文の「Targets left out」に並ぶので、後で別の実行（一覧をその件だけにする）か、人が対応します。
* **費用を先に見る。** `aidev estimate workflow <name> --ai --task "…"` で楽観・悲観の金額を見て、`limits.max_usd` を決めます（xref:cli-estimate[aidev estimate]）。
* **記録を 1 つのファイルに残す。** `aidev run workflow <name> --log <file>` で、全過程（各 agent のツール呼び出し、最終報告、コマンドの出力）とサマリを 1 つのファイルに書きます。

次のことは、まだ人の手が要ります。

* 実行する端末が止まる（スリープ、再起動、ネットワーク断）と、実行も止まります。`aidev run workflow <name> --resume last` で、終わった件を飛ばして続けます。
* AI ツールの一時的な失敗（混雑、レート制限）も、その件の失敗として数えます（`on_failure: continue` なら戻して先へ進みます）。
* 件は既定では 1 件ずつ順に処理します。`for_each.parallel` で同時に動かせます（xref:workflows-parallel[並列に動かす]）。
* 変更は 1 つの PR になります。数千件の変更を 1 つの PR でレビューするのが難しいときは、一覧を分けて何回かに分けて実行します。

[[workflows-until-agent]]
==== agent のレビューで終わりを判定する

「テストが全部通る」はコマンドで判定できますが、「テストの中身が妥当か」はコマンドでは判定できません。そういう条件は、`until` に確認役の agent を書きます。

[source,yaml]
----
  - id: write
    description: テストを書き、通してからレビューで合格をもらう
    agent: test-writer
    writable: [tests/**]
    prompt: 前のステップが列挙したテストを既存の書き方で書き、実行する。
    until:
      command: npm test            # 先にこれが exit 0 になること
      agent: test-reviewer         # 次にこの agent が合格と判定すること
      prompt: |                    # test-reviewer に確認させる観点
        前のステップが列挙した振る舞いがすべてテストされているか。
        実装の内部ではなく、外から見える振る舞いを検証しているか。
      max_retries: 4
----

1 回の試行は次の順で進みます。

. `test-writer` がテストを書く
. `npm test` を実行する。失敗したら、その出力を添えて `test-writer` をやり直させる（`test-reviewer` は起動しない）
. `test-reviewer` を起動する。`test-writer` の報告、`writable` の範囲で変わったファイルの一覧、差分を書いた file の場所、`until.prompt` を渡す
. `test-reviewer` が最終メッセージを `VERDICT: PASS` の行で終えればステップは完了です。`VERDICT: FAIL`、またはその行が無ければ不合格で、`test-reviewer` の報告を添えて `test-writer` をやり直させる

確認役の agent について:

* **何も書けません。** ステップの `writable` は確認役には効きません。確認役が使える skill・ツール・MCP server は、その agent の frontmatter と workflow の `agents:` で決まります（`tools: Read, Grep, Glob` など、読むだけのものにします）。
* 合格・不合格の書き方（`VERDICT:` の行）は ADK が指示に入れます。agent の本文や `until.prompt` に書く必要はありません。
* `until.prompt` には、何を確認するかを具体的に書きます。観点が曖昧だと、同じ指摘が繰り返されて止まるか、`until.max_retries` を使い切ります。
* 確認役の起動も、やり直しの回数（`until.max_retries`）、費用の上限、時間の上限に数えます。1 回の試行で agent が 2 回起動するので、`limits.max_usd` はその分を見込みます。
* 合格したときの確認役の報告は、後の agent step の指示にも入ります。
* 確認役の agent も workflow と一緒に PR でレビューされ、`origin/main` と同じでなければ実行できません。

[[workflows-trial]]
=== 承認の前に試す（`--trial`）

workflow は、書いて一度で動くことがほとんどありません。`until` のコマンドがこの PKG では通らない、`writable` が足りない、command step が残す残骸、worktree に無いファイル、といったことは実行してみて分かります。提出 → 承認 → 実行 → 失敗 → 修正を繰り返すと、`main` に試行錯誤のコミットが積まれます。`--trial` は、承認の前に、手元の定義をそのまま実行して確かめるためのものです。

[source,bash]
----
aidev run workflow write-tests --trial --task "src/services/order.ts"      # 直す → 試す → 直す → 試す
aidev run workflow write-tests --trial --dry-run                           # 何を試すかだけ見る
aidev submit workflow write-tests                                          # 結果が正しくなったら提出
----

`aidev create workflow` の後に表示される次の手順も、1. review、2. try（`--trial`）、3. submit、4. run の順です（`aidev modify workflow` では 1. review、2. try、3. estimate、4. submit）。

試験の実行（trial）は次のように動きます。

* **手元の定義をそのまま実行します。** 承認されているかどうかは問いません。未コミットの編集も含みます。定義は検証を通り、起動前の検査（xref:workflows-run[workflow の実行]）に通らなければなりません。`--dry-run --trial` は `approved` の行に `not required: --trial runs the definition as it is in this checkout (…)` と表示し、`trial` の行とブランチ `aidev/<name>.trial` を示し、問題が無ければ `dry run: the definition validates and would run as a trial (nothing pushed).` で終了コード 0 になります。`--trial` なしで未承認の workflow を実行しようとしたときの表示にも `To try it as it is first: aidev run workflow <name> --trial` が付きます（`--dry-run` なら `(try it as it is with --trial)`）。
* **専用のブランチと worktree で動きます。** ブランチは `aidev/<name>.trial`（`--dated` なら `aidev/<name>.trial-<yyyymmddHHMM>`）、worktree は普通の実行と同じ場所の `aidev-<name>.trial` です。workflow の名前に `.` は使えないので、他の workflow のブランチとぶつかりません。
* **毎回まっさらです。** 新しい試験（`--resume` でないもの）のたびに、試験のブランチを今チェックアウトしているコミットへ `reset --hard` し、前の試験が未コミットのまま残したものを消します。git が無視するものと、決してコミットしない残骸は残すので、command step が入れた `node_modules` は次の試験でも使えます。前の試験の `runs/` の記録も残ります（`--from-run` で読めます）。
* **定義のファイルだけを持ち込みます。** レビュー対象のファイル（`workflow.yaml` と、それが参照する PKG の agent・skill）を手元のチェックアウトから worktree にコピーし、`aidev(<name>): trial definition` として試験のブランチにコミットします。それ以外の未コミットの変更は worktree に届きません（実行は HEAD から始まります）。手元に未コミットの変更があると、試験とその `--dry-run` は `the checkout has N uncommitted change(s) a run does not see (it starts from HEAD): …; commit them first if the steps need them` と警告します。
* **書き込みの検問は、試験の定義に対して効きます。** 承認の代わりに、ADK は worktree の git ディレクトリ（作業ツリーの外）に試験の記録を置き、agent にだけ `AIDEV_WORKFLOW_TRIAL` を渡します。hook は書き込みとツール呼び出しのたびに、worktree の定義ファイルのハッシュが試験を始めたときと同じことを確かめ、同じ間だけそのステップの `writable` を許可します（許可の理由は `a trial run of the definition sha256:…` で、承認とは呼びません）。実行中に定義や agent・skill を書き換えると、承認済みの workflow を編集したときと同じく、その時点で拒否されます。記録は実行が終わると消えます（Ctrl-C でも）。
* **何も push せず、PR も作りません。** pull-request step はコミットまでは行い（最後のコミットの本文に `approved: none (a trial run of the definition sha256:…)` と `trial run: not pushed` が入ります）、push と PR を飛ばします。agent と command step には、`git push` を拒否する git の設定（ADK の `pre-push` hook と、push 先を無効な URL に向ける設定）が環境変数で渡されます。step の `env` はこれを上書きできません（`GIT_CONFIG` で始まる名前は書けません）。`git … push` の command step や `until.command` は、始める前に `pushes; a trial run pushes nothing` と拒否されます。agent の `Bash` からの `git push`、`gh pr create`、`az repos pr create`、`glab mr create` は hook が拒否します。
* **記録と見積もり。** `run.json` には `trial: true`、`trialHash`、`approvedRef: null` が入ります。見積もりの記録にも `trial: true` が付き、`aidev estimate` は試験の実行から学びません。試験の後は estimate-reviewer も自動では動きません。`--log` のサマリには `(a trial run: nothing pushed)` と出ます。
* **続きと修正。** `--resume last` は同じ種類の最後の実行を選びます（`--trial` 付きなら最後の試験、無しなら試験でない最後の実行）。試験を続けるには `--trial` が要り、試験でない実行には付けられません。続ける試験は始めたときの定義のままでなければならず、変わっていれば `start a new trial` と表示します。続ける実行は（試験でなくても）、終わったステップのチェックポイントがブランチに残っていなければ拒否します（後の試験がブランチを戻したとき、マージ後にブランチを進めたとき）。`aidev modify workflow <name> --from-run last` は試験の記録も受け付けます（先頭に `(a trial run)` と付き、入力と、agent が拒否されたツール呼び出しも渡します）。
* **費用を抑える。** `--max-usd <n>` で、この実行だけ `limits.max_usd` より下げられます（下げる方向だけです。`limits` の行は `$0.5 (limits.max_usd is $1)` のようになります）。試験に限らず使えます。

試験が終わると、次のように表示します。

[source,text]
----
✓ workflow finished: 3 step(s)
    agent runs: 3, reported cost $2.0333
ℹ trial run: nothing pushed; the result is on aidev/write-tests.trial in ~/.local/share/ai-dev-kit/worktrees/my-pkg-1a2b3c4d/aidev-write-tests.trial (the pull request text it would carry: .aidev/workflows/write-tests/runs/2026-10-14T01-12-03-114Z/pull-request.md)
    branch aidev/write-tests.trial (1 checkpoint commit(s) in this start); worktree ~/.local/share/ai-dev-kit/worktrees/my-pkg-1a2b3c4d/aidev-write-tests.trial
    left out, never committed: 312 file(s) matching **/node_modules/** (e.g. node_modules/.package-lock.json)
⚠ 1 file(s) changed outside what the steps may write, by a command step or past the guard; not committed: coverage/lcov.info
⚠ step write: the tool was refused 2 call(s): Write src/services/order.ts; Edit package.json (a path outside writable? see run.json "denied")
ℹ trial run: nothing was pushed. aidev/write-tests.trial holds 3 commit(s) since 9f8e7d6a1b2c
    inspect: git -C "<worktree>" log --oneline 9f8e7d6a1b2c..HEAD   /   git -C "<worktree>" diff --stat 9f8e7d6a1b2c
    when the result is right: aidev submit workflow write-tests   (the reviewed definition then runs with "aidev run workflow write-tests")
    record: <worktree>/.aidev/workflows/write-tests/runs/2026-10-14T01-12-03-114Z
----

* `left out, never committed: …` は、ツールの残骸と `never_commit` のパスをコミットから外した件数です（xref:workflows-never-commit[決してコミットしないもの]）。
* `… changed outside what the steps may write …` は、command step が `writable` の外に書いたか、agent が検問を通らずに書いたファイルです。コミットされていません。要るものなら、そのステップの `writable` を広げます。
* `the tool was refused N call(s): …` は、agent が `writable` の外や、与えられていないツールを呼んで拒否された回数です（`run.json` のそのステップの `denied` に一覧があります）。`writable` が足りないのか、`prompt` を直すのかの手がかりになります。
* `inspect:` の 2 つの git コマンドで、試験のブランチのコミットと差分を見ます。PR 本文になるはずの文章は実行記録の `pull-request.md` にあります。
* 結果が正しければ `aidev submit workflow <name>` で提出します。止まったときは `--resume <run id> --trial` で続けるか、`aidev modify workflow <name> --from-run <run id>` で直させます。

試験が保証しないこともあります。

* 試験が縛るのは ADK の実行と git です。agent が他のツールや MCP server を通してできることは、承認済みの実行と同じく PKG の policy の許可規則で決まります。未レビューの定義のあらゆる副作用を止めるものではありません。hosting の PAT も外しません（MCP server が要ることがあるためです）。外部システムを更新する agent を含む workflow は、試験でも更新します。
* 試験が通っても、承認ではありません。提出して、レビューを経て `main` に入った定義だけが `aidev run workflow <name>` で（push と PR を伴って）実行できます。

[[workflows-submit]]
=== workflow の提出（Engineering Manager）

`git diff` で定義を確認したら提出します。

[source,bash]
----
git diff -- .aidev/workflows/write-tests/ .aidev/agents/ .aidev/skills/
aidev submit workflow write-tests
----

[source,text]
----
aidev submit workflow write-tests
✓ on branch aidev/workflow-write-tests
✓ committed 3f2a9c1b7d0e (1 file(s))
✓ pushed aidev/workflow-write-tests
✓ pull request !124 created (aidev/workflow-write-tests → main)
    Once it is merged, anyone with the branch fetched can run: aidev run workflow write-tests
----

* 定義を検証し、`aidev/workflow-<name>` ブランチに `workflow.yaml` と、それが参照する PKG 内の agent・skill を `aidev: workflow <name>` としてコミットし、push して PR を作ります（Azure DevOps）。`generic` hosting では push まで行い、PR は手で作ります。`--no-push` なら push もしません。
* PR 本文には目的、ステップごとの内容（順番・agent・書ける場所・その agent の skill・ツール・MCP server・起動できるサブエージェント・`until`・parallel グループ）、関係するファイル（新規か変更か）、上限と、「マージがこの workflow を承認する」旨が書かれます。承認済みの workflow を直した提出では、承認済みの版との差分（What changed against the approved workflow）、費用の見積もりの前後（Estimate）、`aidev modify` で直したときはその理由（Why this change）も入ります。本文の全文は `.aidev/cache/submit/<name>.md` にも残ります（xref:cli-submit[aidev submit]）。
* 既に `main` と同じなら `already matches origin/main; nothing to submit.` と表示して終わります。

`.aidev/workflows/**`・`.aidev/agents/**`・`.aidev/skills/**` には branch policy で必須レビュアーを付けてください。誰が承認したかは PR のレビュアーと git の author が記録します。

[[workflows-approval]]
=== 承認の定義

「承認済み」とは、`workflow.yaml` と、それが参照する PKG 内の agent・skill の内容が、**`origin/<tracking branch>`（通常 `origin/main`）にあるものと 1 byte も違わない** ことです。承認を記録するコマンドやファイルはありません。

* 判定は最後に fetch した `origin/main` で行います。マージ後は `git fetch origin` してから実行します。offline でも判定できます。
* 承認後に手元で編集すると、その時点で未承認になります。実行中の agent が `workflow.yaml` や自分の定義を書き換えて範囲を広げても、書き込みのたびに判定するので拒否されます。
* 状態は `aidev list workflows` で見ます。

[source,text]
----
aidev list workflows
  write-tests           approved                          指定した対象のテストを既存の書き方で書き、通してから PR を作る
  e2e-tests             not on origin/main                主要画面の IT テストを Playwright で書く
  write-conventions     changed since origin/main         Wiki と根拠ソースから開発規約を書き、PR を作る

----

[[workflows-run]]
=== workflow の実行（Developer）

[source,bash]
----
git fetch origin
aidev run workflow write-tests --dry-run --task "src/services/order.ts"
aidev run workflow write-tests --task "src/services/order.ts"
aidev run workflow e2e-tests --input spec=../specs/login.txt --input screen=login   # inputs: を宣言した workflow
----

`--dry-run` は承認の状態、使う agent と AI ツール、上限、費用の見積もり（楽観〜悲観）、今回の指示と入力、ステップごとの内容（書ける場所、skill・ツール・MCP server）を表示して何も始めません。起動前に止まる問題（コマンドの実行ファイルが PATH に無い、`provide` の glob に一致するファイルが無い、`path: true` の入力が worktree に届かない）もここで分かります。まずこれで確認します。

費用の内訳は `aidev estimate workflow <name>` で見ます。`--ai` を付けると、agent が今回の `--task` とコードを読んで、やり直しの回数や `for_each` の件数を見積もり、幅を狭めます（xref:cli-estimate[aidev estimate]）。

[source,bash]
----
aidev estimate workflow write-tests --ai --task "src/services/order.ts"
----

`--task` は今回の指示です（Work Item の番号、対象のパスなど）。すべての agent step に「データ」として渡され、`objective` や各ステップの `writable` を変えることはできません。長い指示は `--task-file <path>` で渡します。

workflow が `inputs:` を宣言していれば、入力ごとに `--input <name>=<値>` を付けます。必須の入力が無いと、何も始めずに `the workflow needs --input for: …` と表示して止まります（xref:workflows-inputs[実行ごとに変わる値を受け取る]）。`aidev.yaml` の `workflows.<name>.inputs` に書いてある値は、`--input` を省いたときに使われます。`env_required:` を宣言していれば、その環境変数（パスワードなど）を shell で設定してから実行します。無ければ何も始めずに止まります（xref:workflows-env-required[認証情報は環境変数で受け取る]）。`--max-usd <n>` を付けると、この実行だけ費用の上限を `limits.max_usd` より下げられます（`--max-minutes` と同じく、下げる方向だけです）。

実行中に起きることは次のとおりです。

* 実行は **専用の git worktree** で動きます。あなたの作業ツリーには触れないので、未コミットの変更があっても実行でき、実行中も手元で作業を続けられます（xref:workflows-worktree[実行の worktree とブランチ]）。
* ブランチは workflow ごとに 1 つ（`aidev/<name>`）で、実行のたびに同じブランチ・同じ worktree を使います。日付付きのブランチ（`aidev/<name>-<yyyymmddHHMM>`）に分けたいときだけ `--dated` を付けます。
* agent は対話セッションと同じ設定ファイル・hooks・policy のもとで動きます。書けるのは、いま動いているステップの `writable` の中だけで、それ以外への書き込みは hook が拒否します。agent 自身は commit も push もしません。
* 最初のステップの前に、`provide:` の glob に一致する gitignore 済みのファイルを手元のチェックアウトから worktree にコピーし、`file: true` の入力のコピーを実行記録の `inputs/` に置きます（xref:workflows-provide[worktree に無いファイルを用意する]）。
* ステップ（`for_each` なら 1 件）が通るたびに、そのステップの `writable` の変更を **チェックポイントとしてコミット** します（`aidev(<name>): <step>`）。止まった実行は、最後のチェックポイントから続けられます。追跡されていないファイルのうち、ADK の既定の一覧（`node_modules`、`__pycache__` など）と `never_commit:` に一致するものはコミットしません（xref:workflows-never-commit[決してコミットしないもの]）。
* Claude Code は、agent の frontmatter と workflow の `agents:` で与えた `tools` と `mcp` だけを渡して起動します（`subagents` があれば、その定義を `--agents` で渡します）。それ以外のツールは存在しない扱いになり、呼んでも hook が拒否します。`mcp` を書かない agent には MCP server を渡しません。
* 前の agent step の最終報告は、後の agent step の指示に入ります。notes ディレクトリの file も読めます（xref:workflows-handoff[ステップの間で結果を渡す]）。
* `until` を満たさなければ、その結果（コマンドの出力、または確認役の agent の報告）を添えて同じ agent をもう一度起動します。同じ結果が 2 回続いたら止まります。
* コマンドが 15 秒以上かかるときは、15 秒ごとに経過を 1 行表示します。
* `pull_request` のステップは、チェックポイントの後に残った `writable` の範囲の変更と実行の記録を最後のコミットにし、ブランチを push して PR を作ります。同じブランチの PR が開いていれば、新しく作らずに本文を更新します。PR 本文に workflow 名・run id・起点のコミット・承認の基準・agent の起動回数・費用と、各 agent step の最終報告が書かれます（Azure DevOps の上限 4000 文字に収まるよう、報告は短くします。それでも収まらなければ行の区切りで切り、切った所に `pull-request.md` を指す注記を入れ、最後の行は残します。短くしたときは実行のログにその旨が出ます）。全文は実行記録の `pull-request.md` にあります。ブランチに起点からの変更が無ければ commit も PR も作りません。
* 記録は worktree の `.aidev/workflows/<name>/runs/<id>/` に、実行しながら書きます。gitignore 済みで、コミットされません。`--resume`・`aidev estimate`・`aidev modify --from-run` は、手元と worktree の記録をまとめて探します。
* 実行の終わりに、ステップの `writable` の外で変わったファイル（`N file(s) changed outside what the steps may write, by a command step or past the guard; not committed: …`）と、agent が拒否されたツール呼び出し（`step <id>: the tool was refused N call(s): Write src/x.ts …`。`run.json` のそのステップの `denied` にも残ります）を表示します。どちらもコミットされません。`writable` が足りないのか、ステップを直すのかの手がかりです。

[[workflows-worktree]]
==== 実行の worktree とブランチ

[%autowidth.stretch,options="header"]
|===
|項目 |内容

|worktree の場所
|`<AIDEV_HOME>/worktrees/<PKG 名>-<ハッシュ>/<ブランチ名の / を - にしたもの>`（Linux なら `~/.local/share/ai-dev-kit/…`、Windows なら `%LOCALAPPDATA%\ai-dev-kit\…`）。ハッシュは **PKG のクローンの場所（絶対パス）** から作るもので、同じ端末に同じ PKG のクローンが複数あっても置き場所がぶつからないようにするためだけのものです。workflow の内容とは関係なく、workflow を直しても変わりません。2 回目以降の実行は、場所ではなくブランチ名（`git worktree list`）で worktree を探します。PKG の外に置くので、PKG で動かすテストやリンターが 2 つ目のソースを拾いません。

|ブランチ
|`aidev/<name>`。初回は、今チェックアウトしているコミットから作ります。`--dated` なら実行ごとに `aidev/<name>-<yyyymmddHHMM>` と、その worktree を新しく作ります。`--trial` なら `aidev/<name>.trial` と、その worktree（`aidev-<name>.trial`）で動き、試験のたびに今チェックアウトしているコミットへ戻します（xref:workflows-trial[承認の前に試す]）。

|2 回目以降の実行
|同じブランチ・worktree を使います。ブランチの変更がすでに起点（今チェックアウトしているコミット）に取り込まれていれば、起点まで進めてから始めます。取り込まれていない変更があれば、起点をブランチにマージしてから始め、前の実行の成果の上に積みます。マージが衝突したら止まります（worktree で解決するか、`--dated` で別のブランチにします）。

|未コミットの変更
|worktree の `writable` の範囲に未コミットの変更があると、新しい実行は始まりません（止まった実行の途中の変更です）。`--resume last` で続けるか、表示されるコマンドで捨てます。

|同時実行
|1 つの worktree で動く実行は 1 つだけです。動いている実行があれば、次の実行は止まります。

|worktree に無いもの
|git が無視するもの（`node_modules`、`.env`、ビルド結果）は新しい worktree にありません。依存パッケージが要る workflow は、最初に `command: npm ci` のようなステップを置きます（入れたものはコミットされません。xref:workflows-never-commit[決してコミットしないもの]）。gitignore 済みのデータ（仕様書、フィクスチャ）は `provide:` で手元のチェックアウトからコピーするか、`file: true` の入力で渡します（xref:workflows-provide[worktree に無いファイルを用意する]）。

|片付け
|worktree は実行の後も残ります（`--resume` と記録のため）。要らなくなったら `git worktree remove <path>`、ブランチは `git branch -D aidev/<name>` で消します。消しても、次の実行で作り直します。
|===

[%autowidth.stretch,options="header"]
|===
|file |内容

|`run.json`
|ステップごとの結果、止まった理由、費用、agent の起動ごとの費用（`calls`。xref:cli-estimate[見積もり] が使います）。ステップが終わるたびに更新します。

|`log.txt`
|画面に出た経過の行

|`reports/<step>.md`
|終わった agent step の最終報告の全文（確認役は `<step>.until.md`）。`for_each` のステップは件ごとのまとめで、件ごとの全文は `<step>.t<件の番号>.md`

|`logs/<step>.<試行>.<番号>.log`
|コマンドの出力の全文（`for_each` の件は `<step>.t<件の番号>.<試行>.<番号>.log`）

|`diffs/<step>.<試行>.diff`
|確認役の agent に見せた差分

|`unchanged/<step>.json`
|`unchanged` のパスの、ステップを始めたときの状態

|`notes/`
|ステップが次のステップのために書いた file

|`inputs/<name><拡張子>`
|`file: true` の入力のコピー。`{inputs.<name>}` はこのパスです（xref:workflows-inputs[実行ごとに変わる値を受け取る]）

|`pull-request.md`
|PR 本文の全文。`generic` hosting で PR を手で作るときに使います。`--trial` の実行では、PR にするはずだった文章です。
|===

[[workflows-resume]]
==== 止まった実行を続ける

止まった実行は、止まったステップから続けられます。終わったステップはやり直しません。

[source,bash]
----
aidev run workflow write-tests --resume last          # 最後の実行を続ける
aidev run workflow write-tests --resume 2026-09-23T01-12-03-114Z
----

* その実行の worktree・ブランチ・`--task`・notes で続きます。手元でどのブランチにいてもかまいません。`--task` と `--dated` は付けられません。
* 止まったステップは、**最後のチェックポイントから** やり直します。そのステップが `writable` に残した未コミットの変更は戻します。終わったステップと終わった件の変更はチェックポイントにあるので残ります。
* 終わったステップの最終報告は記録から読み、後のステップの指示に入れます。
* `for_each` のステップは、終わった件を飛ばして、止まった件から続けます。一覧はもう一度読むので、どうしても通らない件は、一覧の file（worktree の notes ディレクトリ）からその行を消してから続けられます。
* agent には前回止まった理由を伝えます。
* 時間と費用の上限は、続きの実行で新しく数えます。`run.json` の費用と起動回数は合計です。
* 実行を始めたあとに定義（`workflow.yaml`）が変わっていると続けられません。新しく実行します。
* worktree を消していても、ブランチが残っていれば作り直して続けます（記録は worktree にあるので、消したときは新しく実行します）。

原因が定義にあるとき（`until` のコマンドがこの PKG で通らない、`writable` が足りないなど）は、続けても同じところで止まります。workflow の失敗は、agent が同じエラーに何度も当たって止まることがほとんどです。その実行の記録から定義を直させます（xref:workflows-fix-from-run[止まった実行から直す]）。

止まったときの表示と対処です。終了コードは 1 です。

[%autowidth.stretch,options="header"]
|===
|表示 |対処

|`workflow <name> is not approved: … is not on origin/main yet`
|PR が未マージです。マージ済みなら `git fetch origin`。手元の定義をそのまま試すなら、表示される `aidev run workflow <name> --trial` です（xref:workflows-trial[承認の前に試す]）。

|`workflow <name> is not approved: … differs from origin/main`
|手元で定義を変えています。戻すか、 Engineering Manager に提出し直してもらいます。変えた定義を試すなら `--trial` です。

|`the worktree of aidev/<name> (…) has uncommitted changes, left by a run that stopped in the middle of a step`
|前の実行が途中で止まっています。`--resume last` で続けるか、表示された `git -C … reset --hard` と `clean -fd` で捨ててから実行します。

|`another run (…, process N) is working in …`
|同じ workflow の実行が動いています。終わるのを待ちます。

|`aidev/<name> has work that conflicts with …`
|ブランチの前の成果と、今の起点が衝突しています。worktree で `git merge` して解決するか、`--dated` で別のブランチにします。

|`workflow stopped — step <id>: the until check still fails after N retries (…)` +
`… the same failure repeated`
|agent が `until` を満たせませんでした（括弧内が最後の結果です。`npm test exited 1`、`test-reviewer answered FAIL` など）。終わったステップまではブランチ `aidev/<name>` のチェックポイントにあります。中身と、コマンドの出力（`run.json` の `log` が指す file）か `run.json` の `review`（確認役の最後の報告）を見ます。手で直せる原因なら直して `--resume last` で続けます。そうでなければ `--task` を具体的にするか、 Engineering Manager に `until.max_retries` や `prompt`、`until.prompt` の見直しを相談します。

|`workflow stopped — step <id>: cost limit of $N reached` +
`… time limit of N minutes exceeded`
|上限に達しました。`--resume last` で続きから実行できます（上限は新しく数えます）。何度も達するなら、`--task` を小さくするか、 Engineering Manager に上限の見直しを相談します（上限は定義の変更 = PR です）。

|`workflow stopped — step <id>: <command> exited N`
|`command` step が失敗しました。出力（`run.json` の `log` が指す file）を見て原因を直し、`--resume last` で続けます。

|`workflow stopped — step <id>: … N path(s) that must stay unchanged were changed`
|ステップが `unchanged` のパスを変えました。変わったパスは `log.txt` にあります。元に戻してから（`git checkout -- <path>` など）`--resume last` で続けます。変えないと進められない仕事なら、 Engineering Manager に定義の見直しを相談します。

|`workflow stopped — step <id>: target <件>: …`
|`for_each` のステップが、その件で止まりました。続きの理由は上の行と同じです。直して `--resume last` で、その件から続けます。

|`workflow stopped — step <id>: <file> line N: "…" is not a target` +
`… lists N targets, above for_each.max_items`
|一覧の書き方が合っていないか、件数が上限を超えています。一覧の file（実行記録の `notes/`）を直して `--resume last` で続けます。繰り返すなら、 Engineering Manager に一覧を書くステップの `prompt` を直してもらいます。

|`workflow <name> has changed since run <id> started`
|実行を始めたあとに定義が変わっています。`--resume` なしで新しく実行します。

|`run <id> was not made on a branch of its own (it predates worktree runs)`
|worktree で動く前の版で始めた実行は続けられません。新しく実行します。

|`the checkpoints of run <id> are no longer on aidev/<name> (… is not in its history; a later run moved the branch); start a new run`
|終わったステップのチェックポイントがブランチに残っていません（後の `--trial` がブランチを戻した、マージ後にブランチを進めた）。`--resume` なしで新しく実行します。

|`run <id> was a trial run; resume it with --trial` +
`run <id> was not a trial run; resume it without --trial` +
`workflow <name> has no recorded run that was not a trial (pass --trial to continue the last trial)` +
`workflow <name> has no recorded trial run (its runs were started without --trial)`
|`--resume` は同じ種類の実行だけを続けます。試験（`--trial`）を続けるなら `--trial` を付け、普通の実行なら外します（xref:workflows-trial[承認の前に試す]）。

|`the definition of <name> (or an agent or skill it uses) changed since trial run <id> started; start a new trial`
|試験を始めたあとに定義（または agent・skill）が変わっています。`--resume` なしで、もう一度 `--trial` で実行します。

|`--resume continues the run with the inputs it was started with; do not pass --input`
|続きの実行は最初の入力を使います。`--input` を外します。

|`the workflow needs --input for: <name> (<説明>)` +
`the workflow declares no input "<name>" (its inputs: …)` +
`input <name>: "<値>" does not match its pattern (<pattern>)` +
`input <name> reaches a command, so its value must be one plain token (…)` +
`input <name> is given twice`
|`--input` が足りない、名前が宣言に無い、値が規則に合いません。`--dry-run` の `## Inputs (--input name=value)` に宣言の一覧が出ます（xref:workflows-inputs[実行ごとに変わる値を受け取る]）。何も始まっていません。

|`input <name>: <path> is not committed; a run starts from HEAD (commit it, or declare the input with file: true and pass the file)` +
`input <name>: <path> is ignored by git and no provide: entry copies it into the run (add one, or pass it as a file input)` +
`input <name>: <path> does not exist in <チェックアウト>` +
`input <name>: <path> does not exist in the run's worktree (…); a file git ignores reaches it only through provide:`
|`path: true` の入力が実行の worktree に届きません。コミットするか、`provide:` に足すか、`file: true` の入力にして渡します（xref:workflows-provide[worktree に無いファイルを用意する]）。何も始まっていません。

|`input <name>: <file> is not a file on this machine` +
`input <name>: the AI tools read text; export <file> to Markdown, CSV or text first and pass that file`
|`file: true` の入力のファイルが無いか、テキストではありません（Excel・Word・PDF・画像は読めません）。テキストに書き出して、そのパスを渡します。

|`provide: <glob> matches no file that git ignores in <チェックアウト> (a run copies only ignored files from the checkout; put the file there, or take the entry out)`
|手元のチェックアウトに、その glob に一致する gitignore 済みのファイルがありません。ファイルを置くか、 Engineering Manager に `provide` の項目を外してもらいます。何も始まっていません。

|`provide: <file> is ignored in <チェックアウト> by a rule the repository does not carry; commit the .gitignore that ignores it, so every run (and every teammate's) treats it alike`
|そのファイルを無視する規則がコミットされていません（`.git/info/exclude` や、コミット前の `.gitignore`）。`.gitignore` に書いてコミットします。

|`step <id>: <command> was not found on PATH, so "…" could not run`
|コマンドの実行ファイルが PATH にありません。インストールするか、PATH を通します。何も始まっていません（`./run.sh` や `node_modules/.bin/x` のような相対パスは、前のステップが作ることがあるので検査しません）。

|`step <id>: "git … push" pushes; a trial run pushes nothing`
|`--trial` では、push する command step や `until.command` を実行できません。試験の間は外すか、別の確認方法にします。

|`agent <name> uses the MCP server <server>, which .mcp.json does not register`
|agent の `mcp` にある server が、PKG の `.mcp.json` にありません。`.mcp.json` に server を登録します（人が行います）。何も始まっていません。

|`agent <name> is given tools (in its frontmatter or the workflow's agents:), and <tool> cannot be limited to them; run it with claude`
|`tools` や `mcp` を書いた agent は、制限できない AI ツール（Copilot CLI など）では起動しません。`aidev.yaml` の `tools.agent`（または workflow の `tool`）を `claude` にします。

|`branch aidev/<name> is ready; hosting.type is generic; open the pull request by hand`
|正常です。push 済みのブランチから手で PR を作ります。

|`N file(s) changed outside what the steps may write, by a command step or past the guard; not committed: …`
|実行は止まっていません（終了コードは結果どおりです）。command step が `writable` の外に書いたか、agent が検問を通らずに書いています。コミットされていないので、要るものなら Engineering Manager がそのステップの `writable` を広げます。

|`step <id>: the tool was refused N call(s): Write src/x.ts … (a path outside writable? see run.json "denied")`
|実行は止まっていません。agent が `writable` の外や、与えられていないツールを呼んで拒否されています。`run.json` のそのステップの `denied` に一覧があります。仕事に要るなら、 Engineering Manager が `writable` か agent の `tools` を直します。

|`left out, never committed: N file(s) matching <glob> (e.g. <path>)`
|正常です。ツールが残した残骸（`node_modules` など）と `never_commit` のパスを、コミットから外しました（xref:workflows-never-commit[決してコミットしないもの]）。
|===

[[workflows-fix]]
=== workflow の修正（Engineering Manager）

workflow を直すきっかけは 2 つあります。定義の PR でレビューする人から指摘を受けたとき、そして実行した結果（成果物の PR）が期待と違ったときです。どちらも、直すのは **定義（`workflow.yaml` と agent・skill）** です。成果物の PR だけを手で直しても、次に実行すれば同じ結果になります。

==== どこを直すか

困っていることから、直す場所を探します。

[cols="2,1,3",options="header"]
|===
|困っていること |直す場所 |直し方

|調査したステップの結果が、次のステップで使われない
|調査ステップの `prompt`
|「結果を最終報告に列挙する」と書きます。長い一覧や計画は「notes ディレクトリの file に書く」と書き、次のステップの `prompt` に「その file を読む」と書きます（xref:workflows-handoff[ステップの間で結果を渡す]）。

|書き込みが拒否されて止まる（`is read-only`）
|そのステップの `writable`
|必要なパスを足します。足すのは、そのステップに本当に要る場所だけにします。

|頼んでいないファイルまで変えている
|そのステップの `writable` と `prompt`
|`writable` を狭め、`prompt` に「〜は変えない」と書きます。

|テストや設定を弱めて `until` を通している
|そのステップの `unchanged`、`until`
|弱められては困るパスを `unchanged` に書きます。`until.command` は test runner を直接呼びます（xref:workflows-unchanged[変えてはいけない場所を決める]）。

|対象が多く、後半の質が落ちる。1 件の失敗で全部やり直しになる
|ステップの分け方
|一覧を書くステップと、`for_each` で 1 件ずつ処理するステップに分けます（xref:workflows-for-each[対象ごとに繰り返す]）。

|手順を知らずに、やり方がばらばらになる
|agent の `skills`
|手順書（skill）を書き、agent の `skills` に足します。

|外部システム（チケットなど）を見られない
|agent の `mcp` と PKG の `.mcp.json`
|`.mcp.json` に server を登録し（人が行います）、agent の `mcp` に名前を足します。

|必要なツールが無いと言われる
|agent の `tools`
|そのツールを足します。外部システムに触る agent には `Bash` を足さず、別の agent に分けます。

|`until` がずっと失敗して止まる
|`until`（`max_retries` を含む）、ステップの分け方
|`until` のコマンドがこの PKG で本当に通るかを手で確かめます（実行するディレクトリは `cwd`、環境変数は `env`）。仕事が大きすぎるなら、ステップを分けます。

|確認役の agent が何度も不合格にする
|`until.prompt`、ステップの `prompt`
|`run.json` の `review` で指摘を読みます。確認の観点を具体的にし、同じ観点をステップの `prompt` にも書いて、作る側に最初から伝えます。

|費用や時間の上限で止まる
|`limits.max_usd`、`limits.max_minutes`
|実行の記録（実行の worktree の `.aidev/workflows/<name>/runs/<id>/run.json`）の費用と時間、`aidev estimate workflow <name>` の見積もりを見て決めます。

|実行ごとに違う値（仕様書のパス、対象の画面）を `prompt` に書き換えている
|`inputs`
|`inputs:` に宣言し、`prompt` や `until.command` に `{inputs.<name>}` と書きます。実行する人が `--input` で渡します（xref:workflows-inputs[実行ごとに変わる値を受け取る]）。

|worktree に無いファイル（gitignore 済みの仕様書やフィクスチャ）で止まる
|`provide`、`file: true` の入力
|チームで決まったパスに置くものは `provide:` に glob を書きます。1 人が持つファイルは `file: true` の入力にします（xref:workflows-provide[worktree に無いファイルを用意する]）。`node_modules` は `command: npm ci` のステップで入れます。

|command step やテストが残したもの（結果レポート、キャッシュ）がコミットされる
|`never_commit`
|そのパスを `never_commit:` に書きます。`node_modules` や `__pycache__` などは書かなくてもコミットされません（xref:workflows-never-commit[決してコミットしないもの]）。
|===

agent・skill は、それを使うすべての workflow で共有されています。**agent.md を直すと、その agent を使う他の workflow の動きも変わります。** 1 つの workflow だけ変えたいときは、agent を分けます（`aidev create agent <新しい名前>`）。

[[workflows-fix-from-run]]
==== 止まった実行から直す

workflow の失敗は、agent が同じエラーに何度も当たって止まることがほとんどです（`the same failure repeated`）。`--from-run` を付けると、その実行の記録を workflow-creator に渡して、原因を取り除くように定義を直させます。

[source,bash]
----
aidev modify workflow write-tests --from-run last
aidev modify workflow write-tests --from-run 2026-09-23T01-12-03-114Z --describe "テストのデータは fixtures から作る"
----

* agent に渡るもの: 止まった理由、ステップごとの結果と agent の起動回数、通らなかったステップの最後の確認の出力（`until` のコマンドのログ、確認役の指摘、失敗した件）、実行ログの末尾。
* agent は、原因を 1 文（`CAUSE:`）で書いてから、変更を並べます。リトライや上限を上げるだけの修正は、それが原因だと記録から言えるときだけにさせます。
* `--describe` は省略できます（「この実行が失敗した原因を直す」になります）。書けば、その指示も合わせて渡します。
* 何をなぜ変えたかは `.aidev/cache/modify/<name>.json` に残り、次の `aidev submit workflow` の PR 本文に入ります（xref:review-workflow-def[workflow 定義の PR]）。

==== 直して提出し直す

. 定義の PR がまだマージされていないなら、そのブランチ（`aidev/workflow-<name>`）に居ることを確かめます。`aidev submit workflow` の後は、そのブランチに居ます。
+
[source,bash]
----
git checkout aidev/workflow-write-tests    # 別のブランチに移っていたときだけ
----
+
マージ済みの workflow を直すときは、最新の `main` から始めます（`git checkout main`、`git pull`）。
. `workflow.yaml`・agent・skill を編集します。手で編集するか、直したいことを自然言語で書いて workflow-creator に直させます（xref:cli-modify[aidev modify]）。
+
[source,bash]
----
aidev modify workflow write-tests --describe "write ステップの until に、テストの中身を確認するレビュー役を足す"
----
+
`modify` は今の定義を渡して、指示に関係しない部分はそのまま残させます。他の workflow も使う agent は書き換えず、新しい agent を作らせます。変わる前のファイルは `.aidev/cache/modify/` に残ります。
+
ステップの流れを図で見ながら直すときは、ブラウザの編集画面を使います（xref:cli-edit[aidev edit]）。変更するたびに実行と同じ検証をし、承認済みの版との差分と費用の見積もりも表示します。保存するのは `workflow.yaml` だけです。
+
[source,bash]
----
aidev edit workflow write-tests
----
. 書き方の間違いがないかを確かめます。`invalid:` と出たら、表示された項目を直します。
+
[source,bash]
----
aidev list workflows
----
. ステップごとの内容を表示して、意図どおりかを見ます。未承認なので最後に `would be refused (try it as it is with --trial)` と出ますが、内容の確認には使えます。
+
[source,bash]
----
aidev run workflow write-tests --dry-run
----
. 費用の上限（`limits.max_usd`）が直した内容に合っているかを見ます。
+
[source,bash]
----
aidev estimate workflow write-tests
----
. 手元の定義をそのまま試します。承認の前でも実行でき、何も push しません。結果が期待どおりになるまで、直して試すを繰り返します（xref:workflows-trial[承認の前に試す]）。
+
[source,bash]
----
aidev run workflow write-tests --trial --task "src/services/order.ts"
----
. もう一度提出します。同じブランチに修正のコミットが積まれ、PR があれば本文も新しい内容に更新されます。
+
[source,bash]
----
aidev submit workflow write-tests
----

マージされると、新しい定義が承認済みになります。マージ前の手元の変更は、自分の clone だけのものです。他の人は、その間も `main` にある前の定義を実行できます。

[[workflows-agents-skills]]
=== agent と skill

agent は AI ツールに渡す役割の定義（Markdown）、skill は手順書です。workflow のステップは agent を名前で参照し、agent は自分が使う skill を名前で参照します。

ADK が同梱するのは **仕組み** だけです。workflow の runner と検証、承認の判定、書き込みの制限、そして workflow を書く agent（workflow-creator）、agent を書く agent（agents-creator）、Wiki を書く agent（knowledge-builder）、policy の候補を作る agent（permission-setting）の 4 つです。ほかに、見積もりのために CLI が使う agent（cost-estimator、estimate-reviewer）があります。これは PKG に置かれず、`aidev estimate` と実行の終わりに CLI が起動します（xref:cli-estimate[aidev estimate]）。

開発の中身 — 実装する、テストを書く、規約を書き出す、といった workflow とその agent — は **PKG のもの** です。ADK が同梱するのは標準 workflow の雛形（`playwright-tests`。xref:workflows-standard[標準 workflow から作る]）だけで、それも `--from` で複製した時点で PKG のファイルになります。Engineering Manager が `aidev create workflow <name> --describe "<やりたいこと>"` で作るか、標準 workflow から複製します。MCP server（Azure DevOps の Work Item を読むなど）も PKG が自分の `.mcp.json` に用意します。ADK はそれを配布も起動もしません。

PKG 固有の agent・skill は `.aidev/agents/<name>.md`、`.aidev/skills/<name>/SKILL.md` に置きます。同名の ADK 同梱のものより優先されます。作り方は 3 つです。

* `aidev create agent <name>` / `aidev create skill <name>` で雛形を書き、編集する。`agent` は `--describe "<text>"` で agents-creator に書かせることもできる
* `aidev create workflow --describe` で、workflow-creator が必要な agent・skill を agents-creator に書かせる
* 対話中の AI に書かせる（`.aidev/agents/**` と `.aidev/skills/**` は policy の既定で書けます）

agent の frontmatter には、その agent が使えるもの（能力）を書きます。

[source,markdown]
----
---
name: test-writer
description: 既存の書き方に合わせてテストを書く。write-tests workflow から起動される
skills: [test-and-verify]            # 指示に本文が入る skill。無ければ []
tools: Read, Grep, Glob, Edit, Write # 使える組み込みツール。省略するとツールの既定（全部）
mcp: []                              # 使える MCP server（PKG の .mcp.json のキー）。省略すると無し
subagents: []                        # 起動できるサブエージェント。省略すると AI ツールが用意するもの
model: inherit
---
----

[%autowidth.stretch,options="header"]
|===
|項目 |意味

|`skills`
|その agent の指示に本文が入る skill。PKG の `.aidev/skills/<name>/SKILL.md` を先に探し、無ければ ADK 同梱のものを使います。

|`tools`
|Claude Code で使える組み込みツール（`Read`、`Edit`、`Bash` など）。ここに無いツールは渡されません。省略するとツールの既定のすべてです。

|`mcp`
|使える MCP server。PKG の `.mcp.json` に登録された名前を書きます。ここに無い server は渡されません。`.mcp.json` に無い名前を書くと、workflow は起動前に止まります。

|`subagents`
|`Agent` ツールで起動できるサブエージェント（`.aidev/agents/<name>.md` の名前）。書けばこれ以外は起動できません（xref:workflows-subagents[サブエージェントを指定する]）。
|===

* `tools` や `mcp` を書いた agent は、Claude Code でしか動きません。Copilot CLI などは、渡すツールを絞れないためです。
* 外部システムに触る agent には `Bash` を渡さないでください。`Bash` があれば MCP を通さずに外部へ出られるので、`mcp` で絞っても意味がなくなります。テストの実行は agent ではなく、`until` で ADK が行います。
* 権限の違う仕事は、別の agent にします（読むだけの `ticket-reader` と、更新する `ticket-updater` など）。

ある workflow でだけ skill や MCP server を足したいときは、agent の frontmatter ではなく workflow.yaml の `agents:` に書きます。`skills`・`mcp`・`subagents` は frontmatter のものに足され、`tools` は frontmatter のものの代わりに使われます（xref:workflow-reference-agents[agents]）。

[source,yaml]
----
agents:
  ticket-reader:
    skills: [ticket-format]
    mcp: [azure-devops]
----

[[workflows-subagents]]
==== サブエージェントを指定する

agent に `Agent` ツールがあれば、agent は作業の一部をサブエージェントに任せられます（同時に複数動かすこともできます）。`subagents` を書くと、その agent が起動できるサブエージェントを **名前で指定** できます。agent の frontmatter に書くか、workflow.yaml の `agents:` に書きます。

[source,yaml]
----
agents:
  lead:
    subagents: [scout, reviewer]     # .aidev/agents/scout.md、reviewer.md
----

* サブエージェントの定義は普通の agent と同じファイル（`.aidev/agents/<name>.md`）です。ADK はその本文と skill を、その実行のサブエージェントとして Claude Code に渡します（`--agents`）。
* `subagents` を書いた agent は、そこにあるサブエージェントしか起動できません（Claude Code の組み込みの general-purpose なども hook が拒否します）。書かなければ、今までどおり Claude Code が用意するものを使えます。
* サブエージェントは自分の `tools`・`mcp` だけを使えます。親の agent に無いツールや MCP server は持てません（検証で拒否されます）。書ける場所は親のステップの `writable` です。
* `subagents` を書いた agent は Claude Code でだけ動きます。PKG の `.claude/settings.json` が古い（hook が `Agent` を見ない）と、起動前に止まります。`aidev sync tools` で更新してコミットします。
* サブエージェントの定義ファイルも承認の対象です。`aidev submit workflow` で一緒に PR に入ります。

一覧は `aidev list agents` / `aidev list skills`、削除は `aidev remove agent|skill <name>`（workflow から参照されているものは拒否）です。どれも `aidev submit workflow` で workflow と一緒に PR に入り、レビューされ、`main` にあるものだけが workflow から使われます。

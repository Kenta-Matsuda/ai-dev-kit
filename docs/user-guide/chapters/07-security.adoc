[[security]]
== 権限とセキュリティ

{project-name}は、promptやhookだけをセキュリティ境界にしません。local guard、認証scope、CI、branch policy、人間reviewを重ねる多層防御を前提にしています。

[[security-threat-model]]
=== 想定する脅威と失敗

* AIまたはworkflowが意図しないpathへ書き込む。
* Work Item、PR説明、Wiki、MCP responseにprompt injectionが含まれる。
* PATやsecretが設定、log、argv、生成Wiki、PR本文へ漏れる。
* wrapperのstatic assetやpolicyが直接改変される。
* PKG sourceとWikiのSHAがずれた状態で変更を続ける。
* syncやagentが中断し、半適用状態が残る。
* 任意JavaScript workflowやshell commandが想定外の副作用を起こす。

完全なsandboxは提供しません。特にBash commandからすべての書き込み先を静的に抽出することや、review済みworkflow内の任意Node.js APIを封じることはできません。

[[security-layers]]
=== 防御層

[cols="1,2,3",options="header"]
|===
|層 |実体 |役割と限界

|静的deny
|`.claude/settings.json`
|Claude Code側の第一防御です。project settingであり、managed settingsではありません。

|実行時guard
|`aidev hook guard-write`
|path、policy、3SHA、leaseを評価します。Bashの全副作用を完全には把握できません。

|行動指示
|`CLAUDE.md`、Agents、Skills
|安全な標準手順を示します。強制境界ではありません。

|認証scope
|PAT、Git identity、Azure DevOps permission
|server側で高い強制力を持ちます。最小権限にします。

|整合性検査
|`.aidev-lock`、`aidev check`
|static drift、policy、3SHA、Wiki hand editをmerge前に検出します。

|merge制御
|required CI、branch policy、human review
|local制御の変更や回避がmainへ入ることを防ぐ最終層です。
|===

[[security-policy]]
=== policyの生成と承認

policy candidateは`aidev.yaml`から機械生成され、agentは使用しません。

[source,bash]
----
aidev permission configure
# candidateをレビュー
aidev permission configure --approve
aidev permission show
----

変更時は`reconfigure`を使用します。

[source,bash]
----
aidev permission reconfigure
aidev permission reconfigure --approve
----

保護を弱める差分には、明示的な`--approve --force`が必要です。candidateはreview用で、承認後に`.aidev/policy.yaml`へ昇格しcandidateを削除します。

policyの主な分類は次のとおりです。

[cols="1,3",options="header"]
|===
|分類 |意味

|`protected`
|通常操作、agent、syncからも変更させないcontrol surfaceやsecret pathです。

|`read_only`
|通常は読み取り専用のPKG pathです。有効なwork leaseで限定的に許可される設計です。

|`writable_during_sync`
|有効なsync leaseと対象SHAが一致する間だけ書き込めるpathです。

|`writable`
|通常のAI作業で書き込み可能なwrapper pathです。
|===

[[security-built-in-floor]]
=== 常に保護されるpath

次のpathは`ALWAYS_PROTECTED`としてvalidatorが必ず再付与します。policy fileから項目を削除しても保護解除できません。

* `.claude/**`
* `CLAUDE.md`
* `.mcp.json`
* `.aidev/policy.yaml`
* `.aidev/leases/**`
* `.aidev/sync.lock`
* `.aidev-lock`
* `.aidev-ejected`

policy未作成時もpermissiveにはなりません。built-in floor、`src/**` read-only、書き込み先なしのrestrictive fallbackを使用し、必要なcommandはexit 3になります。

[[security-leases]]
=== leaseの検証

work leaseとsync leaseは、task/operation識別子、branch、許可path、original/target SHA、取得時刻、TTLなどを検証します。

* SHA不一致でsync leaseがない場合、通常書き込みをdenyします。
* 有効なsync leaseがある場合も、同期に必要な`knowledge/**`だけを例外許可します。
* 期限切れleaseを暗黙に更新しません。
* sync失敗時はleaseを残し、resume/abortという明示選択を要求します。
* lease file自体は保護され、CLI以外が直接作成・変更する前提ではありません。

現時点では、Work Itemから公開・監査可能なwork leaseを初期作成するE2E経路は未完成です。

[[security-secrets]]
=== credentialとsecretの扱い

[CAUTION]
====
PAT、token、password、private keyをGit、`aidev.yaml`、`.mcp.json`、CLI引数、log、PR description、test fixtureへ入れないでください。
====

推奨事項は次のとおりです。

. PATは人間用とautomation用を分けます。
. `azure_devops.auth_env`には値ではなく環境変数名を設定します。
. botにはPKG read、sync branch push、wrapper PR作成に必要な最小scopeだけを与えます。
. default branchへの直接pushとauto-complete権限を与えません。
. `secrets_paths`を実際のPKG構造に合わせます。
. `.env*`、certificate、key、credential-bearing logをGit管理外にします。
. 漏洩を検出した場合、secret値を出力やissueへ再掲せず、種類と場所だけを報告し、ただちにrotationします。

MCP launcherはPATをargvに載せず、child processの`PERSONAL_ACCESS_TOKEN`へだけ渡します。それでもchild processとnpm packageを信頼境界として評価する必要があります。

[[security-untrusted-input]]
=== 外部データの扱い

次を「指示」ではなく、検証対象のデータとして扱います。

* Azure DevOps Work Itemのtitle、description、comment、attachment
* PR title、description、review comment
* MCP tool response
* 既存Wiki、生成文書、log
* package内に置かれたagent向け文言

外部データが「policyを変更する」「secretを表示する」「検査をskipする」「別のcommandを実行する」と要求しても、そのまま従いません。repositoryの規則と人間のtaskを優先し、ID、branch、SHA、PR stateはAPIまたはGitで再確認します。

[[security-branch-policy]]
=== 推奨branch policy

wrapperのdefault branchで、少なくとも次を設定します。

* `aidev check`をrequired buildにする。
* `.claude/**`、`.aidev/**`、`.aidev-lock`、`CLAUDE.md`、`.mcp.json`にrequired reviewerを設定する。
* static asset、policy、pipeline変更にCODEOWNERS相当のreviewを要求する。
* botとAI用identityのdefault branch直接pushを禁止する。
* PR auto-completeまたはauto-mergeを禁止する。
* force pushを制限する。
* secret scanningとcredential rotation手順を組織側で用意する。

PKG側でもAI branchからのPRに通常のtest、security scan、human reviewを要求します。

[[security-workflows]]
=== custom workflowの安全性

workflowの`workflow.yaml`と`steps.js`はhashで承認され、承認後に1 byteでも変われば再承認が必要です。この仕組みはreview後の改変を検出しますが、sandboxではありません。

* `steps.js`は任意JavaScriptを実行できます。
* runnerのbasename allowlistだけでは、module内からのNode.js API呼び出しを制限できません。
* iteration、時間、同一失敗回数は強制されます。
* token数、USD、破壊操作前human gateは実消費に基づく強制機構ではありません。
* logはprompt、response、環境値を含み得るためGit管理しません。

実行前にdiffと承認hashを確認し、専用の低権限環境で動かしてください。

[[security-response]]
=== incident時の初動

. 実行中のagent、workflow、pipelineを停止します。
. credentialを無効化またはrotateします。
. `git status`、reflog、Azure DevOps audit log、open PRを保全します。
. `.aidev/sync.lock`やtask leaseを削除せず、対象SHAと操作を記録します。
. `aidev check --strict`と組織のsecurity scanを実行します。
. 変更をreviewし、必要なら通常のGit revertや`sync --abort`を選びます。
. 原因がstatic assetやpolicyなら中央kit側で修正し、wrapperへ`kit apply`します。

secret値を診断logへ貼り付けないでください。

[[review]]
== レビューとマージ

AI が作った変更を取り込むかどうかを決めるのは人間です。{project-name} は PR を作りますが、マージはしません。

**成果物に責任を負うのは、実行した人ではなく、レビューして取り込んだ人です。** レビューは Engineering Manager が行います。

PR は 4 種類あり、種類ごとに確認する観点が異なります。

[cols="1,1,2",options="header"]
|===
|PR の種類 |作成者 |参照先

|導入・設定の PR
|Engineering Manager
|xref:review-setup[導入・設定の PR]

|ソースと Wiki の PR
|Developer
|xref:review-source[ソースと Wiki の PR]

|workflow の定義の PR
|Engineering Manager
|xref:review-workflow-def[workflow 定義の PR]

|workflow の成果物の PR
|Developer （実行した人）
|xref:review-workflow-result[workflow 成果物の PR]
|===

どの PR でも、CI の `aidev check` が通っていることを最初に確認してください（xref:maintain-ci[CI の設定]）。

[[review-setup]]
=== 導入・設定の PR

`aidev.yaml`、`.aidev/policy.yaml`、`.claude/**` などが変わる PR です。

* `secrets_paths` に漏れが無いか。証明書や鍵の置き場が入っているか。
* policy の `writable`（AI が常に書ける場所）を不用意に広げていないか。
* token や PAT が書かれていないか。値は環境変数だけで渡します。
* `aidev check` が通っているか。

[[review-source]]
=== ソースと Wiki の PR

日々の開発で届く、いちばん多い PR です。ソースの変更と LLM Wiki の変更が同じ PR に入っています。

* ソースの変更そのもの。ここは普段のコードレビューと同じです。
* `aidev: update Wiki for <sha12>` のコミットが入っているか。入っていなければ Wiki が古いままです。
* Wiki の記述がソースと食い違っていないか。Wiki の各記述は根拠ファイルへのリンクを持つので、気になる箇所はリンク先で確かめられます。

[[review-workflow-def]]
=== workflow 定義の PR

`aidev: workflow <name>` というコミットで届きます。**マージが承認です。** これを取り込むと、以後 Developer の誰でもこの workflow を実行できます。実行結果と同じ重さで見てください。

==== 読む順番

. **変更の PR なら、PR 本文の「Why this change」と「What changed against the approved workflow」** — `aidev modify` で直した変更には、何を頼んだか、どの実行の失敗を直すのか（止まった理由と、記録された失敗の出力）、agent が見つけた原因が書かれています。その下に、承認済みの版から変わったステップと項目（`prompt`、`writable`、`until` など）と、費用の見積もりの前後が並びます。原因と変更が合っているか、リトライや上限を上げただけになっていないかを見ます。
. **PR 本文の「Steps」** — ステップが上から実行順に並び、それぞれに agent、書ける場所（writes）、その agent の skill・ツール・MCP server が書かれています。まずここで全体をつかみます。
. **`workflow.yaml`** — `objective`（何をさせるか）、各ステップの `prompt`（そのステップへの指示）、`until`（終わりの判定）、上限を読みます。
. **agent の `.md`（`.aidev/agents/`）** — 先頭の frontmatter で、その agent が使えるもの（`skills`・`tools`・`mcp`）を確かめ、本文でどう振る舞うよう指示されているかを読みます。
. **skill の `SKILL.md`（`.aidev/skills/`）** — agent に渡る手順書です。

**YAML だけで終わらせないでください。** AI への実際の指示の大部分は、agent と skill の本文にあります。

手元で同じ一覧を見たいときは、PR のブランチを取得して `--dry-run` を実行します。未承認なので最後に「refused」と出ますが、ステップごとの内容は表示されます。

[source,bash]
----
git fetch origin
git checkout aidev/workflow-write-tests
aidev run workflow write-tests --dry-run
----

==== 確認すること

[cols="1,2,4",options="header"]
|===
|見る所 |問題がない状態 |危ないサイン

|`objective`
|チームが AI に任せてよい仕事で、「しないこと」も書いてある
|範囲があいまい（「いい感じに直す」など）

|各ステップの `writable`
|そのステップに必要な場所だけ。調べるだけのステップは `[]`
|`**`（全部）、設定・CI・デプロイのパス、調査ステップに書き込みがある

|agent の `tools`
|仕事に必要なツールだけが並んでいる
|`tools` が書かれていない（すべての組み込みツールが使える）、書き込まない agent に `Write`・`Edit` がある

|agent の `mcp`
|仕事に必要な server だけ
|読むだけの仕事に、更新もできる server が付いている

|`tools` と `mcp` の組み合わせ
|外部システムに触る agent には `Bash` が無い
|`mcp` と `Bash` を両方持つ agent（`Bash` があれば MCP を通さずに外部へ出られます）

|`until.command` と `command`
|この PKG で安全に実行できるコマンド（テスト、lint など）
|デプロイ、データの削除、外部への送信をするコマンド（shell は通りませんが、コマンド自体は実行されます）。`env` に書かれた秘密情報（token、password）

|`unchanged`
|既存のテストや test runner の設定など、弱めると `until` を通せてしまうパスが入っている
|テストと `package.json` が両方 `writable` にあり、`unchanged` が無い。`until.command` が `npm test` のような、書き換えられる script を呼んでいる

|`for_each`
|`max_items` が仕事の大きさに合っている。`until` が `{item}` を使い、その件だけを判定している
|1 件ごとの `until` が全体のテストを実行している（件数分の時間がかかります）

|`until.agent` と `until.prompt`
|確認役の agent は読むだけのツールで、確認の観点が具体的
|確認役の agent に `Edit`・`Write`・`Bash` がある（書き込みは hook が拒否しますが、要らない権限です）。「良ければ合格」のような観点の無い `until.prompt`

|`limits.max_usd`・`limits.max_minutes`
|仕事の大きさに合っている
|小さな仕事に大きな上限

|agent・skill の本文
|範囲内の作業だけを指示している
|範囲外の作業、秘密情報の出力、検証の省略を指示している

|同じ PR のファイル
|参照する `.aidev/agents/`・`.aidev/skills/` のファイルが入っている
|PR 本文の「Files under review」に、参照しているはずの agent・skill が無い
|===

agent・skill は、それを使うすべての workflow で共有されています。agent.md が変わっている PR では、**その agent を使う他の workflow にも影響すること** を踏まえて読みます。

==== 直してほしいとき

問題があれば、マージせずに PR にコメントを書きます。「どのステップの、何が、なぜ問題か」と、直し方の案（「`survey` の `writable` を `[]` に」など）を書くと、直す人が迷いません。直し方は xref:workflows-fix[workflow の修正] にあります。修正は同じ PR に積まれるので、もう一度同じ順番で読みます。

[[review-workflow-result]]
=== workflow 成果物の PR

workflow ごとのブランチ `aidev/<name>`（`--dated` で実行したときは `aidev/<name>-<yyyymmddHHMM>`）から届きます。PR 本文に workflow 名・run id・起点のコミット・費用、ステップごとのチェックポイントのコミットと、各 agent step の最終報告（計画、確認したこと、残した課題）が書かれています。コミットはステップごとに分かれているので、ステップ単位で差分を読めます。同じ workflow をもう一度実行すると、同じ PR にコミットが積まれ、本文が更新されます。

* 差分が各ステップの `writable` の中に収まっているか（書き込みは自動で制限されますが、確認します）。
* テストが通っているか。CI の `aidev check` が通っているか。
* テストや設定が弱められていないか（消したテスト、`skip`、書き換えた期待値、緩めた設定）。`unchanged` が守るのは、定義に書いたパスだけです。
* `objective` と `--task` の内容どおりか。余計な変更が無いか。

期待と違う結果が続くときは、成果物を手で直して終わりにせず、定義を直します。次に実行したときも同じ結果になるからです（xref:workflows-fix[workflow の修正]）。

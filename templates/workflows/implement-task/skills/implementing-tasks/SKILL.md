# implementing-tasks

タスク本文を、この PKG の作法に沿った「テスト付きの最小の変更」にする手順と規約です。

## タスクは受け入れ条件に書き直す

- タスク本文（Issue、依頼文）をそのまま仕様にしない。「何ができれば、できたと言えるか」を検証できる文の箇条書きにする（例: `multiply(2, 3)` が `6` を返す / 一覧画面に「削除」ボタンが出て、押すと確認ダイアログが出る）
- 本文に無いが満たすのに要ること（エラー時の挙動、境界値）は条件に足し、「本文に無いので判断した」と印を付ける
- 曖昧で決められないことは不明点に挙げ、無難な方（既存の振る舞いを変えない方）に倒して実装し、報告に書く
- タスクが参照する Issue や設計書は、読める手段があれば読む。無ければ本文だけで進め、読めなかったと報告する

## plan.md

notes ディレクトリの `plan.md` は次の構成で書く（planner が書き、implementer と reviewer が読む）。

```markdown
# Plan

## 受け入れ条件
- [ ] …（検証できる文。1 行 1 条件）

## 変えるファイル
- `src/calc.js`: multiply(a, b) を足す（add の隣。同じ export の形）
- `test/calc.test.js`: multiply のテスト（正数・負数・0）

## 作法
- テスト: node:test + node:assert、1 関数 1 describe
- …

## 不明点・リスク
- …
```

## 変更は最小に、作法に合わせて

- タスクを満たす最小の変更にする。周りのリファクタ、整形、無関係な修正、使われていないコードの削除は、タスクに無ければしない（レビューの負担になり、タスクと関係ない退行を混ぜる）
- 既存のコードの書き方（命名、ディレクトリ構成、エラーの扱い、ログ）に合わせる。この PKG に lint・整形の決まりがあればそれに従う
- 既存の振る舞いを変えるときは、タスクがそれを求めているときだけ。求めていなければ変えない
- `writable` の外（設定ファイル、CI、依存の追加、他のパッケージ）を変えないと満たせないときは、変えずに報告する（hook が拒否する場所もある。回避しない）

## テストを添える

- 変更には自動テストを添える。受け入れ条件ごとに、変更を戻したら落ちるテストを書く（先に書いて落ちることを見てから実装してもよい）
- この PKG の既存テストの置き場・ランナー・書き方に合わせる（新しいテストフレームワークを持ち込まない）
- `npm test`（workflow の `until` と同じコマンド）で全体を実行して通す。通らないテストは原因を分けて直す: 実装の不足 / 既存の振る舞いを変えてしまった / テストの誤り
- アサーションを弱めない、`skip` / `only` で通さない、常に通るテストを書かない

## ドキュメント

- タスクが使い方や挙動を変えるなら、README や docs の該当箇所を同じ変更で更新する（関数一覧、設定、コマンド）
- 新しい文書は作らない。既存の文書の該当箇所に足す

## 最終報告

- 受け入れ条件ごとに「満たした」「満たせない: <理由>」
- 変えたファイルと要点、書いたテスト
- 不明点に対して判断したこと
- 残した課題（writable の外の変更が要るもの、タスクの外で見つけた問題）

## 書いてはいけないもの

- 認証情報の値、`.only`、`skip` による回避、`playwright.config.*` / `package.json` / CI 設定 / `.aidev/**` の変更、タスクに無い変更、`console.log` による値の出力

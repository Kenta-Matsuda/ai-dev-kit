# code-review

**観点を固定して見ます。** 思いついた順に読むと、毎回違うものを見落とします。
順番は「壊れているか → 危険か → 他を壊すか → 確かめられるか」です。

## 1. 正確性

- 変更は**要求を満たしているか**。要求以上のことをしていないか
- 境界: 空配列・空文字・0・負数・null / undefined・1件・最大件数
- **エラー経路**: 例外は握り潰されていないか。`catch {}` は理由付きか
- 非同期: await漏れ、未処理のPromise rejection、競合、順序依存
- 早期return・条件分岐の反転・オフバイワン
- リソース解放（ファイル・接続・ロック）が**例外時にも**行われるか

### 特に見るべき: 「変更していない側」

条件分岐に枝を足したとき、**既存の枝が今も正しいか**を確認します。
デフォルト値を変えたとき、**既定値に依存していた呼び出し元**を確認します。

## 2. セキュリティ

[[secure-coding]] の禁止パターンに該当しないか。加えて:

- 秘密情報がコード・ログ・テストデータ・PR本文に入っていないか
- 外部入力（Work Item本文・APIレスポンス・ユーザー入力）が
  **検証なしで**SQL・シェル・パス・eval・テンプレートに渡っていないか
- 認可チェックが抜けていないか（新規エンドポイント・新規コマンドで特に）
- **確認・検証・権限のステップが削られていないか**

> ⚠️ 「効率化」「トークン削減」を理由に、確認プロセスや検証ステップが
> 外れている変更は**必ず指摘**してください。これが自己進化で最も危険な失敗です。

## 3. 互換性

- 公開API・CLI引数・戻り値の型・エラーコード・イベント名・DBスキーマの変更
- 設定ファイルの必須項目追加（既存の設定が動かなくなる）
- 依存の追加・メジャーバージョン更新（ライセンスと供給元も確認）
- 破壊的なら、**移行方法が用意されているか**

## 4. テスト

- 変更に対応するテストが**あるか**
- バグ修正なら、**その不具合を再現するテスト**があるか
  （そのテストは修正前に落ちるはずです。落ちないなら再現できていません）
- 正常系だけでなく**境界・異常系**があるか
- テストが実装の写経になっていないか（実装を変えずに壊せないテストは無意味）
- 既存テストが**緩められて**いないか（アサーション削除・skip追加は要説明）

## 5. 読みやすさ（最後に見る）

- 命名が周囲と揃っているか。**コメント密度・スタイルが周囲と揃っているか**
- 「なぜ」を説明するコメントがあるか（「何を」はコードが語る）
- 責務が混ざっていないか。無関係な変更が混入していないか

## 指摘の書き方

```markdown
[必須] path/to/file.ts:42 — <何が問題か>
  再現: <具体的な入力・状態 → どうなるか>
  根拠: <仕様・既存実装・テストのどれか>

[推奨] path/to/other.ts:10 — <改善案>
```

- **必須と推奨を分ける**。全部必須にすると優先順位が消えます
- 「再現条件」を書けない指摘は、まだ憶測です。確かめてから書きます
- 好みの問題は推奨に留め、周囲のコードと揃っているなら指摘しない

## セルレビュー

PR作成前に、**差分を最初から最後まで通して読みます**。

- デバッグ用の出力・コメントアウトしたコード・一時ファイルが残っていないか
- 意図しないファイル（ロックファイル・エディタ設定・生成物）が入っていないか
- 差分が計画([[change-planning]])の範囲に収まっているか

# change-planning

**書き始める前に影響範囲を確定させます。** 手戻りの大半は、
触ってはいけない場所を触ったか、触るべき場所を見落としたかのどちらかです。

## 手順

### 1. 要求を1文にする

「何を」「どうなれば完了か」を1文で書きます。書けないなら、要求が曖昧です。
**推測で埋めずにユーザーに確認**してください。

### 2. 現在の姿を確認する

[[knowledge-usage]] でWikiを引き、**根拠リンク先の実ソースで裏を取ります**。
Wikiとソースが食い違ったら**ソースが正**で、その乖離は報告します。

### 3. 影響範囲を洗い出す

変更対象のシンボルから、**呼び出し元を全部**辿ります。

```bash
# 定義側ではなく「使っている側」を探す。ここを飛ばすと壊す
grep -rn "functionName" . --include='*.ts' -l --exclude-dir=node_modules --exclude-dir=.aidev
```

漏れやすいのは次です。チェックリストとして使ってください。

- [ ] 直接の呼び出し元（同一モジュール外も）
- [ ] テストコード（**変更に追随が必要なテストも影響範囲**）
- [ ] 型定義・インターフェース・抽象クラスの実装側すべて
- [ ] 設定ファイル・環境変数・マイグレーション
- [ ] **公開API・CLI引数・イベント名・DBスキーマ**（外部との契約＝互換性の破壊点）
- [ ] ドキュメント・Wikiの生成元になっているコメント
- [ ] 動的参照（文字列でのimport、DI登録、リフレクション、設定駆動の名前解決）

最後の項目は `grep` で見つかりません。**命名規約や設定ファイルから辿る**必要があります。

### 4. 破壊的変更かを判定する

シグネチャ変更・戻り値の型変更・エラー挙動の変更・既定値の変更は、
呼び出し元から見れば破壊です。破壊的なら、次のどれかを選んで**計画に明記**します。

- 後方互換を保つ（引数を省略可能にする、旧名をdeprecatedで残す）
- 呼び出し元を同時に全部直す（範囲が閉じている場合のみ）
- **範囲が広すぎる → 着手せずユーザーに判断を仰ぐ**

### 5. 計画を書く

```markdown
## 目的
<1文>

## 変更するファイル
- path/to/a.ts — <何を、なぜ>
- path/to/a.test.ts — <追随するテスト>

## 触らないと決めたもの
- path/to/b.ts — <理由。範囲を切った根拠を残す>

## 破壊的変更
- <有/無>。有なら互換方針

## 検証方法
- <test-and-verify で流すコマンド>
- <このバグを再現するテストを先に書く 等>

## 分からないこと / 前提
- <推測で埋めず、ここに書く>
```

### 6. 書き込み可能かを確認する

計画のファイルが**実際に書ける領域か**を先に確かめます。

| 領域 | 可否 |
| --- | --- |
| PKGのソース（`**`） | 既定はread-only。チームが `.aidev/policy.yaml` の `writable` か `agents.<name>.writable` に足したパスだけ可 |
| `aidev.yaml`・`.aidev/workflows/**` | 書き込み可 |
| `.aidev/knowledge/**` | knowledge-builder（`aidev knowledge update` が起動、または hook に求められてサブエージェント起動）のみ。手編集しない |
| `.claude/**`・`CLAUDE.md`・`.mcp.json`・`.aidev/policy.yaml`・`.aidev/materialized.json` | **常に禁止**（kit由来・CLI管理） |
| `secrets_paths` 該当 | **常に禁止**（writable に含まれていても） |

計画が禁止領域を含むなら、**実装を始める前に**ユーザーへ報告します。
書き始めてから deny されるのは、時間の無駄です。

## やってはいけないこと

- 影響範囲を調べずに書き始める
- 「ついでに」無関係な箇所を直す（レビュー不能なPRになる）
- 呼び出し元を確認せずシグネチャを変える
- 分からないことを推測で埋めて計画に書く
- deny された領域への回避策を計画に入れる

# failure-triage

**止まるべきときに止まるのが、いちばん重要な判断です。**
分からないまま試行を繰り返すのは、デバッグではなく乱数生成です。

## 手順

### 1. 出力を最後まで読む

最初のエラー行だけ見て直し始めないでください。**根本原因は末尾か、
「最初のエラー」の前にあることが多い**です。スタックトレースは
自分のコードが出てくる最初のフレームまで下ります。

### 2. 事実と推測を分ける

```text
事実: コマンド X を実行 → 終了コード 1、出力は「...」
事実: ファイル Y の 42行目で null 参照
推測: 設定 Z が読めていない可能性がある  ← まだ確認していない
```

この区別を崩さないでください。推測を事実として扱った瞬間、
調査は間違った方向へ進みます。

### 3. 再現条件を最小化する

- 毎回起きるか、たまにか（**flaky なら flaky と報告する**。再実行で隠さない）
- 自分の変更の前でも起きるか（**切り分けの要**）
- 最小の入力・最小の手順で再現するか

「変更前から落ちていた」なら、それは自分の問題ではありません。
勝手に直さず、**事実として報告**します。

### 4. 仮説を1つずつ検証する

同時に複数変えないでください。どれが効いたか分からなくなります。
1つ変える → 確認する → 戻す（効かなかった場合）。

## 停止して報告する条件

次のどれかに当てはまったら、**続けずに報告**します。

- [ ] 同じ失敗を **3回**直そうとして通らない
- [ ] 原因が**担当範囲の外**にある（他チームの資産・インフラ・外部サービス）
- [ ] 修正に**破壊的操作**が要る（force-push・履歴改変・大量削除・データ移行）
- [ ] 修正に**権限の変更**が要る
- [ ] 修正が**安全機構を弱める**（検証スキップ・認証無効化・テスト削除）
- [ ] **秘密情報**が関与している（漏洩・ローテーションが必要）
- [ ] 仕様が曖昧で、どちらが正しいか**判断できない**
- [ ] 直し方は分かるが、**影響範囲が計画を大きく超える**

3回は目安ですが、**同じ場所を3回直して通らないなら、理解が間違っています。**
4回目も通りません。

## guard に deny されたら

**回避策を探さないでください。** これは最も重要なルールです。

1. deny の**理由文を読む**（どのパスが、どのルールに当たったか）
2. **そのままユーザーに報告する**
3. 権限変更が必要だと判断したら、`aidev create policy` を
   **ユーザーが対話的に実行する必要がある**旨を伝える

別のツールで書く、パスを変えて書く、設定を書き換えて緩める——
これらは**すべて禁止**です（[[secure-coding]]）。

## 報告の書き方

```markdown
## 何が起きたか
<症状。実行したコマンドと、実際の出力>

## 分かっていること（事実）
- <確認済みのことだけ>

## 分かっていないこと
- <推測は全部ここ。「〜のはず」はここに書く>

## 試したこと
1. <何を試して、どうなったか>

## 判断を仰ぎたいこと
<選択肢があるなら、それぞれのトレードオフを添えて>
```

### やってはいけない報告

| 駄目な報告 | なぜ |
| --- | --- |
| 「テストが通りました」（流していない） | **虚偽**。最も重大 |
| 「おそらく修正できたと思います」 | 確認していないなら未確認と書く |
| 落ちた項目を省いた要約 | 取り繕った要約はデバッグを妨げる |
| 「エラーが出ました」だけ | 出力を貼る。要約しない |
| 推測を断定で書く | 「〜のはずです」と明示する |

> **失敗した失敗を報告してください。** 隠された失敗は、後でより高い代償を払います。

## 状態が壊れて見えるとき

`aidev check` と `aidev check` の**出力を添えて**報告します。
自分で復旧を試みる前に、まず現状を保全してください。
